# 多标的策略支持实现方案

> 状态：Runtime v3 已在本地实现，Migration 0013 已应用；未部署生产。
> 验证证据：[策略多标的本地验收记录](策略多标的本地验收记录.md)。
> 日期：2026-10-27

## 1. 目标与当前差距

支持**一份策略联合使用多个标的的数据，自行计算因子、分配仓位和管理交易**。协整配对只是一个例子，同样应能表达在预先绑定的标的集合内计算因子并动态选择持仓、多空组合、动态权重、分批调仓，以及同时维护多个逻辑组合。

平台提供通用的数据、持仓、账户与订单能力；具体组合结构和交易规则归策略代码。不能因为某个例子需要两腿联动，就把运行时固定成两腿、固定比例、一次持有一篮子或统一开平仓。

**本次范围：支持预先指定的多个标的。** 在 Replay 开始前明确并冻结标的集合，准备其所需行情；策略可在集合内部自由计算和组合因子、动态筛选持仓、分配仓位并调仓，实际持仓无需固定。

当前已经能让同一份代码换标的回测，但一个策略实例仍只有单标的执行能力：

| 位置 | 当前约束 | 核心调整 |
| --- | --- | --- |
| `strategy_runtime/api.py`、`runtime.py`、`indicators.py` | 行情和指标按周期索引；`ctx.position` 为单个持仓 | 行情、指标增加标的维度，提供标的集合与持仓映射 |
| `backtest/engine.py`、`broker.py` | 一条主行情流、一个持仓，全局至多一个改仓 Intent | 多流同步推进，一个策略实例联合决策，支持多笔调仓 |
| `controller/replay_execution.py`、`backtest/executor.py` | 冻结、导出、校验一个 Instrument | 冻结并验证完整标的集合与数据依赖 |
| `agent/tools/types.py`、Main/Code Agent 提示词 | 单标的请求与代码契约 | 传递多标的设计、执行绑定与实际结果 |

复用现有 Strategy、Replay、Sandbox 和调用链，不增加业务架构层，也不新建因子平台。

## 2. 策略契约：标的集合、联合计算、自由调仓

新增 **Runtime API v3**，保留 v1/v2 的冻结行为。行情通过标的与周期两个独立维度寻址，各标的可以使用不同的周期配置。

**编码与调用规范：** 标的可使用 `asset_a/asset_b/benchmark` 等业务别名；每个标的内部的周期级别使用 `level_1/level_2/level_3` 等名称，按从小到大理解。信号周期与全局执行时钟分别声明，各标的的数据周期及预热需求可以不同。级别大小是策略编写时遵守的编码规范，是否符合该规范属于策略代码质量；外部调用不根据级别名额外校验 `level_1 < level_2 < level_3`，也不自动排序或修正参数。策略公开参数定义及说明，Main Agent 按说明传参，执行层使用实际参数准备数据并调用策略。

- **数据与持仓：** `ctx.instruments` 提供本次冻结的候选标的集合；行情、历史和指标使用 `(instrument, role)` 寻址；`ctx.positions[instrument]` 返回各标的持仓，`ctx.account` 返回共享账户。固定配对可用别名引用 A/B，集合策略可直接遍历全部标的，不要求代码预先写死交易腿数量，也不要求同时持有全部候选标的。
- **数据依赖：** StrategySpec 声明必要的数据、预热、市场和标的约束，允许仅用于因子或基准的只读标的；Replay 绑定实际 Instrument。策略确实依赖具体品种时保留限制，通用策略不被某次测试的标的锁死。
- **因子与组合：** 因子计算、跨标的排序、权重合成、风险预算、再平衡频率和多个逻辑组合的状态，放在策略代码或其辅助模块中。运行时提供数据与记录能力，不预设协整、等权或某种因子模型；所需统计依赖按实际需求加入固定版本的 Sandbox 白名单。
- **下单：** 支持一次回调调整多个标的，覆盖建仓、加仓、减仓、平仓和反向持仓。目标数量、目标权重、数量比例应有明确区分，不能共用含义模糊的数字字段。

### 2.1 v3 StrategySpec 完整声明

下面是已实现的 Runtime v3 声明形式。所有字段保持字面量声明，便于从代码提取 `runtime_contract`；声明描述参数和数据需求，具体标的与可配置周期在调用时提供。

```python
spec = StrategySpec(
    api_version=3,
    execution_timeframe={
        "binding": "configurable",
        "description": "整个策略联合回调和模拟撮合的周期，例如 5m",
    },
    instrument_roles={
        "asset_a": {
            "description": "策略使用的第一个标的",
            "tradable": True,
            "allowed_markets": ("spot", "futures"),
            "allowed_directions": ("long",),
        },
        "asset_b": {
            "description": "策略使用的第二个标的，可做多或做空",
            "tradable": True,
            "allowed_markets": ("futures",),
            "allowed_directions": ("long", "short"),
        },
    },
    data_roles={
        "asset_a": {
            "level_1": {
                "binding": "configurable",
                "description": "asset_a 的小周期，例如 15m",
            },
            "level_2": {
                "binding": "configurable",
                "description": "asset_a 的中周期，也是主要信号周期，例如 1h",
            },
            "level_3": {
                "binding": "configurable",
                "description": "asset_a 的大周期，例如 4h",
            },
        },
        "asset_b": {
            "level_1": {
                "binding": "configurable",
                "description": "asset_b 的小周期，也是主要信号周期，例如 4h",
            },
            "level_2": {
                "binding": "configurable",
                "description": "asset_b 的中周期，例如 12h",
            },
            "level_3": {
                "binding": "fixed",
                "timeframe": "1d",
                "description": "asset_b 使用的固定日线",
            },
        },
    },
    signal_levels={
        "asset_a": "level_2",
        "asset_b": "level_1",
    },
    warmup_bars={
        "asset_a": {"level_1": 61, "level_2": 21, "level_3": 21},
        "asset_b": {"level_1": 121, "level_2": 61, "level_3": 21},
    },
)
```

字段定义：

| 字段 | 声明形式与含义 |
| --- | --- |
| `api_version` | 固定为 `3`，区分 v1/v2 的调用契约和执行行为。 |
| `execution_timeframe` | 全局执行周期，使用 `binding/description` 声明；支持 `configurable`，或 `fixed` 并提供 `timeframe`。决定联合回调和普通订单下一 Open 的执行粒度；执行器为可交易标的准备对应行情，不要求策略级别中重复声明该周期。 |
| `instrument_roles` | 标的别名到参数说明、交易能力的映射。别名推荐小写 snake_case；具体交易对不写在通用策略逻辑中。`tradable=False` 表示仅用于数据或因子计算；可交易标的分别声明 `allowed_markets/allowed_directions`。确实限定品种时可增加 `allowed_symbols`。 |
| `data_roles` | 标的别名 → 周期级别 → 周期参数说明。每个标的独立声明，级别数量由策略需要决定，同名级别不要求使用相同周期。`description` 提供给 Main Agent，说明参数含义和应如何填写。 |
| `binding` | `configurable` 表示调用时提供具体周期；`fixed` 表示周期由策略声明，必须同时提供 `timeframe`。v3 不使用 `main_multiple` 自动计算跨级别周期；需要的周期关系写入参数说明并由策略编写遵守。 |
| `signal_levels` | 标的别名 → 主要信号级别名，例如 `asset_a → level_2`。这是策略声明的用途引用，实际信号周期取对应级别的绑定值，调用方不再重复传一份信号周期。不限制其它级别参与信号、因子或风控；没有单一主要信号周期的策略可以省略此字段。 |
| `warmup_bars` | 标的别名 → 周期级别 → 正式区间前需要的预热根数，未声明的级别按 `0` 处理。各标的独立统计；相同实际数据流的需求取最大值。 |

`level_1/level_2/level_3` 按从小到大命名是**编码规范**，不是外部绑定约束。v3 不使用 `timeframe_constraints` 强制检查这个顺序，也不根据名字推导、排序或替换周期。参数定义及说明由策略公开，Main Agent 据此填写；命名和策略实现是否符合说明属于代码质量。

上例是两个命名标的的声明，不限制运行时只能支持两个标的。需要遍历任意数量的预先指定标的时，上述按标的组织的映射可使用 `"*"` 作为默认声明，作用于本次提供的标的集合；同一字段中的具体别名声明优先，且完整替换该别名的默认声明，不做隐式深层合并。`"*"` 不是实际标的，也不自动发现标的；显式声明的别名必须在调用中提供，未显式声明的别名使用默认声明。这样集合策略无需因为候选数量变化而改写计算逻辑。

### 2.2 Main Agent 调用参数示例

对应上述声明，`replay_run` 提供的执行参数示意如下；`strategy_update` 使用 `runtime_api_version=3` 生成或显式迁移策略。

```json
{
  "expected_revision": 3,
  "instruments": {
    "asset_a": {"symbol": "BTC/USDT", "market_type": "futures", "contract_type": "perpetual"},
    "asset_b": {"symbol": "ETH/USDT", "market_type": "futures", "contract_type": "perpetual"}
  },
  "execution_timeframe": "5m",
  "timeframe_bindings": {
    "asset_a": {"level_1": "15m", "level_2": "1h", "level_3": "4h"},
    "asset_b": {"level_1": "4h", "level_2": "12h"}
  },
  "lookback_days": 90,
  "initial_capital": "10000",
  "leverage": "1"
}
```

`instruments` 在本次 Replay 中把别名解析为唯一 Instrument，并冻结其身份与规则。`timeframe_bindings` 只需传可配置级别；`asset_b.level_3=1d` 直接使用策略声明。此例中 A 的主要信号周期为 1h，B 为 4h，策略统一每 5m 获得一次回调。

策略代码按别名和级别读取，订单、持仓也使用同一套标的键：

```python
a_history = ctx.market.history(instrument="asset_a", role="level_2", bars=100)
b_history = ctx.market.history(instrument="asset_b", role="level_1", bars=100)
a_average = ctx.indicators.ema(instrument="asset_a", role="level_3", period=20)
a_position = ctx.positions["asset_a"]
```

### 2.3 目标仓位接口

以“逐标的目标数量”作为统一调仓基元，示意如下：

```python
# on_bar(ctx, bars)：同一决策时刻的各标的已收盘行情。
# 策略自行计算因子和目标仓位，下面的数量只是接口示意。
ctx.orders.set_targets(
    quantities={"asset_a": qty_a, "asset_b": qty_b},
    execution_policy="independent",
    reason="按策略目标调仓",
)
```

`quantities` 使用带符号的基础资产目标持仓量：正数做多、负数做空、零表示平仓，未提交的标的维持原状。执行器根据目标与实际持仓计算订单差额。策略可以把权重、对冲比或风险预算换算成目标数量；以后提供权重等便捷接口时，复用相同执行能力。

协整策略可以由此表达 `A:k、B:-kβ`，因子策略也可以表达多个标的各自不同的目标仓位。平台不自动全仓缩放，也不限制只能存在一个逻辑组合。

## 3. 回测：统一时钟、共享账户、明确执行规则

**行情时序。** 使用 `execution_timeframe` 声明的单一执行时钟；每个决策时刻先推进全部必要的可见行情与指标，再回调一次策略。不同标的、不同周期都只能读取当时已收盘数据，联合历史按时间对齐。预热、覆盖检查、文件导出和资源限额按全部数据流计算；起止时间必须对齐执行周期，不对齐时明确拒绝，不自动移动日期。缺数据先补齐，仍不足则失败，不静默丢标的或缩短区间。

**资金与仓位。** 在现有 Broker 内维护共享现金、账户权益、逐标的持仓及保证金占用。策略决定投入多少、是否留现金、如何分配各标的；执行器负责精度、费用、方向与可用资金校验，不能给每个标的各复制一份初始资金。v3 不再强制沿用单标的全仓规则，相关产品及接口说明同步更新；旧 v1/v2 和历史 Replay 保持原口径。

**执行批次。** 普通 Intent 仍在下一主周期 Open 按各标的价格模拟执行。支持两种显式策略：独立执行时，允许某标的拒单而其它订单继续；要求联动时，批次内所有订单先共同校验，再统一提交状态或整批拒绝。每个批次先处理减仓释放资金，再检查增仓；独立执行的增仓顺序固定并冻结，拒单原因返回策略，不默默等权、缩量或更换目标。多个批次涉及同一标的的冲突明确拒绝，待执行状态按标的或批次管理，不再用全局单订单锁阻塞其它标的。

“整批成功或拒绝”是可选的 Bar 级模拟规则，不代表真实交易所原子成交；配对策略可以选择它，普通组合调仓不必被迫使用。

**风险事件。** 成交、拒单和强平回调携带标的及批次身份。单标的风险事件按冻结的市场风控规则处理，其它持仓是否联动退出由策略或显式风险规则决定，不默认全组合清仓。保留现有强平近似并逐标的核算，不引入组合保证金抵扣；回测结束清算全部剩余持仓。

本次沿用现有行情来源及市场能力，先保证同一结算币下的共享账户可正确核算；市场和方向逐标的校验，不把 API 固定成两腿或仅支持合约。

## 4. Replay：冻结完整输入，保留通用结果

- **输入与冻结：** 从单个 `symbol` 扩展为标的集合，可附可选别名；保存各 Instrument 的规则快照、数据依赖、成本与执行策略。Manifest、条件 Hash、重试、基准覆盖和执行证据均包含全部标的，不用第一个标的代表整个 Replay。
- **数据库：** 通过 Alembic 增加标的集合及快照 JSON 字段，旧单标的字段允许 v3 为空，历史记录不回填。Trade/Fill 增加标的身份与订单批次关联；策略可附逻辑组合标签用于归因，不强制所有持仓归属于唯一篮子。
- **结果与统计：** 策略收益、权益和回撤来自共享账户；Trade 继续表示各标的从开仓到平仓的完整交易，成交笔数单独统计。策略明确提供逻辑分组时附加标签盈亏归因，标签汇总不自动解释为组合交易胜率，不强行把所有交易统计改成“整篮子开平仓”。校验各标的净盈亏、成本与账户变化一致。
- **查询与播放：** K 线可按标的查询，交易和持仓返回标的身份；账户曲线按时间记录，各标的持仓与策略记录的因子值、信号和目标仓位使用同一时间轴。因子与诊断数值扩展现有记录能力，不新建因子管理模块。
- **Runner 包：** 同步完整标的绑定、规则快照与 Runtime 版本。当前 Runner 仍为包装占位实现，本次只同步包契约。

### 4.1 回测详情的后端接入约定

前端适配以四项职责分开取数；本轮只调整后端及契约，不修改前端实现。

| 详情区域 | 后端数据来源 | 展示口径 |
| --- | --- | --- |
| 标的行情及成交 | `GET /replays/{id}/candles?instrument=a`；从全量交易中按 `instrument_role=a` 选择成交，或调用带同一筛选的交易接口 | 标的切换只切行情和图内成交；周期以该标的 `available_timeframes` 为准。 |
| 顶部最终指标 | `GET /replays/{id}` 的 `result` | 固定展示本次完整回测结果，切换标的、拖动播放进度均不更换为单腿或历史时点指标。 |
| 底部完整交易时间轴 | 不传 `instrument` 的 `/trades`，遍历 `page/size/total_pages` 收齐后，将每条 `fills` 拍平，按全局 `Fill.sequence` 排序 | 始终包含全部标的成交，保留同一时刻的多条成交；不能只从当前图表的 Candle ID 集合推导。 |
| 交易列表及点击定位 | 全量 `/trades`；每条含标的身份、首尾 Candle ID 和时间、完整 `fills` | 先按 `instrument_role` 切到对应标的，再加载该腿 K 线并用 `entry_candle_id/exit_candle_id` 框选区间。 |

交易列表与底部时间轴默认都展示全部标的，不要求先选择某个标的查看交易；上方 K 线标的切换不联动筛选这两个区域。点击一条交易时只切换上方图表并框选区间，列表与时间轴继续保持全部。后端 `/trades` 省略 `instrument` 返回全部，传入别名则筛选该标的；这是可独立组合的查询能力，不规定前端必须采用哪种筛选控件或联动方式。

顶部收益、净利润与回撤来自共享账户，不对各标的收益率或回撤求和/平均。交易数、胜率和盈利因子以所有标的完整 Trade 为统计单位，与下方列表一致。成交 Fill 数是另一项计数。

一条 Trade 是**一个标的净持仓从 0 建立、期间加减仓、最终归零的完整周期**；反手先结束旧周期再建立新周期。例：ETH 多头与 BTC 空头一起开平仓，列表返回 2 条 Trade，而非 4 条买卖 Fill。不能仅凭同时成交、固定 `group_id` 或相同 `batch_id` 自动推断为 1 笔组合交易：各腿可以分批、异步或反复调仓，`batch_id` 表示订单执行批次，`group_id` 表示策略提供的归因标签，都不是通用的组合生命周期 ID。本轮保留这一灵活性。

v3 的 Trade 与 Fill 直接返回 `instrument_role/instrument_id/symbol/market_type/contract_type`，身份取自本次 Replay 冻结配置；`symbol` 用于展示，`instrument_role` 用于请求和定位，不能通过交易对名称猜别名或合并不同市场的同名交易对。旧 v1/v2 返回兼容。

完整交易时间轴无需新增 HTTP Timeline 接口。现有内部 `replay_get(view=timeline)` 的 `fills` 为有界片段，可能有 `fills_truncated=true`，不能用它代替全量分页交易。详情的 `counts.execution_steps` 是统一时钟步数；`counts.candles` 是各标的必要数据流总和，不能拿它当作当前图表或播放轴的根数。

## 5. Main Agent 与 Code Agent

Main Agent 将用户策略整理为完整 Design：使用哪些标的或标的集合、哪些数据、如何形成信号和目标仓位、何时调仓及如何控制风险；不强制套用“价差、对冲比、一起平仓”的配对模板。

继续通过 `strategy_update` 生成代码，Code Agent 使用 v3 Reference 实现联合计算与通用调仓；静态校验和 Smoke 扩展到多标的数据与订单。信号、因子和仓位规则改变才更新 Strategy revision，兼容契约内的执行绑定变化仍只创建 Replay。

`strategy_get.runtime_contract` 返回策略公开参数定义、参数说明及数据依赖；Main Agent 按说明提供标的、执行周期及各级别周期，信号周期由策略声明的级别引用确定，不重复传参，也不根据命名自行推导周期关系。原有 `replay_run` 和 HTTP 创建接口增加标的集合及可选别名，并同步 `base_replay_id/overrides`。多标的只产生一次联合运行，Main Agent 根据共享账户结果及各标的明细解释表现，不拆成互不影响的单标的回测；Tool Registry 无需增加工具。

## 6. 实施与验收

先打通 v3 数据接口、共享账户和目标仓位执行，再接入 Replay 冻结/结果及 Main/Code Agent，同步接口、数据库和运行时文档。

至少用两类手写策略验证通用性：多腿配对，以及固定候选集合内因子排序后动态选择持仓并调仓。覆盖保留现金、加减仓、不同执行批次、部分拒单、共享保证金、缺数据、无前视和风险事件；回归旧 v1/v2。最后使用真实 LLM 和真实多标的行情跑通对话 → 代码 → Replay，分别报告合成测试与真实调用结果。
