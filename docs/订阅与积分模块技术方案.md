# 订阅与积分模块技术方案

> 更新日期：2026-10-30。已接入权益、动态套餐、报价、Stripe 支付及积分流水。升级确认采用独立居中弹窗；已接入报价内支付方式资料、直接扣款／Stripe 页面两种升级模式及同单续开。加购金额变更自动报价，按钮直接付款；同页付款成功后整页返回原地址，不恢复弹窗或页签。消耗记录采用简洁列表，不提供费用详情入口。前端已发布生产，生产验收限公开只读检查，Live 付款未验证。

## 1. 权益与展示

认证由 auth/session 管理，账务状态独立保存在 `useBillingStore`。会话恢复或登录后并行读取 `/billing/account`、`/credits/balance`，读取订单恢复未完成操作。退出或身份切换时中止请求并清空私有状态，迟到响应按 generation 丢弃。

侧栏和账户设置展示真实订阅名，确认无订阅才显示 Free，未加载显示 `—`；账户设置展示 `available_credits`，不将月度额度、预占或订单积分当余额。Run 结束、付款回站、页面重新激活时刷新权益。

`GET /billing/plans` 是公开套餐唯一来源，套餐金额、积分、rank、版本和加购费率基点均按响应；加购输入采用第 2 节的 $5 起充且无上限规则。Free 仅表示无付费订阅，不是可购买套餐。`/pricing`、`/zh-CN/pricing` 保留公开套餐 SSR，与工作台全屏弹窗共享 `PricingContent`。

套餐内积分与加购单价统一按每 1,000 积分展示美元价格，固定保留两位小数；加购报价展示使用冻结报价的月费、额度及加价基点。此换算仅用于展示，实际购买金额和到账积分以服务端报价为准。

套餐界面只保留标题、套餐／加购内容和实际错误反馈，升级确认在独立居中弹窗展示；不展示订阅信息卡、余额、刷新、常驻订单状态／金额／查单控件。无有效加购资格时直接展示套餐，不渲染任何 Tab 或加购空状态；确认有效付费订阅且可加购时才显示套餐／积分加购 Tab。公开套餐正文始终保留 SSR，私有权益不参与 SSR。认证／权益首次未确定时，固定页签轨道使用与真实页签同尺寸的圆角骨架，购买按钮使用等高骨架且不可操作；确认资格后在原位展示真实页签与按钮，无订阅仍无 Tab，但轨道占位保持。首次恢复或权益失败在该区域重试，已有账户的后台刷新保留内容，避免重复骨架化。

工作台全屏弹窗以整个 `SubscriptionModal` 为唯一纵向滚动容器，关闭区与套餐正文处于普通文档流；向下滚动时关闭按钮一起滚出视口。正文不设置独立滚动区域，桌面与手机均沿用此规则。

点击套餐后仅当前按钮显示居中旋转图标，其余套餐禁用；不增加顶部处理中提示，按钮和卡片位置、尺寸保持不变。升级确认与加购付款沿用按钮内等待反馈；加购自动报价仅在积分数字区域显示小 Spinner，金额和页签仍可操作。确定失败后恢复操作；开始 Stripe 跳转后保持禁用，浏览器返回时解除本地等待状态。按钮保留原无障碍名称并标记 `aria-busy`。

订阅按钮不可用时统一保留淡化赭金底及品牌前景色，覆盖等待、当前套餐、低档套餐不可选等状态，不使用中性灰底／灰字；原生 `disabled` 与购买资格判断保持一致。

## 2. 购买、报价与待付款恢复

- 无订阅：提交 `plan_code` 创建首次订阅。访客先登录并返回价格页，不自动付款。
- 有订阅：当前档和低档禁用，符合资格时请求更高档报价，随后打开 `UpgradeConfirmationModal`。当前套餐及月度积分使用报价的 `current_plan` 已付快照，目标套餐、积分及本次应付金额使用同一报价；业务仍按目标完整月费收费、不抵扣旧费用，付款后生效并重开周期，旧月度余分失效，注册／加购余额保留。弹窗将生效与预计日期合成第一条提示，积分变更规则合成第二条，桌面每条单行。不展示报价有效期或优惠码；“预计下次扣款”只使用 `billing_period_preview.ends_at`，按浏览器本地时区显示日期，不使用旧订阅周期或自行加天数。报价过期仅阻止首次提交，弹窗提供明确的“重新获取报价”，新报价返回后仍需再次点击付款。
- 加购以 `topup_eligible` 为准，前端金额规则固定为 $5 起充、最多两位小数，无业务金额上限或输入字符长度上限。旧 `topup_max_usd` 字段可缺失／为 null，不参与展示、校验或快捷金额筛选；旧目录 min 也不覆盖产品的 $5 起充规则。真正打开加购页签或修改有效金额后，400ms 防抖自动请求 `/billing/topup-quotes`，显示服务端 `credits`；非法金额不请求。不显示“查看报价”步骤或报价教程说明。按钮始终为“支付 $xx.xx”，当前金额、已付套餐版本及未过期报价匹配后才可点击，点击只提交 `quote_id` 创建付款，不自动付款。展示费率使用已付订阅快照，报价后使用冻结报价。后端原金额上限与请求位数限制由后端同步调整，前端放开不代表后端已接受超额报价。
- 编辑金额、隐藏页签或关闭弹窗立即取消报价请求并清空旧报价；迟到响应／错误按请求序号、用户与 generation 丢弃。隐藏的加购组件不清除升级报价。报价期间可继续改金额，付款期间锁定操作。报价错误在积分区提供简洁重试；到期／`QUOTE_STALE` 自动重新报价，之后仍需用户点击支付。未知付款结果继续保留原金融操作。
- Stripe 手动返回不取消订单。未订阅用户可明确重新选择套餐，以新操作 Key 请求后台核实并关闭／替换旧未付流程；结果未知的 POST 仍先恢复原 Key。
- 在途升级不能另开新报价；仅对应目标套餐按钮显示“继续付款”，恢复原订单，其他档位禁用。`stripe_page` 即使旧链接为空或已过期，仍用独立 Key 调用同单 `/billing/orders/{id}/payment-page`，只打开该响应的新链接；不重新报价或下单。加购继续遵守在途限制。
- 取消／恢复续费和 Portal API 方法保留，套餐界面不提供订阅管理区域。

升级弹窗是纯展示组件，由 `PlanSelection` 编排打开、取消、付款及原操作恢复。组件接收冻结报价、等待状态、错误与可恢复状态；银行卡直接取报价的 `payment_method`，以 `Visa*4242` 的单星号格式显示，保持 `last4` 字符串前导零，null 时显示“暂无可显示的默认银行卡”，不猜测其他卡片。右侧卡号下的“其它支付方式”提交同一报价和 `payment_mode=stripe_page`，取得链接后同页跳转，不先扣默认卡；“立即支付 / Pay now”提交 `payment_mode=saved_method`。两个按钮分别绑定明确的付款处理函数：立即支付固定 `saved_method`，其它支付方式固定 `stripe_page`，不使用默认模式。两种提交互斥，未决操作恢复原模式。底部提供“取消”和付款，右上角保留关闭入口；视觉与层级见[浅色版设计决策 §5.8](Trade%20Lab%20浅色版设计决策.md#58-订阅套餐与积分加购)。

升级付款调用 `payQuote(quote, paymentMode)` 且必须显式传合法模式；积分加购仍只传报价。重试是独立入口，未知请求恢复调用 `retryOperation()` 并复用原接口、参数和幂等 Key；升级报价恢复成功后也会打开确认弹窗，不自动提交付款。弹窗独立保留已提交报价快照，不能因 store 在提交时清空报价而关闭；等待期间禁用付款、取消、关闭和其它支付方式，当前提交按钮显示 Spinner，开始跳转后保持锁定直到离页。只有本次返回的对应升级订单明确 `paid + fulfilled` 才关闭确认弹窗；之后账户或余额刷新失败不将已成功付款表现为失败。付款失败或待核实状态保留弹窗，错误和原操作恢复入口放在同一弹窗内，不在被遮挡的套餐页重复展示。弹窗存续时保留底层页签结构，避免在途权益刷新卸载正在使用的确认组件。关闭只结束展示，不丢弃未知金融操作；身份切换及卸载后不处理旧用户响应。

## 3. 同页 Stripe 与返回原页面

付款返回可支付订单、`action_type=redirect` 且有效的 HTTPS `payment_action.url` 时，使用 `window.location.assign` 在当前标签页前往 Stripe。原卡扣款未完成但 Invoice 仍 open 的后端状态为 `requires_action`，有可用链接即跳转；真正 `failed`、已关闭、已过期等终态不跳转。`paid`（包括等待履约）和非 pending 的履约状态均优先于旧 URL，不再次付款；明确 `paid + fulfilled` 后关闭确认并刷新权益。普通套餐／工作台不运行订单定时轮询，不保留另一个等待付款的原标签页。

跳转前在当前标签页的 sessionStorage 仅按用户保存 `owner/orderId/path`：原地址经过安全白名单校验，保留 query/hash。不保存套餐弹窗、页签、账户设置等页面交互状态；旧记录中的相关字段读取时丢弃。研究草稿继续由独立的原有草稿模块保存，不属于支付回站状态。

成功地址 `/billing/payment-return?order_id=...` 是内部 CSR 回站处理路由，noindex、no-store，不展示订单结果页或手动查询控件。恢复认证后校验本人订单，仅在该短暂处理期间查询账务状态（最多约 15 次、间隔 1 秒），刷新权益，然后以 `window.location.replace` 整页加载原地址。只有 `paid + fulfilled` 代表权益已交付；退款／争议、历史 superseded 及取消返回参数都不能冒充新到账。

返回后创建新页面实例，订阅／账户设置弹窗默认关闭，价格页使用默认套餐页签；刷新同样不会重新打开弹窗。全局弹窗只保留正常路由／身份切换时关闭的规则，不参与付款恢复。无合法原地址记录时整页返回当前语言价格页；存储不可用不阻止付款。回站认证失败时先登录，保留 order_id。

Stripe 手动“返回”由服务端 Checkout 的 cancel_url 决定，当前本地后端配置：

```dotenv
BILLING_SUCCESS_URL=http://localhost:6002/billing/payment-return?order_id={order_id}
BILLING_CANCEL_URL=http://localhost:6002/pricing?payment_cancelled=true&order_id={order_id}
BILLING_PORTAL_RETURN_URL=http://localhost:6002/pricing
```

价格页在应用就绪后清理取消标记和 order_id，不展示订单页，不将返回当作后台取消。旧 Checkout 的 `cancelled=true` 回站地址也兼容为直接返回价格页。后端改配置需重启，且只影响新建的 Stripe Checkout；旧 Session 的地址已在供应商侧冻结。生产需将来源替换正式 HTTPS 域名。

升级若需用户认证，后端可能返回托管 Invoice URL；该动作仍在同页打开，但不采用 Checkout 的成功／取消配置。已保存测试卡直接扣款的升级不跳转；托管 Invoice 自动回站不是当前已验证能力。

## 4. 幂等与用户隔离

复用 HTTP `requestJson`，不使用通用 operation 的 24 小时失效限制。付款、升级预览和订阅变更等持久操作在 POST 前按用户保存原接口、原参数及 UUID Key；拿到订单后保存订单 ID。只保存非密钥恢复字段，不保存 Token、卡资料或研究正文。

自动加购报价只创建可失效报价，不扣款、预占或发放积分。每次请求仍带独立 UUID 幂等 Key，但属于当前可见金额的临时请求，不进入持久金融操作，也不设置全局 `busy`。新金额或重试生成新报价；取消后的服务器报价允许自然到期，响应不能写回当前 UI。退出和身份切换中止报价并清空私有状态，付款仍使用原有持久幂等机制。

网络中断、超时、503、40960／待核实结果保留原操作，恢复使用原接口、参数和 Key；已明确拿到订单的操作按 ID 查询。确定业务拒绝清除操作，新报价／明确重新购买使用新 Key。初始化和焦点恢复仅按需读取，不启动常驻查单。身份切换只读取对应用户记录，认证与账务不合并，不增加代理或 BFF。

升级请求在新建与重发的统一出口均检查付款模式，缺失或非法时禁止提交，不默认原卡、不自动补参数。含糊的未决请求保留原接口、参数、Key 与购买锁定，用于核对原订单；隐藏不能执行的付款重试入口，不自动丢弃记录或换 Key 再下单。已明确模式的网络重试仍原样恢复，不要求用户再次选择模式。

同单撤销 API `cancelUpgradeOrder()` 已封装并复用独立幂等操作恢复；本次未新增撤销订单入口。确认弹窗的取消／关闭、浏览器后退和 Stripe 回站均不自动调用它。若后端撤销返回已支付订单，按实际状态处理；40960 不清除未决操作或订单。

## 5. 代码入口与对话衔接

账户设置的“消耗记录”在打开页签时按需读取 `GET /credits/ledger?page=1&size=20`，沿用服务端实际积分增减记录的排序、分页及总数，不在前端再次筛选或聚合。接口在分页前统一过滤 `credits_delta = 0` 的内部预占／释放等过程记录；造成实际扣减的过期预占回收仍返回。每行左侧显示活动名称，下方以 `YYYY.MM.DD HH:mm:ss` 展示紧凑 UTC 时间，右侧只显示 `credits_delta` 的实际正负增减；正值使用主题金黄色，负值保持主文字色。

活动名称直接按服务端 `action` 使用[接口定义文档 §16.6](接口定义文档.md#166-get-apicreditsledger)的中英文映射：注册奖励、积分加购、Basic／Pro／Max 订阅、积分补偿分别展示；保留通用 `grant` 发放及原消费／回收／撤销／恢复名称，未知值显示“其他变动”。历史订阅名称由该条 action 决定，不读取当前套餐、余额批次或 metadata 推断来源，不新增请求；首订、续费与升级入账不再自行细分。

不展示表头、说明段、每行余额、预占变化附注、详情入口或费用明细，也不发起费用详情请求。失败重试针对原请求页，未知活动保留双语回退，空态和必要分页保持简洁。

列表上方仅以一行文字展示当前套餐与剩余积分，复用 `useBillingStore` 的账户和 `available_credits`，不为摘要新增请求，未加载时显示 `—`。每条流水底部使用 `--color-border-default` 细分割线，不增加统计卡片或行背景。

`useCreditHistory` 的数据与请求生命周期属于当前页签实例，不进入全局缓存或浏览器存储。退出、身份切换、关闭弹窗／页签时清空并中止请求，另以请求序号与用户检查丢弃迟到成功和错误。接口目前没有研究名称或按研究聚合能力，来源信息不完整的历史入账仍返回 `grant`；UI 不承诺“按每次研究”的清单。完整字段边界见[接口定义文档 §16.6–16.7](接口定义文档.md#166-get-apicreditsledger)。
