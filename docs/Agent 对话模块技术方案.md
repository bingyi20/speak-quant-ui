# Agent 对话模块技术方案

> 日期：2026-09-15
> 状态：主流程已实现；实际接入范围与验证证据见 [Agent 对话接口联调记录](./Agent%20对话接口联调记录.md)。
> 目标：打通新建对话、纯文本发送、Agent 流式回复、底部输入区域快捷问答、消息卡片、卡片打开侧边面板，以及历史消息恢复。

## 1. 方案结论与范围

本期围绕一个完整聊天流程实现：用户发送文字，AI 逐步回复，需要澄清时在底部输入区域展示题目，生成资产时展示可点击卡片，重新打开历史时恢复消息。回复期间可以继续输入，但不能发送；本期不做暂停。

代码放在现有 `conversation` 模块中，复用已经具备的登录、请求、流式连接、Markdown 渲染和页面布局。开发重点是把这些能力接起来，并补上消息更新、输入状态和历史恢复，不新增一套聊天框架。

主流程：

```text
新研究 → 发送第一条消息 → 创建并进入对话
                              ↓
                   AI 逐步回复文字、更新卡片
                              ↓
                如需澄清，在底部输入区域作答并提交
                              ↓
                    本轮结束后继续发送消息

点击资产卡片 → 打开策略详情或 Replay 结果概览
打开历史对话 → 恢复已有消息；仍在回复时继续展示
```

### 1.1 本期交付

| 能力       | 本期实现边界                                                                           |
| ---------- | -------------------------------------------------------------------------------------- |
| 新建对话   | 点击“新研究”只打开输入页；首次有效发送才创建 Conversation                              |
| 页面嵌入   | 落地页、新研究页和后续 SEO 页面复用同一个输入组件，内置登录衔接、创建对话和跳转        |
| 登录衔接   | 访客发送后登录，恢复原始草稿及该次发送意图；普通登录不自动发送                         |
| 用户输入   | 普通输入支持纯文本、多行、IME 防误提交与草稿恢复；Clarification 支持快捷选择及文字作答 |
| Agent 回复 | Markdown 流式展示，支持只有文字、只有卡片、文字与多卡片组合                            |
| 工具调用   | 展示服务端提供的临时工具状态；不展示工具参数、原始结果或内部推理                       |
| 消息卡片   | Strategy、Replay 及未知类型的安全降级展示；Clarification 独立投影为输入区问答          |
| 侧边面板   | Strategy / Replay 卡片打开真实详情；桌面分栏、H5 全屏；版本与回测范围见[策略详情模块技术方案](策略详情模块技术方案.md)    |
| 历史恢复   | HTTP 消息分页、向上加载、刷新恢复、活动 Run 恢复、终态后校准                           |
| 稳定性     | 回复结束前禁止发送、重复点击防护、网络中断恢复、认证过期、切换对话及账户时隔离迟到响应 |

普通输入框继续只支持纯文本；Clarification 在底部输入区域逐题展示，展开时位于普通输入框上方；用户快速选择或填写答案后统一提交，普通输入及草稿始终保留。它属于本期交互，不按聊天卡片展示，也不打开资产面板。后端仍用 `clarification_card` 和 `card.upsert` 传递数据，协议名称不决定前端外观。

### 1.2 暂不实现

- 附件、图片、语音、富文本编辑、输入框引用和 Replay 定位追问的 `context`。
- Strategy 恢复操作，以及 Replay 图表、回放与交易明细；Design、代码、历史节点与结果概览已由策略/Replay 模块接入。
- 前端回测表单、Replay 创建/重试/取消按钮、Runner 下载和订阅计费。
- 消息编辑、重新生成回复、分支对话、并行发送或消息队列。
- 暂停/停止 Agent 回复：本期没有可用能力，不提供对应操作；后续后端支持暂停后，回复中的发送按钮再改为暂停按钮。
- 下一步建议提取、Markdown 内嵌业务组件语法、公式、Mermaid 图表和代码执行。
- 完整 Replay 生成后自动打开/播放。当前结果概览由用户点击打开；完整 Replay 播放阶段再接回自动打开/播放行为。

Agent 可以在后端自主编排本次请求需要的 Strategy / Replay 操作，前端通过同一个消息 Run 展示结果卡。这不代表前端已实现这些资产的完整业务。

## 3. 接口与数据契约

### 3.1 本期 API

下表路径相对 `/api`。JSON 接口均通过 `$http.requestJson()` 或 `$http.operation()`，读取已解包的 `data`。

| 接口                                | 输入 / 输出重点                                                                                                                    | 调用时机                                                   |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `POST /conversations`               | `{ content }` → HTTP 201 `{ id, title }`；幂等键必填                                                                               | 首次有效发送；已创建首条用户消息与 Run，不能再补发首条消息 |
| `GET /conversations/{id}`           | `{ conversation: ConversationSummary }`                                                                                            | 首次进入、终态后刷新元数据、错误恢复                       |
| `GET /conversations/{id}/messages`  | `before_sequence?`、`limit`；返回 `items/has_more/next_before_sequence/active_run`                                                 | 最新消息初始化、向上分页、终态校准                         |
| `POST /conversations/{id}/messages` | 普通消息传 `{ content }`；快捷回答按第 5.5 节携带回答上下文 → HTTP 202 `{ user_message, updated_messages, agent_run }`；幂等键必填 | 继续对话或提交 Clarification 答案                          |
| `GET /conversations/{id}/assets`    | 当前 `strategy` 与分页 `replays`；`page/size` 只作用于 Replay                                                                      | 初始化、终态后刷新、面板加载更多                           |
| `GET /agent-runs/{id}/events`       | 使用响应提供的 `stream_url`，标准 fetch SSE                                                                                        | 有活动 Run 时订阅                                          |
| `GET /agent-runs/{id}`              | Run ID、所属 Conversation、状态、error、时间、`stream_url`                                                                         | 断流、恢复校验                                             |

`stream_url` 可以自带 `/api` 前缀，直接交给现有 URL resolver，不能重复拼成 `/api/api/...`。继续使用其 API 来源和路径校验，禁止将 Access Token 放入 URL。

资产详情请求由策略/Replay 模块管理（见[策略详情模块技术方案](策略详情模块技术方案.md)）。对话模块不订阅 Conversation 级流，不连接消息 Run 内部的嵌套 Replay Run，不引入 `Last-Event-ID` / `seq` 续传，也不假设存在消息按 ID 查询或 Run 重试接口。

### 3.2 三种数据模型分开

| 模型                 | 内容                                                                                       | 约束                                                                      |
| -------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| HTTP Message DTO     | `id/conversation_id/agent_run_id/sequence/role/status/content/cards/created_at/updated_at` | 最终消息、服务端 sequence；实际可空性和省略字段按真实 schema 补齐         |
| Snapshot Message DTO | `id/role/status/content/cards`                                                             | 示例没有 sequence、时间、conversation_id；不能直接强转成完整 HTTP Message |
| 本地待发送项         | 本地 intent ID、固定正文、提交状态、错误                                                   | 先按正常用户气泡展示；内部等待响应对齐服务端 ID/sequence，失败才显示提示  |

SSE Envelope 为 `{ run_id, conversation_id, occurred_at, payload }`，事件名来自 SSE `event` 字段。`occurred_at` 用于展示或诊断，不作为排序或去重版本号。

已定义的 Run 状态为 `queued/running/completed/failed/cancelled/waiting_user`；其中后四种是当前 Run 的终态。`waiting_user` 表示本轮输出已经结束，用户文字回答会创建新 Run，不是恢复旧连接。

Card 保留服务端字段名：`id/type/status/resource_id/title/summary/data`。`clarification_card` 同样参与状态归并，但由输入区消费，不进入资产卡片 renderer。类型注册表是开放的；先校验公共字段，再验证已知类型的 `data`，不把所有卡片强制收窄成封闭枚举。卡片标题、摘要与工具标签按纯文本处理，不能作为 HTML 插入。

### 3.3 服务端关键保证

实现依赖接口文档第 5、6、11 节的以下保证，真实联调必须覆盖：

1. 创建 Conversation 时同一事务创建首条用户消息和 Run。
2. Messages 在同一数据库会话中先读取 `active_run`，再读历史；最终 Message 和 Run 终态在同一事务提交，避免“无活动 Run 也无最终消息”的空档。
3. SSE 首先发送 Snapshot，再发送边界之后的事件；生成中的 Assistant 内容不在 HTTP 历史中。
4. 服务端先持久化最终消息 / 卡片，再发布 `run.finished`。
5. Run 在 HTTP 与 SSE 建连之间结束时，SSE 仍能返回终态 Snapshot 和终态事件。
6. offset 使用 Unicode Code Point；文本、工具和卡片共享稳定 `message_id`。

前端可以处理重试与竞态，但不能用本地假完成弥补这些保证缺失。

## 4. 模块结构与状态归属

### 4.1 建议目录

以下为落地后的主要结构。简单展示留在所属组件内，未额外建立转发层。

```text
app/features/conversation/
  api.ts                         # 现有 API + 消息、Run、资产概要、SSE 订阅入口
  types.ts                       # HTTP DTO、Run、Card 公共结构
  agent-events.ts                # SSE payload 类型和运行时校验
  message-state.ts               # Snapshot/Delta/Card/Tool 归并与消息投影
  history-state.ts                # 复用并补齐元数据刷新/并发能力
  history-store.ts
  submission.ts                  # 稳定发送意图与幂等恢复
  clarification.ts               # 当前题目投影与批量答案校验
  composables/
    useResearchEntry.ts          # 所有入口共用的新建、登录衔接、路由跳转
    useResearchDraft.ts          # 用户 + 新研究/会话作用域草稿
    useConversation.ts           # 单会话初始化、发送、校准、清理
    useAgentRun.ts               # Run 订阅、状态检查、重连
    useStreamingText.ts          # 按吐字速度消费展示队列、字素分帧追加与任务清理
    useClarification.ts          # 当前题目投影、答案草稿、校验与一次提交
    useConversationScroll.ts     # 底部跟随、上拉锚点、回到最新
  components/
    ResearchEntry.vue            # 可直接嵌入任意站内页面的发起对话入口
    MessageComposer.vue          # 纯文本输入组件：v-model + 状态 + 事件
    ClarificationQuestions.vue   # 底部输入区域的快捷问答区
    ConversationWorkspace.vue    # 对话组合、面板视图与选中引用
    MessageList.vue              # 消息排列、稳定 key，按角色选择对应组件
    UserMessage.vue              # 用户气泡、纯文本，仅失败时提示与重试
    AssistantMessage.vue         # AI 回复布局、Markdown、工具状态、资产卡片
    cards/
      MessageCard.vue            # renderer 分派与未知类型降级
    ConversationAssetListPanel.vue    # 真实概要列表、分页与独立列表过渡
    ConversationAssetDetailPanel.vue  # 选中资产详情壳、全屏与独立详情过渡
  index.ts                       # 对外组件、类型与必要能力
```

`useAgentRun` 调用模块 API 的订阅入口，API 再复用 `openEventStream`。Run endpoint、JSON 解析和业务状态不能散落到组件。`app/lib/sse` 不导入任何业务模块。

用户消息与 Assistant 回复分别实现，使用各自的布局、样式和展示逻辑。`MessageList` 只负责排列消息并按角色选择 `UserMessage` 或 `AssistantMessage`，不再增加只做转发的 `MessageItem` 层，也不强行共用一个气泡模板。

### 4.2 唯一数据归属

| 数据                                          | 唯一归属                                                                                       |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| ConversationSummary、收藏/历史分页、顶部标题  | 现有 history store；对话 controller 不另存一份摘要                                             |
| 当前会话的 HTTP 消息、分页游标                | `useConversation` 页面作用域                                                                   |
| 当前 Run 的消息覆盖层、工具状态、Run 状态     | 同一对话 controller 持有的运行状态；由纯 reducer 更新，包含 Clarification 协议数据             |
| 合成后的消息列表                              | 从持久消息、Run 覆盖层和待发送项计算得到，不再单独保存                                         |
| 当前资产概要列表                              | 当前对话 controller；卡片是消息当时的摘要，资产列表是当前资源视图                              |
| 输入草稿                                      | 用户 + `new` / conversation ID 的 sessionStorage；问答选择额外按 message/card/question ID 隔离 |
| 待发送意图                                    | 当前标签页内的共享提交 composable，必要字段可在 sessionStorage 恢复                            |
| 面板、滚动和选中引用                          | `ConversationWorkspace` / `useConversationScroll`                                              |
| SSE reader、AbortController、计时器、操作句柄 | composable 闭包，不放 Pinia、Nuxt payload 或浏览器持久缓存                                     |

消息不叠加 `useAsyncData` 缓存或全局 Pinia 镜像。当前会话卸载后释放消息和连接，重新进入通过 HTTP + Snapshot 恢复；本期不常驻所有会话流，也不承诺切换会话后恢复精确的旧阅读锚点。面板开关则必须保留当前聊天的滚动和输入。

### 4.3 与现有 history store 的整合

移除 `workspace.vue` 中独立触发详情加载的 watch，由对话 controller 在初始化和终态时调用 store 的显式 `refreshDetail(id)`。顶部继续读取 store 中的记录，避免 layout 与页面重复请求或标题各存一份。

该入口必须真正刷新，即使侧栏中已有此记录也不跳过，并暴露 loading / error / 成功结果给页面处理 404、403 和临时故障。补充统一的摘要写回能力供详情、PATCH 和列表使用，保留现有 rename/favorite/delete 交互。

异步摘要刷新与用户重命名/收藏存在竞态：复用请求取消及代次保护，拒绝已被后续写操作淘汰的读结果，避免旧标题覆盖 PATCH 成功后的标题。列表仍按服务端分页重校验，不能仅把新记录塞到第一行而不修正后续偏移页。

### 4.4 落地页与 SEO 页快速嵌入

将现有 `ResearchEntry` 做成可直接使用的“发起对话输入框”，从 `conversation/index.ts` 公开导出。本项目内的落地页、新研究页、文章页或其他 SEO 页面，嵌入这个组件即可使用完整流程，不在页面里重复写登录判断、创建请求或路由跳转。

**已实现的嵌入方式：**

```vue
<script setup lang="ts">
import { ResearchEntry } from '~/features/conversation'
</script>

<template>
  <ResearchEntry :show-examples="false" />
</template>
```

页面可以设置输入提示文案、是否显示示例以及紧凑样式；不要求提供用户 ID、登录回调或发送接口。新增 `showExamples` 控制示例显示，保留现有展示属性，显示示例与紧凑样式分别控制。

用户点击发送后的行为由组件统一完成：

| 用户状态           | 行为                                                                              |
| ------------------ | --------------------------------------------------------------------------------- |
| 已登录             | 创建对话，携带这条首条消息，直接跳转 Agent 会话页                                 |
| 未登录             | 保留输入并进入登录；成功后自动继续本次发送，再跳转 Agent 会话页，无需再次点击发送 |
| 正在恢复登录状态   | 输入可编辑，等待恢复结果后再允许发送，避免误判为访客                              |
| 创建失败或登录取消 | 保留输入，按第 5 节的恢复方式处理                                                 |

仅输入、点击示例或打开页面不触发登录与创建。所有嵌入入口都使用 `useResearchEntry` 的同一套行为；登录后借助 `/new-task` 消费待发送意图，无需返回来源 SEO 页面重新挂载输入框。

`MessageComposer` 仍是内部的纯输入控件，用于组合新研究入口与会话内继续聊天；外部 SEO 页面使用已经封装好完整行为的 `ResearchEntry`。同一页面嵌入多个入口时共享新研究草稿和发送状态，输入元素使用各自唯一 ID，避免重复提交和标签关联错误。

输入高度按实际显示行数自适应，包含自动折行：会话内最小 2 行，新研究入口最小 3 行，最多显示 16 行，超出后内部滚动。文字增删、粘贴、草稿恢复和分屏宽度变化都会重新计算高度，发送清空后恢复初始高度；输入浮层与消息底部留白同步更新。

SEO 页面继续使用 `public` 布局和 SSR；嵌入输入框不会把整页改成客户端渲染。服务端输出公共内容和空输入框，浏览器端再恢复登录与草稿；不把私人草稿写入 HTML，也不为了展示入口而加载历史消息、资产或连接 SSE。会话数据只在跳转后的 Agent 会话页加载。

## 5. 创建、发送与草稿

### 5.1 首次发送

1. 输入组件只产生 `submit`。controller 校验 `content.trim()` 非空、认证恢复是否结束、是否已有未决提交。
2. 已核对后端 schema：正文去除首尾空白后须为 1–20000 个 Unicode 字符，前端按相同规则提交，保留正文内换行。空格不能创建空会话。
3. 生成一次提交意图，固定请求正文与幂等 key，并在发请求前同步锁定本轮发送。输入框仍可编辑草稿，草稿变化不能改变已经冻结的请求体。
4. 已登录时执行 `api.create(content, key).execute(signal)`；成功只读取 `id/title`，保存已知 Conversation ID，并跳转 `/conversations/{id}`。
5. 创建成功后只清除仍对应本次提交的草稿版本；如果用户已继续编辑，将新草稿保留并衔接到新会话输入区。将意图转为“已创建，待打开”，保留已创建 ID；路由跳转成功后再清除意图。若跳转失败或此时刷新，提供“打开对话”，不能再次创建或重新发送首条消息。
6. 详情页统一初始化，不依赖创建响应携带消息、资产或 Run。侧栏刷新失败不回滚创建结果，可单独重试列表。

### 5.2 登录后的发送意图

访客点击发送时保存草稿和 `create` 意图，进入 `/login?returnTo=/new-task`。正文、幂等 key 和用户信息不进入 URL。

登录成功后，在现有匿名草稿迁移位置，将本次待登录意图一次性绑定到新登录用户。新研究 controller 在认证与客户端存储恢复完成后消费该意图；普通访问 `/new-task`、点击示例、普通登录均不触发提交。

取消登录或离开该流程时保留可编辑草稿，撤销自动继续标记；失败也不循环自动提交。账户切换不会把 A 用户的未决操作自动绑定到 B。认证失效后的继续对话意图只能由原用户恢复。

### 5.3 继续发送

同会话采用确定的串行对话规则：本轮消息提交后，直到服务端回复全部结束，才允许发送下一条。整个等待和回复期间输入框都可输入、修改和换行，发送按钮禁用；不会缓存一个待自动发送的队列。

发送前要求：最新历史初始化成功、没有 `queued/running` Run、没有状态未知的恢复过程、没有待校准终态或未决提交。普通发送和 Clarification 提交共用同一个发送条件；按钮点击、Enter、表单 submit 都必须经过 controller 的同一检查，发请求前同步锁定，防止连续操作重复触发。回复完成后只恢复可发送状态，不自动发送用户已输入的草稿。

点击发送后，立即在消息列表尾部展示正常样式的用户气泡，并清空本次输入，让用户继续编辑下一条草稿。气泡不展示“发送中”、进度图标或“发送成功”标记；只有请求失败时，才在原气泡旁显示轻量失败提示和重试入口。

内部先使用本地 intent ID 标识这条消息。HTTP 202 返回后，将服务端 `user_message.id` 和 sequence 对齐到原气泡，不新增一条、不闪烁、不再次清空输入，按消息 ID 应用响应中的 `updated_messages`（普通消息为空数组），随后连接 `agent_run.stream_url`。立即显示消息是前端的展示方式，内部仍以真实响应确认是否已保存。

网络超时也使用同样的轻量失败提示，不增加“结果待确认”的独立界面状态。内部保留原文和同一次提交的标识，因为消息可能已经到达服务端；点击重试仍复用原操作，避免重复发送。失败气泡保留原文，不自动覆盖用户已经开始编辑的下一条草稿。

### 5.4 幂等与刷新中断

仅为未决创建/发送记录最小恢复信息：`kind/owner/conversationId?/key/content?/createdAt/phase/acceptedConversationId?`。它是草稿提交记录，不保存 Token、Agent 历史或 SSE 数据。每个标签页、每个用户至多保留一个未决消息提交，解决后及时清理。Clarification 提交还需冻结完整请求体中的 `reply_to_message_id/structured_answers` 及问题引用，重试时完整恢复原批量答案和来源。

- `http.operation()` 负责生成和复用请求键；组件不接触 Header。
- 同一次意图重试，正文、接口、key 不变。服务端明确拒绝后修改正文是新意图，生成新 key。
- 结果不明时先解决旧意图，不提供会默默放弃旧 key 的“重新发送”。
- 刷新后若记录仍在有效期内，用保存的 key 和正文重建操作；创建意图从新研究入口恢复，已知会话的发送意图先加载历史状态再执行同键确认。刷新不会凭空获得“未发送”的结论。
- 保存并检查最初 `createdAt`；不能因重建句柄重新计算 24 小时有效期。超过时限不自动重试，先查看历史确认状态，并提示可能已提交。现有接口不能按幂等 key 查询结果，这是一项明确的恢复边界。
- sessionStorage 被禁用时仍可在当前页面完成发送和内存重试，但整页刷新后的未决提交不能保证自动恢复；不宣称跨标签页或跨设备去重。

创建失败保留输入，继续发送失败保留原用户气泡及文本并显示失败提示；正常展示气泡不额外宣告保存成功。复制回复可作为轻量交互实现，重新生成回复不在本期范围内。

### 5.5 Clarification 回答提交

按照更新后的接口定义，单题和多题统一使用 `structured_answers` 数组，单题就是一个元素。选中选项保存本地答案并进入下一题，最后一题选中后仍需点击“提交回答”，一次请求保存全部答案、生成一条用户消息并启动一轮 AI 回复。

请求示例：

```json
{
  "reply_to_message_id": "01K_ASSISTANT_MESSAGE",
  "structured_answers": [
    { "question_id": "01K_QUESTION_MARKET", "value": "合约" },
    { "question_id": "01K_QUESTION_TIMEFRAME", "custom_text": "15m" }
  ]
}
```

每题使用服务端给出的 `question_id`，选择答案填 `value`，自定义答案填 `custom_text`，二者只填一个非空字符串，最多 2000 字符。选项必须来自原题，自定义回答须由该题允许；仅提交已填写的有效答案，不重复题目 ID；全部跳过时传空数组。此为 2026-09-09 新前端目标，现有后端仍要求非空数组及全部必答题，待同步修改（见接口定义文档待变更说明）。

本期问答提交不传 `content`，由服务端按原题顺序生成可读的用户消息。普通输入框中的草稿单独保留，不自动当作补充文字提交。旧的单对象 `structured_answer` 仅由后端兼容，新前端不使用；也不把整组答案拼成普通文本作为接口降级方案。

提交时可先按问题和答案生成一条正常样式的本地用户气泡，不显示发送中；成功后用服务端 `user_message` 替换为最终正文。随后按 ID 应用 `updated_messages`：原 Assistant 消息保留题目，已答状态及 `data.answers` 同步更新，问答区收起，再连接返回的新 Run。无需等新 Run 完成才显示已答状态。

同一来源 Assistant 消息的多张澄清协议卡片也可一起提交，前端统一收集有效已填项；部分填写及全部跳过尚待后端支持。整组由服务端一次保存，任何一题不合法则整组不保存；失败保留已选答案，沿用轻量失败提示和重试。请求结果未知时，使用同一幂等 key 和同一组答案重试，避免多条用户消息或重复启动 AI。

接口已明确：漏答或非法选项等返回 400，请求格式错误返回 422，已回答的题目用新 key 再次提交返回 409；前端显示可读错误，409 时刷新原题状态。同 key 重试返回首次结果。普通文字发送仍走普通消息路径，不由前端擅自转成结构化答案。

## 6. 进入会话与历史恢复

### 6.1 统一初始化

在认证可用且 API 开启后，为 `{ userId, conversationId, pageGeneration }` 创建作用域，启动以下独立任务：

- history store 强制刷新 Conversation 详情。
- `messages({ limit: 50 })` 获取最新一页。
- `assets({ page: 1, size: 20 })` 获取轻量资产列表。

使用独立结果处理，资产失败不阻塞历史或 SSE，详情/历史的失败有各自状态；若详情明确返回无权访问或资源不存在，则结束整个会话作用域。Messages 成功即可渲染；`active_run=null` 时不建流，存在时只连接它指定的一个 Run。

会话首次加载完成后定位最新消息。历史为空且有 active Run 时展示正在恢复的占位，不能误导为可重新提交首条消息；历史为空且没有 Run 则展示服务端实际空状态。

### 6.2 向上分页

- 只使用服务端 `next_before_sequence`，不自行计算页码或猜测 ID 顺序。
- `items` 已按 sequence 正序；按 Message ID 去重后归并，持久消息按 sequence 排序。
- 记录顶部可见消息 ID 及相对位置，前插历史后恢复锚点，不把用户拉到底部。
- “加载更早消息”请求一次只执行一个；失败保留现有列表和原游标，可原位重试。
- 老页响应中的 `active_run` 不覆盖当前实时订阅；它不是一个新的订阅指令。订阅切换只由初始化、发送响应或显式最新状态刷新触发。
- 终态校准或新一轮初始化可取消老的分页请求；无法取消的迟到结果通过代次和写入规则丢弃，不能覆盖已更新的卡片或消息状态。

### 6.3 历史与实时合成

消息列表由一个纯投影函数生成：

```text
HTTP 持久消息（按 ID 保存，sequence 排序）
  + 当前 Run 覆盖层（按 message_id 覆盖对应行）
  + 本地已展示的用户消息（外观与正常用户气泡一致）
  → 唯一的可见消息列表
```

Snapshot 消息若在历史中存在，复用其 sequence 与位置，正文、卡片和状态用该 Run 的最新覆盖层；否则先按 Snapshot 数组顺序、后续事件首次出现顺序放在历史尾部。不从 ULID、时间或本地序号伪造服务端 sequence，终态 HTTP 校准后采用真实顺序。

Snapshot 可以更新更早消息上的卡片，因此覆盖层归属由“本次订阅 Run + 涉及的 message IDs”决定，不能只筛选历史消息原始 `agent_run_id`。重新连接时原子替换整个本 Run 覆盖层和活动工具，删除新快照中已经不存在的临时内容，同时完整保留其他历史。

## 7. SSE 归并与恢复

### 7.1 每个事件的处理

事件进入 reducer 前先验证 JSON、Envelope、payload 必需字段、当前 Conversation / Run 归属和连接代次。旧连接的回调直接丢弃；同一条流必须在合法 Snapshot 后才处理增量。

| 事件            | reducer 行为                                                          | 副作用由 controller 执行                     |
| --------------- | --------------------------------------------------------------------- | -------------------------------------------- |
| `run.snapshot`  | 原子替换本 Run 消息、卡片、工具和状态；计算各文本初始 code point 长度 | 结束恢复占位；终态 Snapshot 进入终态校准     |
| `message.delta` | 定位/创建 Assistant 容器，验证 offset 后追加正文                      | 合并刷新 Markdown 和滚动                     |
| `tool.status`   | 按 `(message_id, id)` 更新临时状态；可以先创建空消息容器              | 结束项短暂展示后移除，定时器带 Run 代次      |
| `card.upsert`   | 定位/创建消息；按 `card.id` 整体替换或追加，保留首次位置              | 面板通过引用读取最新卡片，不每个事件请求详情 |
| `run.finished`  | 校验终态；清工具；统一收尾仍为 streaming 的消息                       | 关闭订阅并刷新最终 HTTP 数据                 |

`completed/waiting_user` 将仍为 `streaming` 的消息收为 `completed`；`failed/cancelled` 收为相应状态，不删除已输出正文或已产生资产。只有临时工具且最终没有正文/卡片的空容器在权威同步后移除。

未知事件忽略并记录不含正文的协议诊断；未知卡片按公共字段降级，不中断流。已知核心事件的关键结构错误、非法 offset 或缺失首 Snapshot 触发受限恢复，不猜测状态；重复收到相同协议错误后停止自动循环并提供手动恢复。

### 7.2 Unicode offset 算法

每条实时消息维护 `content` 和 `codePointLength`。Snapshot 时扫描一次全文，Delta 只统计本次片段；不在每个 token 到达时反复统计全文。

```text
length = 当前 codePointLength
start = start_offset
end = end_offset

先验证 start/end 为非负整数，end >= start，
且 Array.from(delta).length == end - start。

end <= length                  → 完全重复，忽略
start == length                → 追加 delta，length = end
start > length                 → 缺口，停止本连接并恢复 Snapshot
start < length < end           → 部分重叠，恢复 Snapshot，不自行裁剪
```

Emoji、组合字符和换行均按 code point 计数，不使用字符串 `.length` 或按视觉字形数计数。缺口恢复通过重连原 Run 的 SSE 获得 Snapshot，不虚构独立 Snapshot endpoint。

### 7.3 分开表达连接状态与业务状态

| 层       | 建议状态                                             | 用途                         |
| -------- | ---------------------------------------------------- | ---------------------------- |
| 页面加载 | `loading/ready/error/not-found`                      | 初始化与读取错误             |
| 提交     | `idle/submitting/uncertain/rejected`                 | 用户消息是否被接受           |
| 连接     | `idle/connecting/streaming/recovering/offline/error` | 前端是否正在接收实时输出     |
| Run      | 服务端六种状态，外加本地尚未确定                     | 后端任务是否仍在执行         |
| 最终同步 | `idle/syncing/error`                                 | 终态数据是否已通过 HTTP 校准 |

这些是内部控制状态，用于禁止重复提交和恢复请求；不会逐一变成用户气泡上的状态标签。用户消息正常显示，仅失败时提示。

不使用一个 `loading` 布尔值同时控制这些行为。例如断网时 Run 可能仍在执行；结束生成后也可能尚未完成 HTTP 同步。

### 7.4 断线重连

现有 `openEventStream` 会直接重试 URL。本模块设置 `maxRetries: 0`，使用单一的业务恢复循环，避免内外两层重试叠加：

1. 正常终态、主动卸载、切换账户产生的 abort 不重连。普通 EOF、45 秒无字节/心跳或网络故障进入恢复状态，保留已见内容。
2. 调用断开前那个 `run_id` 的 `GET /agent-runs/{id}`；查询失败不推断 Run 结束。
3. `completed/failed/cancelled/waiting_user`：用 HTTP 历史和资产校准，不再连接旧流。
4. `queued/running`：重新打开该 Run 的 `stream_url`，等待 Snapshot 完整替换旧临时层。
5. Token 过期由共享 HTTP session 单次刷新协调处理，再执行原请求；不重新 POST 用户消息。刷新失效后由现有认证机制进入登录。
6. 使用有上限的指数退避，建议最多自动重试 4 次（1、2、4、8 秒并加少量抖动），之后提供“恢复连接”。收到有效 Snapshot 后确认数据恢复，但不立即重置失败预算；连接稳定一段时间（建议 30 秒）后才重置，避免“Snapshot 后立即 EOF”的反复建连。重复协议错误单独累计并停止自动重试。
7. 浏览器离线时暂停自动请求，联网后恢复同一流程；这些监听及延时均随作用域清理。`online` 只表示可以尝试请求，不表示恢复成功。

HTTP/TCP 保序与 Snapshot 已承担事件边界，前端不按 `occurred_at` 重新排序事件。传输层终止判断只接受校验通过、归属匹配的 `run.finished`，不能仅比较 event 字符串。

终态 Snapshot 已明确 Run 结束时，可以直接进入 HTTP 校准并主动结束订阅，不必因随后 `run.finished` 丢失一直等待。这里依据的是明确终态数据，普通 EOF 仍不代表完成。

### 7.5 终态校准

收到合法终态后先保留当前正文和卡片，标记为对应状态，清掉工具及首字 Loading；并行刷新最新消息、Conversation 元数据和资产概要。取消、失败、等待用户都执行这一流程。

HTTP 返回同一消息 ID 时替换临时内容并取得真实 sequence。最新一页不足以覆盖本 Run 涉及的全部消息时，沿 `before_sequence` 补读。Clarification 提交已经通过 `updated_messages` 更新原题，不为更新已答状态重新读取全部已加载历史。分页校准保留视口锚点，不清空再重画整个列表。

校准覆盖本次 Snapshot/事件涉及的持久内容 ID，保留已经加载的其他历史消息。若游标到底仍找不到应持久化的非空消息，作为契约异常报告；不能无限分页或悄悄删除已输出内容。纯工具临时容器不属于必须持久化的集合。

消息校准成功后释放 Run 覆盖层；失败保留带“同步失败，可重试”状态的最终内容，不显示为已恢复完整历史。在校准完成前暂不开始下一 Run，避免单 Run 覆盖层被新发送替换。仅资产/侧栏刷新失败不阻塞后续聊天，保持局部错误和重试。

页面重新获得焦点且当前没有健康订阅时，执行一次节流的最新状态校验；如果服务端仍有活动 Run，继续恢复该 Run，并保持发送禁用。此处只处理服务端状态恢复，不引入多标签页并发发送或排队场景。

### 7.6 发送按钮状态与后续暂停能力

| 当前状态                                 | 输入框                 | 本期发送按钮 / 提交行为                               |
| ---------------------------------------- | ---------------------- | ----------------------------------------------------- |
| 空闲且草稿非空                           | 可输入                 | 可发送                                                |
| 请求提交中、等待首字、Agent 回复中       | 可输入                 | 禁用发送，不提供暂停或停止操作                        |
| 断线恢复、Run 状态待确认、终态消息校准中 | 可输入                 | 保持发送禁用，不能把网络断开视为回复完成              |
| 本轮回复全部结束且消息同步完成           | 可输入，保留下一条草稿 | 草稿非空时恢复发送；`waiting_user` 后也可提交澄清答案 |
| 本轮明确失败并完成状态同步               | 可输入，保留草稿       | 允许用户发起下一条消息                                |

“回复全部结束”依据合法 `run.finished` 或恢复时获得的权威终态，不依据文字暂时停止增长、某张卡片完成、工具状态结束或网络 EOF。发送锁覆盖整个 Run，所有提交入口共享，输入框是否可编辑与发送是否可用分别控制。

本期没有可用的暂停消息能力，前端不实现暂停/停止请求，也不接入接口文档列出的 `/agent-runs/{id}/cancel`。`cancelled` 仅作为协议可能返回的终态兼容展示，不代表存在用户可点击的取消功能。关闭页面或切换会话时的 abort 只结束前端订阅。

后续后端支持暂停后，AI 回复期间的发送按钮再切换为可点击的暂停按钮；具体请求、暂停后的状态和是否支持继续需按届时契约实现，不能提前把暂停等同于 cancel。

## 8. 消息与卡片 UI

### 8.1 文本渲染

两类消息的组件职责：

| 组件                   | 负责的界面与逻辑                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------- |
| `UserMessage.vue`      | 用户气泡、纯文本换行；仅失败时显示轻量提示，并向上发出重试事件                        |
| `AssistantMessage.vue` | AI 回复的独立布局，组合 Markdown 正文、首字等待、临时工具状态、资产卡片及回复异常状态 |

`AssistantMessage` 内继续复用 `MarkdownContent` 和卡片组件，直接渲染轻量工具状态列表。Clarification 的当前作答区仍放在底部输入区域，不塞入回复组件。各组件只接收所需展示数据并向上发出交互事件；请求、消息更新与去重、Run 生命周期仍由对话 controller 统一管理，不在两种消息组件中各做一套。

用户消息用 Vue 文本插值，保留换行、折行长文本，绝不按 Markdown 解析。Assistant 复用现有第三方 `marked` 解析 Markdown，再通过 `sanitize-html` 清洗 HTML，最终由 `MarkdownContent.vue` 展示；不自行实现 Markdown 解析器。

```text
SSE 文本片段 → 立即归并原始 Markdown → 展示队列按字素小步追加
             → marked.parse() → sanitize-html → MarkdownContent.vue
```

第三方库负责语法解析与 HTML 清洗；项目代码只负责消息状态、流式刷新调度、Vue 封装和样式。现有依赖已经满足本期文本需求，暂不另加整套聊天 UI 框架。历史与实时复用同一条渲染链路；如果后续需要公式、代码高亮或更完善的未闭合语法体验，再评估对应插件或流式渲染组件，不在本期手写这些语法。

首期支持现有 renderer 的段落、标题、强调、列表、引用、代码块、链接和表格；不开放原始 HTML、图片、iframe、事件属性或不安全 URL。表格统一撑满正文宽度，使用独立容器承载横向滚动；代码块和宽表格局部滚动，不撑破聊天内容列。非法或不完整 Markdown 可以暂时按解析器结果展示，不能影响流的收取。

每次先把 Delta 立即归并到原始正文，展示侧通过 requestAnimationFrame 按字素边界小步追加（不拆开完整 Emoji）。默认每秒 60 个字素，积压较大时最多加速到 180 个，每帧最多 4 个；掉帧不会积攒一次性补字，新片段也不重置吐字时钟。不再把任意大小的片段压缩到固定 160ms 内显示完，避免大块回复仍呈现整段跳出的感觉。历史与 Snapshot 直接恢复，非追加的正文修正立即替换。正常终态继续消费已有展示队列，失败、取消、切后台或减少动态效果偏好立即补齐；卸载清理调度，不影响 Run 终态、发送权限和历史持久化。

Markdown 仍由 marked 解析并经过 sanitize-html 清洗。MarkdownContent 使用局部 DOM 更新替代整块 innerHTML 替换：相同节点保持原位，只追加新节点或更新变化的文本及属性，保留代码块和表格的横向滚动位置。DOM 更新工具不解析 Markdown 语法，只接受清洗后的 HTML；SSR 与客户端沿用同一份安全渲染结果。

本期没有正文与卡片交错的 block/offset 协议，因此消息内固定为“正文 → 临时工具状态区 → 有序资产/通用卡片区”。`clarification_card` 从可操作消息卡片区排除，单独投影到底部输入区域的问答区；原始协议数据仍保留在所属消息中。不能根据到达时间把卡片塞进某段 Markdown，也不从代码围栏或特殊字符串推断工具调用。

生成期间工具区保留 20px 单行最小高度，无工具时透明隐藏，有工具时用 200ms 透明度过渡显示，减少提示出现和消失时的高度跳变；多个真实工具仍按列表自然增高。此处参考 geo-cn-admin 的工具占位方式。该项目正文直接追加 SSE 文本，并没有前端逐字动画；实际网络片段大小和吐字速度尚未作两项目对比测量。

首字前在回答起点显示轻量 Loading；首个文字、卡片或工具状态出现后由实际内容承接，不叠加无意义 Spinner。历史完成回复不重演加载状态。已显示正文仍有后续处理时，用实际工具/卡片状态表达进度。

消息操作栏使用原始 content 复制，状态非 streaming 且展示队列追平正文后出现。MessageList 标记最后一条 assistant 消息，并共享午夜 / 页面重新可见时的日期刷新；历史消息通过 hover 或键盘焦点显示操作栏。时间优先使用历史接口 created_at；尚未入历史的新消息使用首个消息事件的 occurred_at，Snapshot 重连保留已有时间。缺少历史和先前事件时间的 Snapshot 暂不展示时间，待历史同步补齐，不以重连时间冒充创建时间。

### 8.2 卡片映射

聊天卡片仅作资产入口，不展示 `summary` 长摘要或指标，不提供下载按钮。标题单行省略，悬停保留完整标题；状态与点击能力仍按接口数据判断，原摘要数据保留供详情使用。

| 类型                              | 聊天中显示                                                | 交互与降级                                                                |
| --------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------- |
| `strategy_card`                   | 图标、单行标题、策略文档类型；异常或生成中显示简短状态       | 有 `resource_id` 时打开 Current Strategy 面板壳；生成中无 ID 时仅显示状态 |
| `replay_card`                     | 图标、单行标题、回测记录类型；异常或生成中显示简短状态 | 有 ID 即可打开对应 Replay 面板壳，运行/失败/取消状态也可查看概要          |
| `clarification_card`              | 消息区不渲染可操作卡片；当前题目展示于底部输入区域          | 快速选择/文字作答并统一提交，详见第 8.3 节；无资产面板                    |
| `actions` / `replay_confirmation` | 公共标题、类型及兼容说明                                  | 不开启预留操作，不根据 `data.actions` 动态执行请求                        |
| 未知 `type` / 已知类型非法 `data` | 公共字段有效时展示通用卡片                                | 无未定义操作；局部异常不影响其余回复                                      |

卡片更新必须完整替换，不能深合并旧 `data`；同 ID 甚至可能由兼容确认卡变成 Replay 卡。只按 `card.id` 维护位置，不按 `resource_id` 去重：多条消息可以各自引用同一个 Current Strategy。

Clarification 的 `completed/answered/answers` 以服务端为准。快捷回答成功后立即应用响应中的 `updated_messages`，无需等待下一轮 AI 回复结束；普通文字消息不由前端自行推断题目已回答。

### 8.3 底部逐题快捷问答

`ClarificationQuestions.vue` 在底部输入浮层中逐题展示，展开时放在始终可见的普通输入框上方，间隔 12px，保持与消息列同宽。卡片顶部显示题目、当前题号 / 总数、前后导航和关闭按钮；选项按带数字标记的整行纵向排列，底部右侧始终为可点击的 Skip 按钮。卡片最高 `min(48dvh, 440px)`，当前题目的选项可独立滚动，顶部与底部输入及操作保留；小屏导航与题目分行显示。展开时整个输入浮层限高为对话列可用高度减 24px，卡片优先收缩并内部滚动；普通输入框此时最多显示 4 行，超出内部滚动，收起问题后恢复 16 行上限。

关闭只是收起本地问答，聚焦普通输入框，不提交、不伪造跳过或已答状态；“继续回答”入口改为发送按钮左侧的问答图标加题数，使用 MessageComposer 的 before-send 插槽，由工作区提供；完整中英文提示通过 title / aria-label 提供，点击重新展开同一题并保留已填答案，收起的问答组件不再输出独立入口。关闭使用 Vue 离场钩子，由工作区测量卡片和恢复后的入口实际位置，通过 Web Animations 执行 240ms 卡片平移缩小淡出，入口自身不做动画；离场元素固定定位并设为 inert / aria-hidden，不参与浮层高度。快速重开和卸载取消动画，减少动态效果模式直接完成离场。普通输入组件保留挂载，草稿不因切换丢失。新来源消息到来自动展开新题目组。

1. 每组协议卡片包含 1～5 道题，每题有 2～5 个快捷选项，当前服务端仍返回必答标记，但前端统一允许跳过，不再展示必答 / 选答差异。每题使用单选；`allow_custom=true` 时提供文字回答入口，选项与自定义文本互斥，按接口校验最多 2000 字符。问题 ID 使用服务端提供的稳定值，历史数据也不由前端补造 ID。
2. 选择快捷选项或输入有效自定义回答后按 Enter，确认当前题并进入下一题；末题确认直接提交整组。Shift+Enter 换行，输入法组合期间的 Enter 不触发操作。自定义输入位于底部编辑图标后，提示“输入其他回答，按回车确认”，高度随内容增长，最高 120px 后内部滚动。右侧始终为跳过（中文“跳过”、英文“Skip”），无箭头、无禁用态，不随文字输入切换含义；Skip 清除当前题答案并前进，末题 Skip 直接提交此前已填的有效答案。不再提供单独的跳过按钮、补全必答题或提交按钮。前后导航和关闭保留草稿，重复点自定义不清空内容；无效或超长草稿不能通过 Enter 确认，也不进入最终提交数组。所有题均可跳过，空数组表示本组全部跳过。末题仍遵守 Run 和未决提交的发送锁，阻塞期间点击不发请求、不清除当前草稿，不自动排队；正常状态整组只产生一次消息请求。现有后端尚不支持部分 / 空数组提交，真实请求失败沿用现有错误与同 key 重试，不能视为业务成功。

3. 题目可以随流到达后提前展示/填写，提交需等本轮 Run 结束，以避免与后端仍在执行的 Run 冲突。`waiting_user` 是本期主要的可提交状态。
4. `useClarification` 从已归并消息中派生当前待回答组，不复制一份远程卡片状态。仅激活最新一轮来源 Assistant 消息中的有效 `waiting_user && answered=false` 题目；同一消息有多张澄清协议卡片时按卡片及题目顺序统一展示、一次提交，不跨消息打包。更早的待答标记不能因上拉历史重新激活；提交后用 `updated_messages` 更新原题状态。
5. 同一来源的 upsert 保留仍合法的选项和自定义答案；问题、选项或 `allow_custom` 改变后重新校验。新问题组替换旧组，不能将仅同名的 question ID 当作同一题继承答案。
6. 刷新和从历史进入时，由 HTTP / Snapshot 恢复当前题目，默认定位首个缺少有效答案的题目（必答缺失或已填答案失效）；已有有效答案且没有缺失时定位最后一题，全为选答且未填写时从首题开始；本地未提交选择按用户、会话、来源消息、card ID 和 question ID 恢复，并对最新选项重新校验。已回答题目不恢复成可提交表单。
7. 已答 Clarification 不在 Assistant 消息下额外渲染已答题数或折叠答案，答案只通过用户消息展示服务端生成的纯文本，结构化数据和已答状态仍保留；被后续普通文字越过的未答旧题继续提供只读问题回看；不重复挂载历史问答表单或资产卡。当前待答消息若只有 Clarification 数据，展示底部题目区即可，不额外生成空白气泡。
8. 支持 Tab / Enter 操作、焦点提示、题目标签和题号播报；焦点在问答卡片内且不在文本输入区时，数字键可选对应选项，自定义输入中的数字和输入法组合不触发选择。用户切题或点击“继续回答”后焦点移到题目，流式新题到来时不主动聚焦。问答区出现或收起时同步调整消息底部留白，浮层高度变化本身不触发消息滚动，用户可手动将最后一条消息滚出遮挡区。

用户选项、自定义输入与工具/卡片摘要一样按文本处理。澄清区只展示结构化事件中的题目，不能从 Markdown 中猜测问题并自动生成表单。

### 8.4 侧边面板

`ConversationWorkspace` 的局部状态保存选中引用 `{ kind, resourceId, messageId?, cardId? }`，不复制整张卡片到另一份长期状态。面板通过当前消息/资产概要解析标题和状态，卡片 upsert 后已打开面板也随之更新。

- 列表与详情是独立组件 `ConversationAssetListPanel` / `ConversationAssetDetailPanel`，各自持有面板 DOM、布局样式和 Vue Transition，不在同一面板内切换内容。工作台分别保存 `listOpen` / `detailOpen`，只负责互斥打开与选中资源；对应的可见状态保留至各自离场完成，快速反向切换不会被旧的关闭回调覆盖。
- 桌面列表在页头下方以固定窄栏展开，使用聊天画布底色，占用布局空间并同步压缩聊天；列表不提供调宽或全屏。详情使用表面色，保留比例分栏、拖动及键盘调宽，列表不会改变上次详情宽度。
- `SplitPane` 只处理布局宽度及调宽，不拥有业务面板的进出场动画。列表和详情分别使用 `asset-list-reveal` / `asset-detail-reveal` 与独立动效变量，可分别调整方向、时长和缓动。点击聊天卡片或列表卡片均打开同一个详情组件，触发同一段详情滑入；列表独立向右离场，聊天宽度从当前占位连续过渡。全屏将同一详情 DOM Teleport 到 body，覆盖侧栏及页头且去除圆角；退出移回原分栏并恢复阅读位置。全屏及小屏保留覆盖布局直到离场结束，消息及输入始终保持挂载。尺寸、边框拖动提示和动效参数以 [设计决策 §7–8](./Trade%20Lab%20浅色版设计决策.md#7-replay-面板与研究体验) 为准。
- H5：列表在页头下方覆盖聊天区域，保留右上角开关；详情沿用全屏覆盖层。两者保留后台 Conversation 实例，处理焦点、关闭返回和安全区；返回后保持输入与阅读位置。
- Strategy 卡始终指向当前 Strategy；早期摘要不表示历史节点。Replay 卡始终绑定它自己的 Replay ID。
- 面板 Header 展示资源标题；策略版本、Design、代码、回测列表及 Replay 结果概览由各功能模块读取真实接口，具体契约见[策略详情模块技术方案](策略详情模块技术方案.md)。
- 右上角纯图标按钮切换列表，`aria-expanded` 只反映列表是否展开；列表不设关闭按钮，收起使用同一入口或 Esc。点击聊天或列表内的卡片切换为详情，列表随即关闭，按钮恢复未展开态。关闭详情回到聊天，不自动返回列表；取消常驻返回资产列表按钮；仅从策略进入 Replay 时提供返回策略，并保留列表范围和位置。离场完成后清空选中引用，切换会话也重置。
- 列表将真实 Strategy / Replay 概要映射为 `MessageCard`，与聊天共用 `components/cards/MessageCard.vue`；标题、图标、类型、副行状态、hover 和点击样式只维护一份。列表按策略在前、回测在后平铺，不显示分组标题、数量或分组空态，不重复显示版本、摘要或指标。
- 资产入口保留在会话页头，初始无资产时展示空态；读取失败用局部重试状态，不能伪装成“没有资产”。列表分页只补读 `/assets` 的 Replay 部分。

## 9. 滚动、生命周期与错误体验

### 9.1 滚动规则

- 消息滚动区域延伸至页面底部，输入框与快捷问答作为底部浮层覆盖其上。观察输入浮层实际高度，消息底部 padding 同步增加该高度及 24px 留白；浮层上沿使用 32px 向上透明的画布色渐变，不拦截滚动条与滚轮。
- “回到最新”按钮位于输入浮层上方；快捷问答和错误提示改变浮层高度时，留白和按钮位置一起更新。
- 输入框增高、缩小或其他浮层高度变化只更新底部 padding，不触发消息滚动；即使暂时遮挡消息，也不为避让输入框而自动移动内容。滚动跟随只观察消息内容尺寸和滚动视口尺寸，不观察包含底部 padding 的外框尺寸。
- 首次进入默认最新；用户主动发送时定位到新消息。
- 用户位于底部附近时，在消息布局更新后同步定位底部，不再为滚动叠加追赶动画；程序定位不误判为用户滚动。用户上滚、触摸或键盘向上阅读时立即中止跟随。“回到最新”按钮的显隐独立于跟随状态：距底部超过 60px 才显示，回落到 10px 以内隐藏，中间区间保持当前状态以避免闪烁；停止跟随后消息增长也重新测量距离。首次定位和点击回到底部立即完成。
- 卡片尺寸、Markdown 表格或分栏宽度变化时，按是否跟随底部决定定位；否则保留首个可见消息锚点。
- 向上分页、终态归并、面板开关不能重置阅读位置。终态刷新分页只更新已加载 sequence 范围及新消息，不展示为覆盖范围而额外读取的较早消息；按最新用户消息 ID 判断发送定位，不能因较早消息数量变化跳底。布局转换只替换容器，不重建业务 controller。
- 首期采用分页与稳定组件 key；不预先引入虚拟列表。长会话性能实测后再判断是否需要虚拟化。

### 9.2 清理与异步响应隔离

每个请求和事件都校验 `userId + conversationId + pageGeneration`，流额外校验 `runId + connectionGeneration`。切换 ID、退出、换用户、当前对话永久删除成功或页面卸载时，先提高代次再 abort，清理工具淡出、退避、渲染、滚动及网络监听。

对话 controller 同步观察认证归属；不能只依赖 `$http.cancelAll()`。本地消息、临时工具和资产状态立即释放，迟到 Promise、旧 SSE、旧分页不能写回。草稿按用户隔离，退出时清除自动继续标记，不跨账户发送。

SSR 不读写浏览器存储，不输出私有消息或草稿；沿用 `/new-task`、`/conversations/**` 的 CSR、noindex 和 no-store。`NUXT_PUBLIC_API_ENABLED=false` 时保持明确离线预览，无假成功或生产 Mock。

### 9.3 错误与可恢复动作

| 场景                | 界面行为                                | 恢复动作                                            |
| ------------------- | --------------------------------------- | --------------------------------------------------- |
| 创建/发送网络超时   | 保留原气泡和原文，仅显示轻量失败提示    | 原 key、原正文重试                                  |
| 字段校验失败        | 输入附近显示本地化错误，保留草稿        | 修改后新意图提交；普通消息按接口校验最多 20000 字符 |
| 429 / 临时不可用    | 显示限流/服务不可用提示，无自动重复写入 | 按错误含义重试；存在未决结果时保留原 key            |
| 初始历史加载失败    | 错误与重试，不展示成空历史；暂停发送    | 重新读取最新 Messages                               |
| Run failed          | 保留部分文本/卡片，展示业务失败         | 同步历史；可继续新消息，不提供不存在的 Run 重跑     |
| SSE EOF / 断网      | 保留已输出内容，显示连接恢复状态        | 查询原 Run 后重连或校准                             |
| 401 且 Refresh 失败 | 清理私有运行状态，保留隔离草稿          | 登录返回原会话，再读历史及活动 Run                  |
| 403 / 404           | 结束订阅，显示无权访问或不可用          | 返回新研究/历史列表，不无限重连                     |
| 最终消息同步失败    | 保留终态内容并提示同步失败              | 仅重试读取，不重发用户消息                          |
| 资产/侧栏刷新失败   | 聊天继续，对应区域提示                  | 局部刷新，不回滚已完成对话                          |

固定 UI 文案同步维护 `zh-CN.json` 与 `en-US.json`。用户正文、Agent Markdown、卡片标题/摘要、工具 `label` 不由前端翻译。状态标签和错误用本地化映射，未知状态提供中性降级，不把内部 error 堆栈直接展示。

发送按钮有可访问名称，禁用状态可被辅助技术识别；流式正文不逐 token 使用 `aria-live` 朗读，状态区只播报阶段变化。保留键盘焦点、移动键盘可见性及 reduced-motion 支持。

## 10. 接口接入时的检查

当前产品规则已经明确，可以据此开始实现。字段是否可空、错误如何返回、没有资产时返回什么，都是开发时对照真实接口完成的常规检查，不需要产品逐条确认，也不据此增加功能范围。

多道澄清题一次提交的接口已补齐，按第 5.5 节直接接入。成功响应同时给出用户回答和原题更新后的消息，历史恢复使用服务端保存的题目、答案与已答状态；该项不再待确认，也不再采用纯文本聚合的临时方案。

断线后内容是否完整、重复数据是否显示两遍、历史问题状态是否更新，属于实现后的验证场景，按第 12 节检查。它们不作为开始主流程开发前必须逐项解决的独立需求。

## 11. 分阶段实现顺序（初始计划）

以下用于追溯实施顺序，不作为当前完成度清单；实际结果见 [联调记录](./Agent%20对话接口联调记录.md)。

| 阶段           | 工作内容                                                                       | 完成判据                                                                   |
| -------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| P0：接入准备   | 对照现有接口补齐请求和数据类型，接入整组答案提交及更新后的消息                 | 具备发送、读取历史与接收回复所需的接口函数                                 |
| P1：创建与历史 | 提供可嵌入页面的研究入口；接通创建、登录恢复、历史及继续发送；挂入稳定会话容器 | 真正只创建一次；刷新能读到用户消息；失败草稿可恢复                         |
| P2：实时主流程 | reducer、Snapshot/Delta、工具、Run 终态、Markdown 节流、滚动跟随               | 文字可持续流式展示，无重复/错序；一轮结束后能继续发送                      |
| P3：卡片与面板 | 资产 Card renderer、同卡更新、底部输入区域问答及提交、资产概要、桌面/H5 面板壳   | 题目作答后一次提交；实时和历史状态一致；资产点击指向正确资源；详情按专项方案接入 |
| P4：恢复与验证 | 状态查询后重连、发送禁用与恢复、校准分页、账户/路由隔离、错误及可访问性        | 断线/刷新/快速切换不丢最终结果、不重复发消息；完成真实联调                 |

发送串行规则、恢复与异步响应隔离从 P1/P2 的状态结构中落实并逐步验证，不能到 P4 才引入身份归属或更换数据模型。每阶段可分独立提交，但完成 P1/P2 不等于完整主流程已交付。

## 12. 验证与验收

### 12.1 单元与状态测试

围绕高风险数据规则测试，不为纯样式或简单组件拼装增加重复测试。

- Snapshot 替换仅影响对应 Run；与 HTTP 同 ID 不重复；较早消息更新保持位置。
- 文本、卡片、工具任意一种先到；只有卡片、只有工具以及一条消息多张卡片。
- Unicode code point、完全重复 Delta、部分重叠、缺口、非法 offset、坏 JSON 与未知事件。
- card upsert 整体替换且不改变位置；同 card ID 类型改变；未知卡片降级。
- 终态状态映射、工具清理、重复终态幂等处理、HTTP 校准失败时保留覆盖层。
- 网络 EOF、心跳超时、离线恢复、先查原 Run 再决定建连、401 刷新复用；主动 abort 不重连。
- 发送条件在请求前同步生效；等待首字、流式回复、工具执行、恢复期间均不可发送，但可编辑草稿；终态后不自动发送草稿，旧提交完成不清除新草稿。
- 未决写操作复用正文/key；刷新恢复保留原始有效期；普通登录不发送；访客意图只消费一次。
- 上拉与终态校准竞态、旧连接/旧用户/旧会话响应丢弃、旧标题不覆盖重命名。
- Clarification 单题也使用数组、多题及同消息多张协议卡片一次提交、部分填写和全部跳过、选项/自定义互斥、失败保留答案、同 key 重试，以及 `updated_messages` 立即更新题目与历史答案恢复。

### 12.2 浏览器测试（Mock 隔离）

在 `tests/e2e/` 新增对话请求/流夹具，仅用于测试。桌面和移动端覆盖：

1. 新研究空白不创建，IME 不误发，双击只产生一次创建；访客登录恢复与失败重试。继续发送时正常气泡立即出现，没有发送中或成功标记；请求失败才显示失败入口，成功对齐不会重复气泡或清掉下一条草稿。落地页与另一个 SEO 页面嵌入同一个 ResearchEntry，均验证已登录直接发送、未登录登录后自动发送并进入会话，页面无需另写业务处理。
2. 用户纯文本按原文显示；Assistant Markdown、代码块、表格、安全链接与恶意输入清洗。
3. 实际分块到达时可观察逐步更新，不能只断言最终一次性文本；工具及卡片先于文本也正常。
4. Strategy / Replay 打开正确面板；关闭、分栏、H5 返回不丢消息、草稿和位置。
5. 上拉历史不跳底；用户上滚暂停自动跟随；刷新完成历史不重演 Loading。
6. 历史中有 active Run 自动恢复；建连前已结束；生成中刷新；断流但后端完成。
7. 快速切换两条会话、退出/换用户、删除当前会话，不被迟到事件污染。
8. 发送结果未知、Run 失败、同步失败与局部资产错误均可恢复。
9. 回复期间可输入和换行，但点击发送、Enter 与 Clarification 提交均不产生新消息请求；没有暂停/停止按钮，也不发送 cancel 请求；本轮结束后可手动发送保留的草稿。
10. SEO 页保留服务端输出的正文，HTML 不含私人草稿；同页多个研究入口标签 ID 唯一且共享发送状态；仅浏览页面不创建会话或连接 SSE。
11. Clarification 在普通输入框上方逐题展示，普通输入始终可用；选择不会立即发送；单题/多题均只提交一次结构化答案，成功即更新原题并收起问答区，失败可重试，刷新可恢复题目及答案；普通聊天草稿保持独立。

Mock 可以证明前端分支和归并规则，不能证明 Agent 真实输出或后端持久化。

### 12.3 真实接口联调

使用专用测试账户，不修改已有用户研究，不记录 Token、验证码、完整敏感请求或 Agent 内部日志。证据记录接口、响应结构、观察结果与脱敏标识；测试数据完成后清理。

| 场景                         | 必须观察到的结果                                                                                    |
| ---------------------------- | --------------------------------------------------------------------------------------------------- |
| 首次纯文本提问               | 201 返回 ID 后正常进入；首条用户消息只有一条；从 active Run 收到回复                                |
| 普通追问 / 快捷回答澄清      | 题目区提交一次返回一个新 Run；历史问题/答案可回看；`waiting_user` 后可继续                          |
| Agent 生成 Strategy / Replay | 真实 card upsert 更新同卡；点击资源指向正确；不伪装详情实现                                         |
| 回复中编辑下一条             | 等待首字和整个回复阶段可编辑，所有发送入口不可用；回复结束后保留草稿并恢复手动发送，无暂停/停止操作 |
| 工具状态                     | running/结束正确变化；刷新仅恢复活动工具；最终历史没有临时工具日志                                  |
| 生成中刷新 / 断网重连        | 恢复同一 Run，不再次提交用户消息；最终 Markdown 和卡片完整                                          |
| 创建/发送响应丢失            | 同 key 重试没有重复 Conversation、用户消息或 Agent Run                                              |
| Run 在建连前结束             | 终态 Snapshot 或权威 HTTP 恢复正常，无永久 Loading                                                  |
| 执行失败                     | 以服务端最终状态收尾；刷新后状态与卡片一致                                                          |
| 历史超过一页                 | 最新及更早消息顺序正确；旧澄清卡更新可见                                                            |
| 账户与会话切换               | 当前界面仅显示当前用户/会话数据                                                                     |

需要核对是否经真实网络流式到达，而非后端缓冲到最后一次返回。无法触发的故障或未准备好的 Agent 链路明确标记“未验证”，不以 Mock 结果代替。
