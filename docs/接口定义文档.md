# SpeakQuant MVP 接口定义文档

> 文档版本：V1.2\
> 更新日期：2026-10-13\
> 协议：HTTPS + JSON；Agent 实时消息使用 SSE  
> API 前缀：`/api`

## 1. 文档范围

本文是 SpeakQuant MVP 前后端联调契约，覆盖：

- Google 登录、邮箱验证码登录、JWT 刷新和退出。
- 用户资料和产品语言。
- Conversation History、消息历史和资产列表。
- Agent 实时 SSE、断线重连和结构化卡片事件。
- Current Strategy、Strategy History 和恢复。
- 回测条件、确认、进度、取消、失败和重试。
- Replay 指标、K 线、交易时间线、洞察和报告。
- Runner 下载包构建和下载。
- 支付订单、周期订阅、升级/取消、积分加购、余额/流水/费用明细与积分不足反馈。

Agent Loop、策略代码生成、回测引擎和 Replay 生成算法属于后续独立技术方案。本文只规定它们对前端暴露的输入、状态和输出。

## 2. 通用协议

### 2.1 环境

| 环境 | Base URL |
| --- | --- |
| 本地 | `http://127.0.0.1:6001/api` |
| 测试 | 后续由部署环境提供 |
| 生产 | `https://speakquant.com/api`，必须 HTTPS |

所有业务接口和健康检查统一使用 `/api` 前缀，不使用 `/v1`；健康检查的完整路径为 `GET /api/health`。下文接口 Path 相对 Base URL，`/health` 对应完整路径 `/api/health`。

### 2.2 请求 Header

| Header | 必填 | 说明 |
| --- | --- | --- |
| `Authorization: Bearer <access_token>` | 受保护接口必填 | JWT Access Token |
| `Content-Type: application/json` | JSON 请求必填 | UTF-8 JSON |
| `Accept: application/json` | HTTP 接口建议 | 响应格式 |
| `Accept: text/event-stream` | SSE 必填 | SSE 响应格式 |
| `X-Request-ID` | 否 | 前端链路 ID；不传则服务端生成 |
| `Idempotency-Key` | 创建资源/触发任务时必填 | 建议 UUID；支付模块使用持久幂等键，规则见 16.1，其余接口沿用各自幂等窗口 |
| `Accept-Language` | 否 | 新建会话/发送消息时选择本次 Agent Run 的系统提示语言，规则见下；不控制模型回复语言 |

**Agent 系统提示语言：**`POST /conversations` 和 `POST /conversations/{id}/messages`（含澄清回答）优先使用发起请求的 `Accept-Language`。支持 `en-US`、`zh-CN`，`en` / `en-*` 归为 `en-US`，`zh` / `zh-*` 归为 `zh-CN`，匹配不区分大小写；按 `q` 从高到低选择支持的语言，省略 `q` 视为 1，同权重按 Header 原顺序，`q=0` 不选。Header 缺失或没有支持的语言时回退当前 `user.locale`，仍无法匹配时使用 `zh-CN`。例如 `Accept-Language: en-US,en;q=0.9,zh-CN;q=0.8` 选择英语，即使用户消息为中文。

该语言随本次后台 Run 使用，覆盖 Agent 成功/取消/空输出/失败等终态兜底，以及积分不足、风险限制、费用待核实、模型费率未配置等计费错误提示。无模型正文时，普通 Assistant 消息使用本地化兜底；失败原因与 SSE `payload.error.message`、GET Run `data.error.message` 使用同一语言和错误原因，`error.key` 不变。文案生成是确定性处理，不调用 LLM，也不额外扣积分。

系统提示在新消息及 Run 错误落库时固定为**发起请求时**的界面语言；后续 GET/SSE 的 Header 或界面切换不会重新翻译已保存内容。已有模型正文仍按用户消息和上下文生成，后端不翻译正文，不重写历史消息。本规则不代表 Replay、Tool/Card 展示及其他所有 HTTP 接口已完成国际化。

除登录、验证码、Refresh、公开配置、Health，以及第 16 节明确列出的公开/供应商签名接口外，其余接口统一使用：

```http
Authorization: Bearer eyJ...
```

### 2.3 成功响应

所有非 SSE 接口使用统一 Envelope：

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "request_id": "req_01K..."
}
```

- `code=0` 表示成功。
- HTTP Status 表达协议结果；`code` 表达稳定业务结果。
- 删除成功返回 HTTP `200` 和 `data.deleted=true`，不使用无响应体的 `204`。
- 除明确展示完整 Envelope 的示例外，后续接口示例均表示 Envelope 内的 `data` 字段。

### 2.4 错误响应

```json
{
  "code": 40902,
  "message": "Strategy 已发生变化，请重新确认",
  "data": null,
  "error": {
    "key": "BACKTEST_CONFIRMATION_STALE",
    "fields": {
      "expected_revision": 4,
      "actual_revision": 5
    }
  },
  "request_id": "req_01K..."
}
```

通用错误：

| HTTP | code | key | 场景 |
| --- | --- | --- | --- |
| 400 | `40000` | `BAD_REQUEST` | 请求格式或业务参数错误 |
| 400 | `40001` | `IDEMPOTENCY_KEY_REQUIRED` | 缺少幂等 Key |
| 401 | `40100` | `AUTH_REQUIRED` | 未提供 Token |
| 401 | `40101` | `AUTH_TOKEN_INVALID` | Access Token 非法 |
| 401 | `40102` | `AUTH_TOKEN_EXPIRED` | Access Token 过期 |
| 401 | `40103` | `AUTH_SESSION_REVOKED` | Session 已撤销 |
| 401 | `40104` | `REFRESH_TOKEN_INVALID` | Refresh Cookie 缺失或无效 |
| 403 | `40300` | `FORBIDDEN` | 无权访问资源 |
| 404 | `40400` | `RESOURCE_NOT_FOUND` | 资源不存在或不属于当前用户 |
| 409 | `40900` | `RESOURCE_STATE_CONFLICT` | 当前状态不允许操作 |
| 409 | `40901` | `REVISION_CONFLICT` | 乐观锁 revision 不一致 |
| 409 | `40902` | `BACKTEST_CONFIRMATION_STALE` | 回测确认卡已失效 |
| 422 | `42200` | `VALIDATION_ERROR` | 字段校验失败 |
| 429 | `42900` | `RATE_LIMITED` | 频率限制 |
| 500 | `50000` | `INTERNAL_ERROR` | 未知服务端异常 |
| 503 | `50300` | `SERVICE_UNAVAILABLE` | 外部服务或执行器暂不可用 |

字段错误放在 `error.fields`，不得把第三方 SDK、SQL 或堆栈信息返回前端。

### 2.5 时间、ID 与数值

- 本地业务 ID 均为 26 位 ULID 字符串，前端不得转为 Number；支付动作中的供应商 ID 是不透明字符串，见 16.1。
- 时间均为 ISO 8601 UTC，如 `2026-08-20T09:30:00.123456Z`；当前支付链接到期时间的序列化兼容规则见 16.1。
- 金额、价格、数量和比率在 JSON 中统一返回字符串，避免 JavaScript 浮点误差。
- 比率为小数，例如 `"0.12340000"` 表示 `12.34%`。
- 普通业务列表使用 `page/size`；消息历史和 K 线使用各自的顺序位置参数。

### 2.6 分页

Conversation、Strategy History、Replay、Trade 等普通列表统一使用：

```http
GET /api/conversations?page=1&size=20
```

响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "items": [],
    "page": 1,
    "size": 20,
    "total": 52,
    "total_pages": 3
  },
  "request_id": "req_01K..."
}
```

- `page` 从 1 开始，默认 1。
- `size` 默认 20，最大 100。
- 数据库使用 `OFFSET (page - 1) * size LIMIT size`。
- Conversation History 变化时，不保证跨多次请求形成严格静态快照；MVP 接受列表更新造成的轻微位置变化。
- 消息历史继续使用 `before_sequence/limit`，便于向上加载。
- Replay K 线继续使用 `cursor/limit`，便于顺序读取大体量数据文件。

### 2.7 幂等与并发

- 创建 Conversation、发送消息、创建/重试 Replay、恢复 Strategy，以及第 16 节用户发起的支付/报价/订阅变更 POST 必须带 `Idempotency-Key`。Runner Package 按服务端 Build Key 自然幂等，不依赖前端生成幂等 Key。
- 相同用户、接口和 Key 的重试返回第一次请求的结果，不重复执行。
- Strategy 修改使用 `expected_revision` 防止旧页面覆盖；Agent 创建 Replay 时在同一事务中锁定并冻结 Current Strategy。预留兼容接口仍会比较确认卡片中的 `strategy_revision`，不要求前端单独回传版本号。
- 前端收到 `40901/40902` 后应刷新对应详情，不自动重复覆盖。

### 2.8 语言边界

- Agent 不接收或保存单独的对话语言字段，默认根据用户当前消息和上下文选择合适的回复语言。
- 系统界面、固定错误文案等非 LLM 内容的国际化独立处理，本阶段不展开具体方案。

## 3. JWT 认证

### 3.1 Token 规则

- Access Token：JWT，有效期 1 小时，通过 `Authorization` Header 发送。
- Refresh Token：随机不可读的长期 Token，不设置业务过期时间，通过 HttpOnly Cookie 保存。
- Web 前端不读取 Refresh Token，不放入 localStorage。
- Refresh Token 使用 `<session_id>.<random_secret>` 结构；Session ID 只用于定位，随机部分必须具备至少 256 bit 熵。
- Refresh 时不轮换 Refresh Token，只签发新的 Access Token。
- 正常产品流程只有用户主动退出会撤销 Session；浏览器清除 Cookie、账号删除或管理员禁用属于例外。
- JWT 签名算法生产环境使用 `RS256` 或 `EdDSA`，禁止把对称密钥交给前端。

Access Token Claims：

```json
{
  "iss": "trade-lab-api",
  "aud": "trade-lab-web",
  "sub": "01K...user_id",
  "sid": "01K...session_id",
  "type": "access",
  "iat": 1787216400,
  "exp": 1787220000,
  "jti": "01K...token_id"
}
```

Refresh Cookie：

```text
Set-Cookie: trade_refresh=<token>; HttpOnly; Secure; SameSite=Lax; Path=/api/auth; Max-Age=315360000
```

`Max-Age=315360000` 约为 10 年，用于实现产品意义上的“永久登录”；浏览器规范不存在真正无限期 Cookie，并且浏览器或用户仍可能主动清理。开发环境可关闭 `Secure`，测试和生产必须开启。

### 3.2 AuthResponse

Google 登录、邮箱验证和 Refresh 成功统一返回：

```json
{
  "access_token": "eyJ...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "user": {
    "id": "01K...",
    "email": "user@example.com",
    "display_name": "User",
    "avatar_url": null,
    "locale": "zh-CN",
    "timezone": "UTC",
    "created_at": "2026-08-20T09:00:00Z"
  }
}
```

## 4. 公开与认证接口

### 4.1 接口清单

| PATCH | `/users/me` | 是 | 更新基础设置 |

### 4.2 `GET /meta/quick-examples`

Query：`locale=zh-CN|en-US`，默认读取 `Accept-Language`。

```json
{
  "items": [
    {
      "id": "trend_following",
      "title": "趋势跟随",
      "content": "当 BTC 的 20 日均线上穿 60 日均线时做多……"
    }
  ]
}
```

最多返回 4 条。该配置可以来自代码或配置中心，MVP 不要求数据库表。

### 4.3 Google 登录

#### 4.3.1 `GET /auth/google/config`

无需登录。返回 `ApiResponse<{client_id, nonce}>`，并设置 10 分钟有效的
`trade_google_nonce` HttpOnly Cookie（Path=/api/auth/google，SameSite=Lax，非 local 环境 Secure）。
响应 `Cache-Control: no-store`。前端 fetch 必须携带 `credentials: include`，将 nonce 传入
`google.accounts.id.initialize`。重复初始化会替换当前浏览器的 challenge。
未配置 `GOOGLE_CLIENT_ID` 返回 `50300 SERVICE_UNAVAILABLE`。

无请求 Body。实际请求地址为 `GET /api/auth/google/config`，成功响应示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "client_id": "<web-client-id>.apps.googleusercontent.com",
    "nonce": "<server-generated-random-string>"
  },
  "request_id": "<request-id>"
}
```

- `client_id` 是公开的 Web 客户端标识，可提供给前端；Client Secret 不参与本流程。
- `nonce` 用于将 Google 签发的 ID Token 与当前浏览器的登录请求关联，不能省略或自行生成替代。
- Cookie 由浏览器管理，前端无需也不能读取其 HttpOnly 内容。
- nonce Cookie 的服务端签名有效期为 10 分钟。Google credential 还受自身 `exp` 限制，两者分别校验。
- 不要在每次组件 render、按钮点击或普通 API 请求前重复调用此接口；新 Cookie 会覆盖旧 challenge。


#### 4.3.2 `POST /auth/google`

前端通过 Google Identity Services 获得 Credential 后提交，服务端必须验证签名、`aud`、`iss`、`exp`、`email_verified` 和 Cookie 对应的 `nonce`。
Google 时间声明允许最多 30 秒时钟偏差；签名、受众和 nonce 仍严格校验。
只接受 JSON 回调提交，Origin 必须位于 `CORS_ORIGINS`，请求必须携带 credentials。
本接口不是 GIS HTML 自动 POST/redirect 接收端，不采用 `g_csrf_token` 表单协议。

请求：

```json
{
  "credential": "google_id_token"
}
```

请求字段：

| 字段 | 类型 | 必填 | 约束 / 说明 |
| --- | --- | --- | --- |
| `credential` | string | 是 | GIS callback 返回的 Google ID Token，长度 1～16384；不是 Google Access Token 或 OAuth code。 |
| `verification_id` | string / null | 否 | 第三方邮箱补验证时与 code 一起提交，长度 26；来自 `/api/auth/email/code`。 |
| `code` | string / null | 否 | 第三方邮箱补验证时提交，必须为 6 位数字字符串。 |

不接收额外字段，包括客户端自报的 email、sub、name、picture 或条款版本。普通登录只传 credential。

响应：`ApiResponse<AuthResponse>`（见 3.2），并设置 `trade_refresh` HttpOnly Cookie；
成功响应 `Cache-Control: no-store`，同时清除 `trade_google_nonce` Cookie。
返回的 Access Token 是 SpeakQuant 自己签发的业务 Token，后续 API 使用它作为 Bearer Token。


业务规则：

- 已绑定的 Google `sub` 优先定位用户，Provider 邮箱变更不改变绑定，也不覆盖用户主邮箱。
- 首次绑定：Gmail 或 `email_verified=true` 且具有 `hd` 的 Workspace 邮箱可直接匹配并复用原用户。
- 其他第三方邮箱首次绑定（含新用户）返回 `40910 GOOGLE_EMAIL_VERIFICATION_REQUIRED`，data 为 `{email}`。
  前端调用 `/auth/email/code`，再向本接口提交原 credential 加 `verification_id`、`code`。
  服务端验证验证码所属邮箱一致、未过期且未消费，原子创建/绑定身份、消费验证码并签发 Session。
  不要先调用 `/auth/email/verify` 消费此绑定验证码。若 challenge 或 credential 过期，重新发起 GIS 登录。
- 同邮箱验证码登录复用用户并补齐 email identity；停用账号不能通过任一方式登录。
- 首次 Google 创建、同邮箱绑定和已绑定 Google 再次登录，均只补齐用户主资料中为空（`NULL`、空串或纯空白）的 `display_name` / `avatar_url`。已有值保留，包括邮箱前缀昵称；不会因再次登录覆盖用户已保存的资料。
- Google `name` 去除首尾空白后取前 100 字符；`picture` 仅接受长度不超过 2048 的 HTTPS URL。Google 缺少或未提供有效资料时不补；新用户缺少有效 `name` 时仍使用邮箱前缀作为昵称兜底。
- 验签失败：`40105 GOOGLE_CREDENTIAL_INVALID`；challenge 失效：`40106 GOOGLE_LOGIN_CHALLENGE_INVALID`；
  Origin 非法：`40300 FORBIDDEN`；并发唯一约束冲突：`40911 AUTH_CONFLICT`（客户端可重试）；
  Google 公钥网络故障：`50300 SERVICE_UNAVAILABLE`。成功后清除 challenge Cookie。
- 凭据只用于本次验签，不保存或记录 Google Token；用户、身份、条款和 Session 在一个事务内提交。
- Timezone 初始为 UTC，登录后可通过用户设置接口修改。
- 登录即代表用户接受页面展示的当前服务条款和隐私政策。具体生效版本由服务端配置并写入 Consent，不接受客户端自报版本。


#### 4.3.3 第三方邮箱首次绑定

如果 Google 账户使用非 Gmail、非 Google Workspace 托管的邮箱，即便 Google 返回
`email_verified=true`，首次绑定也需要确认当前邮箱归属。服务端返回 HTTP 409：

```json
{
  "code": 40910,
  "message": "请先验证邮箱以关联 Google 账号",
  "data": {"email": "user@example.com"},
  "request_id": "<request-id>",
  "error": {
    "key": "GOOGLE_EMAIL_VERIFICATION_REQUIRED",
    "fields": {}
  }
}
```

前端按以下顺序继续，Google credential 仅临时保存在内存：

1. 使用响应 `data.email` 调用 `POST /api/auth/email/code`，获得 verification_id；根据 expires_in / resend_after 展示有效期和重发倒计时。
2. 用户输入验证码后，调用 `POST /api/auth/google`，请求如下。不要先调用普通 `/api/auth/email/verify`，否则会提前消费验证码。
3. 成功后清除内存中的 Google credential、验证码和 verification_id，使用返回的 AuthResponse 完成登录。

```json
{
  "credential": "<the-google-id-token-kept-in-memory>",
  "verification_id": "<26-character-verification-id>",
  "code": "123456"
}
```

后端根据验证过的 Google credential 确定邮箱，并校验验证码记录对应同一邮箱；
用户创建或复用、身份关联、验证码消费、Consent 和 Session 一并提交。
绑定成功后再次使用同一 Google sub 登录，无需重复邮箱补验证。

#### 4.3.4 错误与前端处理

| HTTP | code / error.key | 前端处理 |
| --- | --- | --- |
| 401 | `40105 GOOGLE_CREDENTIAL_INVALID` | 凭据无效、过期或 nonce 不匹配等；提示重新开始 Google 登录，不无限重试原 credential。 |
| 401 | `40106 GOOGLE_LOGIN_CHALLENGE_INVALID` | nonce Cookie 缺失、无效或过期；检查 credentials、主机名及 Cookie 配置，再重新初始化。 |
| 401 | `40103 AUTH_SESSION_REVOKED` | 用户已停用等，停止登录并展示账号状态提示。 |
| 403 | `40300 FORBIDDEN` | 检查请求 Origin 与后端 CORS_ORIGINS；浏览器自动设置 Origin，前端 JS 不手动伪造。 |
| 409 | `40910 GOOGLE_EMAIL_VERIFICATION_REQUIRED` | 进入 4.3.3 的邮箱补验证流程。 |
| 409 | `40911 AUTH_CONFLICT` | 并发唯一约束冲突；允许用户重试，避免并行重复提交。 |
| 400 | `40010 EMAIL_CODE_INVALID` | 验证码错误、已失效、已消费或邮箱不匹配；提示更正或重发。 |
| 400 | `40011 EMAIL_CODE_EXPIRED` | 重新发送邮箱验证码。 |
| 429 | `42901 EMAIL_CODE_ATTEMPTS_EXCEEDED` | 停止尝试当前验证码，重新申请；发送限流另按 4.4 处理。 |
| 422 | `42200 VALIDATION_ERROR` | 按字段约束修正请求；不要记录或显示 credential 内容。 |
| 503 | `50300 SERVICE_UNAVAILABLE` | 可能未配置 Client ID，或 Google 公钥验证服务不可用；保留邮箱登录入口并提示稍后重试。 |

Google 弹窗被取消、SDK 未加载或浏览器阻止登录提示时，可能没有任何后端请求。
前端需区分这些状态与后端 HTTP 错误，不把用户取消显示为账号异常。

#### 4.3.5 本地前端接入步骤

本地配置约定：

| 配置 | 当前值 / 要求 |
| --- | --- |
| 前端地址 | `http://localhost:6002` |
| 后端 API Base URL | `http://localhost:6001/api` |
| Google Cloud 项目 | `Trade Lab` / `trade-lab-507705`（既有控制台名称与 Project ID） |
| 开发 OAuth 客户端 | `Trade Lab Web Local`（历史名称），Web application 类型 |
| Google Authorized JavaScript origins | `http://localhost`、`http://localhost:6002` |
| 后端环境变量 | GOOGLE_CLIENT_ID 为上述客户端；CORS_ORIGINS 包含前端来源；本地 APP_ENV=local |

浏览器统一用 localhost 访问前端和后端。虽然后端 CORS 也允许 `http://127.0.0.1:6002`，
Google 客户端当前未配置这个来源；localhost 与 127.0.0.1 也不能混用为 Cookie 主机名。
前端 6002 与后端 6001 是跨 Origin、同 Site，因此仍需要 CORS 和 credentials: include。

接入顺序：

1. 在登录页提供真实服务条款和隐私政策链接，按产品约定展示同意提示，并保存用户登录前输入。
2. 从 Google 加载 GIS SDK，等待脚本 load 后再访问 google.accounts.id，不使用旧版 platform.js / gapi.auth2。
3. 获取一次 `/api/auth/google/config`，将 client_id、nonce 传给 initialize，渲染官方按钮。
4. 将 callback 的 credential 提交后端；成功后保存内存 Access Token 与用户状态，返回登录前的页面。
5. 若需要邮箱补验证，保留当前 challenge 和内存 credential，按 4.3.3 继续。

以下示例展示接入核心。`onAuthenticated`、`onEmailVerificationRequired`、`onError` 是前端传入的 UI / 状态处理函数；
`onEmailVerificationRequired` 收到的 credential 只能保存在内存中。示例不包含产品条款 UI 和通用 HTTP Client 的刷新逻辑。

```html
<script src="https://accounts.google.com/gsi/client" async defer></script>
<div id="google-login-button"></div>
```

```javascript
const API_BASE = 'http://localhost:6001/api';

async function authRequest(path, body, method = 'POST') {
  const response = await fetch(`${API_BASE}${path}`, {
    method,
    credentials: 'include',
    cache: 'no-store',
    headers: body === undefined ? {} : { 'Content-Type': 'application/json' },
    body: body === undefined ? undefined : JSON.stringify(body),
  });
  const result = await response.json();
  if (!response.ok || result.code !== 0) {
    throw Object.assign(new Error(result.message || '登录失败'), {
      status: response.status,
      key: result.error?.key,
      data: result.data,
    });
  }
  return result.data;
}

// 在 SDK load 完成、页面已展示条款后调用；同一次登录流程只初始化一次。
async function mountGoogleLogin({
  element, onAuthenticated, onEmailVerificationRequired, onError,
}) {
  try {
    const config = await authRequest('/auth/google/config', undefined, 'GET');
    google.accounts.id.initialize({
      client_id: config.client_id,
      nonce: config.nonce,
      auto_select: false,
      use_fedcm_for_prompt: true,
      use_fedcm_for_button: true,
      callback: async ({ credential }) => {
        try {
          const auth = await authRequest('/auth/google', { credential });
          onAuthenticated(auth); // 内存保存 auth.access_token，更新 auth.user。
        } catch (error) {
          if (error.key === 'GOOGLE_EMAIL_VERIFICATION_REQUIRED') {
            onEmailVerificationRequired({ email: error.data.email, credential });
          } else {
            onError(error);
          }
        }
      },
    });
    google.accounts.id.renderButton(element, { theme: 'outline', size: 'large' });
  } catch (error) {
    onError(error); // SDK 加载失败、配置失败和网络错误需展示可恢复提示。
  }
}

// 补验证页面：分别由“发送验证码”和“提交验证码”动作调用。
async function sendGoogleEmailCode(email) {
  return authRequest('/auth/email/code', { email });
}
async function confirmGoogleEmail(credential, verificationId, code) {
  return authRequest('/auth/google', {
    credential, verification_id: verificationId, code,
  }); // 返回 AuthResponse，按普通登录成功处理。
}
```

- React/Vue 等组件不要因重渲染重复 initialize；开发模式 effect 重入时应复用初始化 Promise，避免两个配置请求覆盖 Cookie。
- 同一页面的按钮和 One Tap 共用一次 initialize。若 challenge 过期或用户退出后重新登录，清理旧流程再获取新配置；需要时重新挂载登录页。
- Google 登录成功会清除 challenge Cookie，不能继续复用旧 credential 创建新会话。普通业务请求不需要重新执行 GIS 登录。
- 前端刷新会话使用 `POST /api/auth/refresh`，明确指定 POST 并携带 Cookie；正式产品统一由 HTTP Client 处理刷新与请求重试。
- 业务接口使用 `Authorization: Bearer <SpeakQuant access_token>`。Refresh 失败按 4.6 返回登录页，保留用户输入。
- 退出使用 `POST /api/auth/logout`，携带 Access Token 和 Cookie；成功后清理内存状态并调用 `google.accounts.id.disableAutoSelect()`，不退出用户的整个 Google 账号。

### 4.6 `POST /auth/refresh`

无 JSON Body，浏览器自动携带 Refresh Cookie。服务端校验长期 Session，更新 `last_used_at`，返回新的 Access Token 和 User；Refresh Token 本身保持不变。

前端跨 Origin 开发时必须使用 `credentials: "include"`；服务端 CORS 只能允许明确的前端 Origin，不能在携带 Cookie 时使用 `*`。

若 Cookie 缺失、Token 不匹配或 Session 已撤销，返回 `40104 REFRESH_TOKEN_INVALID` 或 `40103 AUTH_SESSION_REVOKED`。前端清除内存 Access Token 并回到登录页，同时保留未提交输入到浏览器本地草稿。

前端统一刷新规则：

1. 普通业务接口收到 `40102 AUTH_TOKEN_EXPIRED` 时调用一次 Refresh。
2. Refresh 成功后替换内存中的 Access Token，并重试原请求一次。
3. 多个请求同时发现过期时复用同一个 Refresh Promise，避免并发刷新风暴。
4. 重试后仍为 401 时停止重试，进入登录页，避免死循环。

Refresh 逻辑只存在于统一 HTTP Client，不进入 Conversation、Agent、Replay 等业务代码。

### 5.3 `POST /conversations`

空白 New Conversation 不调用此接口。用户首次发送非空内容时调用。

Header：`Idempotency-Key` 必填；建议携带当前界面 `Accept-Language`，本次 Run 系统提示按第 2.2 节规则选择语言。

请求：

```json
{
  "content": "当 BTC 20 日均线上穿 60 日均线时做多"
}
```

请求体只提交首条消息内容。Agent 根据用户消息和上下文选择回复语言。

响应 HTTP `201`：

```json
{
  "id": "01K...",
  "title": "新研究"
}
```

服务端在同一事务中创建 Conversation、首条用户消息和 Agent Run，但创建接口只返回路由跳转所需的信息，不承担详情页数据聚合职责。

会话标题独立于策略名称：首轮成功回复（含等待澄清）结束时，以用户首条消息为主、首轮回复为辅，生成一次简短标题，自动标题最长 80 字符；普通问候也会生成标题，无需先创建 Strategy。生成失败时使用首条消息的单行前 80 字符。标题在终态 SSE 事件前保存，前端收到终态后刷新 Conversation 详情及列表即可。后续策略更新不自动改标题；用户通过 `PATCH /conversations/{id}` 手动改名后永不被自动生成覆盖，包括生成中的并发改名。原有已命名会话保持不变。

前端收到 `id` 后跳转到 Conversation 详情页，并统一执行：

```text
GET /conversations/{id}
GET /conversations/{id}/messages
GET /conversations/{id}/assets
```

Messages 接口在返回持久化消息历史的同时，通过 `active_run` 返回当前 Run 和 `stream_url`；前端随后连接 SSE。首次进入、刷新页面和从历史列表进入均使用相同初始化流程。

### 5.6 `PATCH /conversations/{id}`

请求字段均可选，但至少提交一个字段；未修改的字段直接省略：

```json
{
  "title": "我的 BTC 趋势策略",
  "is_favorite": true,
  "status": "archived"
}
```

- `title` 是研究名称（Conversation 标题），传入字符串长度为 1～200 个字符；保存时去掉首尾空白。前端应先去掉首尾空白，再校验非空及长度。超过 200 字符返回 HTTP `422`、`code=42200`、`error.key=VALIDATION_ERROR`。
- 用户修改 title 后 `title_source=user`，后续 AI 不再自动覆盖。
- 收藏不改变“全部”列表；收藏后记录进入“收藏”列表并移出“非收藏”列表，取消收藏则相反。

成功返回 HTTP `200`，`data` 直接为更新后的 `ConversationSummary`。完整 Envelope 示例：

```json

  "message": "ok",
  "data": {
    "id": "01K...",
```

### 5.8 Message

```json
{
  "id": "01K...",
  "conversation_id": "01K...",
  "agent_run_id": "01K...",
  "sequence": 12,
  "role": "assistant",
  "status": "completed",
  "content": "我先确认一个会显著影响策略的问题……",
  "cards": [],
  "created_at": "2026-08-20T09:31:00Z",
  "updated_at": "2026-08-20T09:31:04Z"

```

Message 不定义 `type=text/markdown`，内容格式由 `role` 决定：

- `role=user`：`content` 是无格式纯文本，前端必须转义后展示，不解析 Markdown。
- `role=assistant`：`content` 是 Markdown，前端按统一 Markdown 规范渲染并执行 XSS Sanitization；普通纯文本天然也是合法 Markdown。
- `cards` 始终为数组；普通消息返回空数组。同一条 Assistant 消息可以附带多张卡片，卡片不改变 `content` 的渲染格式。

### 5.9 `GET /conversations/{id}/messages`

Query：

- `before_sequence`：加载更早消息；首次不传。
- `limit`：默认 50，最大 100。

响应：

```json
{
  "items": [],
  "next_before_sequence": 100,
  "has_more": true,
  "active_run": {
    "id": "01K_RUN",
    "status": "running",
    "stream_url": "/api/agent-runs/01K_RUN/events"
  }
}
```

`items` 始终按 sequence 正序，只包含已经持久化的消息。当前实现不会把生成中的 Assistant 半成品写入 MySQL；实时文本、工具状态和卡片以 SSE Snapshot 为准。

`active_run` 可以为 `null`。Agent 消息正在编排 Replay 时优先返回前端已经连接的 `message` Run；没有活动的消息 Run 时，返回最新的 `queued/running` 确定性操作 Run。

服务端在同一数据库会话中先读取 `active_run`，再读取消息历史。Agent Finalizer 在同一事务中写入最终 Assistant Message 并结束 Run，因此这个响应只会表达两种有效状态：存在 `active_run`，前端继续连接 SSE；或者 `active_run=null`，最终消息已经可以从历史中读取。

### 5.10 `POST /conversations/{id}/messages`

Header：`Idempotency-Key` 必填；建议携带当前界面 `Accept-Language`，普通消息和澄清回答均按第 2.2 节规则选择本次 Run 系统提示语言。

请求：

```json
{
  "content": "为什么这里没有开仓？"
}
```

字段：

- 普通文本消息只需提交 `content`，其余字段均为特定交互场景下的可选字段。
- 回答 Clarification 时，传 `reply_to_message_id` 和非空 `structured_answers` 数组，一次提交卡片内所有必答题。每项为 `{question_id,value}` 或 `{question_id,custom_text}`，二者恰好填写一个非空字符串（最长 2000 字符）；`question_id` 必须使用卡片返回的题目 ID，不得重复。
- 批量回答时可以省略 `content`，服务端按原题顺序生成包含题目和答案的用户纯文本消息；如传入 `content`，则作为补充文字追加在回答之后。普通消息仍必须传非空 `content`（最多 20000 字符）。
- 原 `structured_answer` 单对象仅保留兼容，不可与 `structured_answers` 同传，也需要提供 `reply_to_message_id`；新接入统一使用数组，单题时数组长度为 1。
- 从 Replay 发起追问时可传 `context={replay_id,trade_id,fill_id,insight_id,timestamp}`，只提交当前交互实际关联的字段。
- 服务端必须验证 Replay 以及可选的 Trade/Fill/Insight 属于当前 Conversation。
- 请求体不包含 `client_message_id`；请求重试统一使用 Header 中的 `Idempotency-Key`，由前端公共 HTTP 层自动生成，业务页面无需处理。

整组回答请求示例：

```json
{
  "reply_to_message_id": "01K_ASSISTANT_MESSAGE",
  "structured_answers": [
    {"question_id": "01K_QUESTION_MARKET", "value": "合约"},
    {"question_id": "01K_QUESTION_TIMEFRAME", "custom_text": "15m"}
  ]
}
```

服务端验证题目属于被回复的 Assistant 消息、选项有效、自定义回答被允许，且同一卡片的必答题已全部回答。漏答、未知题目或非法选项返回 HTTP `400`、`BAD_REQUEST`；重复题目 ID、空答案、同时填写选项和自定义文本等请求格式错误返回 HTTP `422`、`VALIDATION_ERROR`。已完成的卡片再次使用新幂等 Key 提交返回 HTTP `409`、`RESOURCE_STATE_CONFLICT`；相同 Key 重试返回首次成功结果。

整组答案、原卡片的已答状态、一条 User 消息和一个新 Agent Run 在同一事务中保存；任一题校验失败，整组不保存。答案可以覆盖被回复消息内的多张澄清卡片，但每张涉及的卡片均须提交全部必答题。

响应 HTTP `202`：

```json
{
  "user_message": {
    "id": "01K...",
    "conversation_id": "01K...",
    "sequence": 37,
    "role": "user",
    "status": "completed",
    "content": "为什么这里没有开仓？",
    "cards": [],
    "created_at": "2026-08-20T09:35:00Z"

    "id": "01K_RUN",

```

`updated_messages` 返回本次提交所更新的历史 Assistant 消息，结构与 `/messages` 的 `items` 相同。普通发送时为 `[]`；批量回答成功时包含被回复的消息，其卡片已更新为 `status=completed`、`data.answered=true`，并在 `data.answers` 中保存答案。前端按消息 `id` 替换本地记录，再连接新 Run 的 SSE。刷新后通过 HTTP 历史恢复同样的题目、答案和已答状态。

## 6. Agent Run 与 SSE

SSE 的作用域是单个 Agent Run，不是整个 Conversation：

```text
一条用户消息或一次确认操作
  → 创建一个 Agent Run
  → 返回该 Run 唯一的 stream_url
  → SSE 只推送该 Run 的消息文本、临时工具状态、卡片及卡片状态
  → Run 完成、失败、取消或等待用户后关闭连接
```

- 历史 Conversation 消息只通过 HTTP 获取。
- SSE 不发送此前 Agent Run 的历史消息。
- 用户回答 Clarify、请求回测或再次追问时，会创建新的 Agent Run 和新的 `stream_url`。
- Messages 响应中的 `active_run` 只表示前端当前应连接的一个 `queued/running` Run。Agent 调用 `replay_run` 时内部会有一个 Replay 执行 Run，但它的状态卡同步到外层消息 Run，前端仍只连接消息 Run。

内部职责边界：

```text
AgentLoop → RunOutputStore → Redis
Redis → SSE API → 前端连接
AgentRunExecutor → AgentRunFinalizer → DAO → MySQL
```

- Agent Loop 只输出 Delta/Event，不处理或感知 SSE 连接。
- Redis 隔离生成端和传输端；零个、一个或多个 SSE 连接都不影响 Agent 执行。
- SSE API 只读取 Redis 并写入当前 HTTP Response，不负责保存最终业务数据。
- Agent Run 的最终落库由 Executor 调用 Finalizer 完成。

### 6.1 接口清单

| Method | Path | 用途 |
| --- | --- | --- |
| GET | `/agent-runs/{run_id}` | 查询 Run 最终/当前状态 |
| GET | `/agent-runs/{run_id}/events` | 订阅标准 SSE |
| POST | `/agent-runs/{run_id}/cancel` | 取消可取消的 Run |

### 6.2 为什么使用 fetch SSE

浏览器原生 `EventSource` 不能设置 `Authorization` Header。本项目使用 `fetch()` 获取 `text/event-stream` 并通过 `ReadableStream` 解析 SSE，不把 JWT 放进 URL。

前端伪代码：

```ts
const response = await fetch(streamUrl, {
  headers: {
    Authorization: `Bearer ${accessToken}`,
    Accept: "text/event-stream",
  },
  signal: abortController.signal,
});

if (!response.ok || !response.body) {
  // 按统一错误响应处理
}

// 使用项目 SSE parser 逐块解析 response.body，不按网络 chunk 直接 split 行。
```

### 6.3 SSE 响应 Header

```http
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```

服务端每 15 秒发送注释心跳：

```text
: ping 2026-08-20T09:30:15Z

```

### 6.4 SSE 与 Access Token 生命周期

- Access Token 只在建立 SSE HTTP 连接时校验一次。
- SSE 建立成功后，即使 Access Token 在运行途中到达 `exp`，服务端也不因此主动关闭该连接。
- 不在心跳或每个事件上重复校验 JWT 过期时间。
- 如果网络断开后重新连接时 Access Token 已过期，SSE 请求返回 `40102 AUTH_TOKEN_EXPIRED`。
- 前端调用 `POST /auth/refresh`，获得新 Access Token 后重新连接原来的 `active_run.stream_url`。
- Refresh 和重连不会创建新的 Agent Run，也不会重新提交用户消息、Clarify 回答或回测请求。
- 重连成功后先收到该 Run 的 `run.snapshot`，再继续接收实时增量。

### 6.5 SSE Frame

```text
event: message.delta
data: {"run_id":"01K...","conversation_id":"01K...","occurred_at":"2026-08-20T09:30:01Z","payload":{"message_id":"01K...","start_offset":0,"end_offset":8,"delta":"正在整理策略规则"}}

```

所有 `data` 都包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `run_id` | string | Agent Run ID |
| `conversation_id` | string | Conversation ID |
| `occurred_at` | datetime | 事件时间 |
| `payload` | object | 事件专属数据 |

### 6.6 SSE 事件

| event | payload | 前端行为 |
| --- | --- | --- |
| `run.snapshot` | `{run, messages, active_tools}` | 用本次 Run 的文本、卡片和正在执行的工具覆盖本地临时状态 |
| `message.delta` | `{message_id, start_offset, end_offset, delta}` | 消息不存在则创建，然后按字符偏移追加 Markdown |
| `tool.status` | `{message_id, id, label, status}` | 按 `id` 创建或更新临时工具执行状态 |
| `card.upsert` | `{message_id, card}` | 在对应消息的 `cards` 中，按 `card.id` 创建或整体替换 |
| `run.finished` | `{status, error}` | 标记 Run 终态并关闭 SSE |

`run.finished.status` 只允许 `completed/failed/cancelled/waiting_user`；仅 `failed` 时 `error` 非空，结构为 `{key,message}`。积分不足和费用待核实同样通过该事件反馈，完整字段、错误键和前端处理见 16.8。前端收到 `run.finished` 时同时清除该 Run 仍存在的临时 Tool Status。

协议刻意不定义 `run.started`、`message.started`、`message.completed`、`tool.started`、`tool.completed`、`card.created` 和 `card.updated`：

- Run 是否已开始由 `run.snapshot.run.status` 表达，额外的 `run.started` 不会带来新的业务状态。
- 第一条 `message.delta` 到达时，前端若找不到 `message_id`，直接创建空的 Assistant 消息并追加文本；不需要先等 `message.started`。
- 第一条 `card.upsert` 也可以创建对应 `message_id` 的 Assistant 消息容器，因此卡片可以先于文本出现，也可以完全不带文本。
- 第一条 `tool.status` 同样可以创建对应 `message_id` 的前端临时 Assistant 容器；这不代表单独创建一条持久化 Message。工具开始与结束统一使用同一事件和 `id` 原位更新。
- `card.upsert` 同时覆盖创建和更新，前端不需要维护两套分支。
- 消息是否已经完成跟随整个 Run 的 `run.finished`；当前不存在“一次 Run 内某条消息先独立完成、其他消息继续生成”的业务需求，因此不重复发送 `message.completed`。
- `run.finished` 不能省略，因为单纯关闭连接无法区分正常完成、等待用户、业务失败和网络中断。

服务端在每条 Assistant 消息开始输出前生成固定的 `message_id`，属于该消息的文本、临时工具状态与卡片事件始终使用同一 ID。

收到 `run.finished` 后，前端将该 Run 下仍为 `streaming` 的消息统一收尾：Run 为 `completed/waiting_user` 时设为 `completed`，Run 为 `failed/cancelled` 时设为对应状态。以后只有真的出现“同一 Run 内多条消息需要独立结束”的业务场景，才新增消息级终态事件。

不得用 `message.delta` 传内部思维过程、隐藏推理、Prompt、代码执行日志或服务队列术语。

`run.snapshot` 示例：

```json
{
  "run": {
    "id": "01K_RUN",
    "status": "running"
  },
  "active_tools": [
    {
      "message_id": "01K_MESSAGE",
      "id": "call_01K",
      "label": "正在读取回测详情",
      "status": "running"
    }
  ],
  "messages": [
    {
      "id": "01K_MESSAGE",
      "role": "assistant",
      "status": "streaming",
      "content": "我正在整理策略规则",
      "cards": [
        {
          "id": "01K_CARD",
          "type": "strategy_card",
          "status": "generating",
          "resource_id": null,
          "title": "正在生成 Strategy",
          "summary": null,
          "data": null
        }
      ]
    }

}
```

Snapshot 中的 `messages` 只包含本次 Agent Run 创建或正在更新的文本，以及这些消息所附卡片的最新概要和状态；`active_tools` 只包含当下仍在执行的临时工具状态。Snapshot 不包含整个 Conversation History，也不包含 Strategy 或 Replay 详情。历史记录仍由 `GET /conversations/{id}/messages` 返回。

#### Tool Status 协议

`tool.status` 用于不产生持久业务资产的通用读取或检查工具，例如“读取网页策略详情”和“读取回测详情”。

开始执行：

```text
event: tool.status
data: {"run_id":"01K_RUN","conversation_id":"01K_CONVERSATION","occurred_at":"2026-08-20T09:31:00Z","payload":{"message_id":"01K_MESSAGE","id":"call_01K","label":"正在读取回测详情","status":"running"}}
```

执行完成：

```text
event: tool.status
data: {"run_id":"01K_RUN","conversation_id":"01K_CONVERSATION","occurred_at":"2026-08-20T09:31:02Z","payload":{"message_id":"01K_MESSAGE","id":"call_01K","label":"已读取回测详情","status":"completed"}}
```

`status` 只允许 `running/completed/failed`。前端使用同一 `id` 原位更新；收到 `completed/failed` 后可以短暂展示再折叠或淡出。

`label` 由服务端 Tool Definition 生成，不使用模型自由生成的文案。事件不发送原始 Tool Name、Arguments、Result、内部日志或异常堆栈。工具结果只进入 Agent Transcript，Agent 随后通过 `message.delta` 继续回答。

Tool Status 不单独创建 Conversation Message、不写入 MySQL，也不进入 HTTP 历史消息。Redis `RunLiveState` 只保存当前 `running` 项；新连接使用 `run.snapshot.active_tools` 恢复当前进度，已结束的历史 Tool Status 不恢复。

`RedisRunOutputStore` 处理 Tool Status 时必须先更新 `RunLiveState` 再发布事件：`running` 时加入 `active_tools`，`completed/failed` 时从 `active_tools` 移除。这与文本、Card 使用同一 Snapshot 边界规则，保证断线重连时不会留下已结束的“正在读取”状态。

#### Snapshot 与实时 Delta 的实现模型

Agent 生成过程不依赖前端连接，前端连接、断开或重连都不能暂停或改变 Agent。服务端为每个运行中的 Agent Run 维护一份短期 `RunLiveState`：按 `message_id` 保存当前完整文本、Offset 和有序 `cards` 数组，按 Tool Call ID 保存当前 `active_tools`，同时保存 Run 状态以及服务端内部使用的最后 Redis Stream ID。

Agent Loop 每次获得新的 LLM 文本块时只调用 `RunOutputStore` 输出 Delta。`RedisRunOutputStore` 负责：

1. 将文本追加到 `RunLiveState.messages[message_id].content` 并更新该消息的 Offset。
2. 发布带有 `start_offset/end_offset` 的 `message.delta`。

这两项 Redis 更新必须保持一致，但属于输出存储实现，不属于 Agent Loop 或 SSE 连接逻辑。Agent Loop 不持有前端连接列表，也不向任何 SSE Response 直接写数据。

`RunLiveState` 才是运行过程中 Snapshot 的实时来源。Snapshot 本身不是持续变化并反复推送的对象；每次建立 SSE 连接时，服务端从当时的 `RunLiveState` 复制一份不可变快照发送给该连接。

为了覆盖“读取 Snapshot 的同时生成器仍在输出”的竞态，SSE 服务必须按以下顺序建立连接：

1. 先订阅该 Run 的实时事件，并开始在服务端缓冲新事件。
2. 再读取当前 `RunLiveState`，向前端发送 `run.snapshot`。
3. 根据 Snapshot 对应的最后 Redis Stream ID，丢弃已经包含在 Snapshot 中的缓冲事件，只发送边界之后的新事件；文本 Offset 继续作为前端内容连续性校验。
4. 继续转发之后到达的新事件，直到 Run 进入终态并关闭 SSE。

因为生成器总是“先更新实时状态，再发布 Delta”，所以：订阅前产生的文本一定已包含在 Snapshot 中；订阅后产生的文本一定会进入连接缓冲。两者可能重叠，但不会形成缺口，重叠部分由 Offset 去重。这个过程不需要暂停 Agent。

生产环境中 `RunLiveState` 与实时事件通道必须是 API 实例和 Agent Worker 可共同访问的短期基础设施；共享内存仅用于单进程开发，分布式部署使用 Redis。MySQL 检查点用于历史读取和故障恢复，不作为正常连接时实时 Snapshot 的唯一来源。

前端连接时不传事件 `seq`。文本连续性由 `start_offset/end_offset` 校验；Tool Status 按 `id` 更新；卡片先按 `message_id` 定位所属消息，再按 `card.id` 原位替换。SSE 建立后依赖 HTTP/TCP 保序；连接中断时重新建立连接并获取新的 Snapshot，而不是要求旧连接续传。

前端收到快照后直接替换对应 Run 的临时 UI。随后处理 delta 时：

`start_offset/end_offset` 使用 Unicode Code Point 数量；Python 使用 `len(content)`，JavaScript 使用 `Array.from(content).length`，避免 Emoji 等字符造成偏移理解不一致。

- `end_offset <= 当前内容长度`：该 delta 已包含在快照中，忽略。
- `start_offset == 当前内容长度`：正常追加。
- `start_offset > 当前内容长度`：出现缺口，重新获取 Run/Message 快照，不猜测缺失内容。

#### Run 终态持久化顺序

Agent Loop 返回最终 `AgentRunResult` 后，由 `AgentRunExecutor` 负责收尾：

```text
AgentRunExecutor
  → AgentRunFinalizer
      → DAO 事务写入 MySQL
  → MySQL 提交成功
  → RunOutputStore 发布 run.finished
  → SSE API 转发终态事件并关闭连接
```

成功事务保存该 Run 产生或更新的全部 Assistant 最终消息及其 `cards` 数组，更新 Agent Run、Conversation，并按本次结果写入 Strategy、Replay 等相关业务数据。失败或等待用户时同样先通过 Finalizer 保存对应状态，再发布 `run.finished`。

必须先提交 MySQL，再发布 Redis `run.finished`。否则前端收到终态后立即请求 HTTP 详情，可能读取不到最终数据。SSE API 不参与该事务，也不能承担最终消息落库职责。

### 6.7 Clarification Card

```json
{
  "id": "01K_CARD",
  "type": "clarification_card",
  "status": "waiting_user",
  "resource_id": null,
  "title": "需要确认策略信息",
  "summary": "请选择交易市场和执行周期",
  "data": {
    "questions": [
      {
        "id": "01K_QUESTION_MARKET",
        "question": "这个策略用于现货还是合约？",
        "required": true,
        "options": ["现货", "合约"],
        "allow_custom": false
      },
      {
        "id": "01K_QUESTION_TIMEFRAME",
        "question": "使用哪个执行周期？",
        "required": true,
        "options": ["1h", "4h"],
        "allow_custom": true
      }
    ],
    "answered": false,
    "answers": []
  }
}
```

Clarification 与其他卡片一样通过 `card.upsert` 发送。Agent 将当前已知、可一起确认的问题合并为一次 `ask_user` 调用，一张卡片包含 1～5 道题，每题提供 2～5 个快捷选项。前端按 `questions` 顺序让用户连续作答，完成整组后通过 `POST /conversations/{id}/messages` 一次提交 `structured_answers`，不逐题发送消息，不单独产生回答接口。
`options` 是 Agent 动态生成的选项文本数组，前端直接展示并将选中的文本作为回答提交；当前不定义额外的 `label/value` 对象。

每题的 `id` 由服务端生成，在 SSE 和历史消息中保持稳定，前端原样用作 `question_id`。旧历史卡片缺少题目 ID 时，服务端读取时补齐稳定 ID，无需前端自行生成。当前生成的题目均为 `required=true`；`allow_custom=false` 时只能提交选项中的文本。仅当前题的答案引入无法预先确定的新问题时，Agent 才在下一轮继续询问。

提交成功后卡片保留原有题目，将 `status` 置为 `completed`、`data.answered` 置为 `true`，`data.answers` 按题目顺序保存 `{question_id,value}` 或 `{question_id,custom_text}`。前端据此恢复已答内容并停止重复提交。

Clarification 是全局通用交互，不是回测专用确认：问题能归纳为少量封闭选项、点击明显比输入更方便时使用。需要开放式补充、解释取舍，或者按钮没有降低回答成本时，Agent 直接在 Markdown 中自然语言提问；用户仍通过同一个消息接口回答。

### 6.8 Card 协议

SSE 中的卡片只携带前端展示和后续 HTTP 跳转所需的最小信息：

```json
{
  "id": "01K_CARD",
  "type": "replay_card",
  "status": "queued",
  "resource_id": "01K_REPLAY",
  "title": "BTC 均线趋势策略 · 第 1 次验证",
  "summary": "正在准备行情数据",
  "data": null
}
```

Card 公共字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | Card ULID；创建后保持不变，是更新卡片的唯一键 |
| `type` | string | 卡片渲染类型；新增类型不改变 SSE 事件协议 |
| `status` | string | 当前状态；合法值由具体 `type` 定义 |
| `resource_id` | string/null | 对应业务资源 ID；生成完成前或无独立资源时为空 |
| `title` | string | 卡片标题 |
| `summary` | string/null | 卡片简要说明 |
| `data` | object/null | 类型专属的轻量展示数据；不得放入完整业务详情 |

首次出现：

```text
event: card.upsert
data: {"run_id":"01K_RUN","conversation_id":"01K_CONVERSATION","occurred_at":"2026-08-20T09:32:00Z","payload":{"message_id":"01K_MESSAGE","card":{"id":"01K_CARD","type":"replay_card","status":"queued","resource_id":"01K_REPLAY","title":"BTC 均线趋势策略 · 第 1 次验证","summary":"正在准备行情数据","data":null}}}
```

完成后更新同一张卡：

```text
event: card.upsert
data: {"run_id":"01K_RUN","conversation_id":"01K_CONVERSATION","occurred_at":"2026-08-20T09:32:09Z","payload":{"message_id":"01K_MESSAGE","card":{"id":"01K_CARD","type":"replay_card","status":"queued","resource_id":"01K_REPLAY","title":"BTC 均线趋势策略 · 第 1 次验证","summary":"已确认，等待执行","data":null}}}
```

前端先按 `message_id` 定位消息，再在该消息的 `cards` 数组中按 `card.id` 执行 upsert：不存在则追加，存在则使用完整 `card` 对象原位替换。首次出现顺序就是卡片展示顺序，后续更新不得改变位置。Redis Stream 保证同一 Run 内事件顺序，因此不额外引入卡片 `version`。

一条 Assistant Message 可以包含零张、一张或多张卡片。同一条消息中的每张卡片必须使用不同 `card.id`；一张卡片从 `generating` 更新为 `completed` 时必须保持原 ID。新增卡片类型只需要新增对应 Card Schema 和前端 Renderer，不新增 SSE event。

当前卡片类型：

- `clarification_card`：`waiting_user/completed`。
- `strategy_card`：`generating/completed`。
- `replay_card`：`queued/running/completed/failed/cancelled`。
- `actions`：`available/disabled`，预留。

`replay_confirmation` Renderer 暂时保留兼容，但 Agent 当前不生成该卡片。

以上只是当前 Renderer 注册表，不是封闭枚举。前端遇到暂不认识的 `type` 时，至少可以使用公共字段渲染通用标题、摘要和状态，不得因此中断后续 SSE 处理。

回测执行期间不定义结构化阶段列表，通过同一张 `replay_card` 的 `status/summary` 表达必要状态。未来如果需要更细进度，仍只扩展该卡片，不新增独立进度实体。

预留确认卡片通过 `data.conditions` 携带允许用户编辑的少量条件；运行中的 Replay 卡片不携带 Strategy Code、K 线、交易记录、Timeline、洞察或报告。`resource_id` 可用后，前端通过 Strategy 或 Replay HTTP 接口获取详情。

### 6.9 首次连接与断线恢复

前端进入 Conversation 详情页时：

1. 并行请求 `GET /conversations/{id}`、`GET /conversations/{id}/messages` 和所需资产接口。
2. HTTP Messages 负责渲染已经持久化的完整历史。
3. Messages 响应的 `active_run=null` 时不建立 SSE，页面完全使用 HTTP 数据。
4. `active_run` 存在时连接其 `stream_url`。
5. SSE 首条 `run.snapshot` 中的当前 Run 消息按 `message_id` upsert 到消息列表，之后再追加 Delta。

若 Run 在“Messages 返回 active_run”之后、SSE 真正建立之前已经完成，SSE 接口仍返回一次包含最终消息和终态 Run 的 `run.snapshot`，随后发送对应终态事件并关闭。Snapshot 与 HTTP 历史出现同一消息时统一按 `message_id` upsert，不会重复展示，也不需要重新提交消息。

SSE 本身只负责实时传输，本项目不承诺逐包重放。恢复的是当前文本、正在执行的工具和卡片最新状态：

1. 网络断开后，前端只检查刚才断开的 `run_id`，调用 `GET /agent-runs/{run_id}`；需要时同时刷新 Conversation Messages。
2. Run 已完成、失败、取消或 `waiting_user` 时，直接使用 HTTP 的消息和资源状态恢复页面，不再连接该 Run 的 SSE。
3. 只有该 Run 仍为 `queued/running` 时，才重新请求它原来的 `stream_url`。
4. 服务端新连接建立后首先发送 `run.snapshot`，仅包含该 Run 的文本、活动工具和卡片最新状态。
5. 前端使用 Snapshot 覆盖旧的流式文本、活动工具和卡片，再继续接收 `message.delta/tool.status/card.upsert`。
6. Access Token 过期时先调用 Refresh，再携带新的 Authorization 重连。

这种恢复允许丢失已经没有意义的中间传输包，但不会丢失用户消息、最终 AI 回复和已经持久化的卡片/资源结果，也避免把高频文本事件写入 MySQL。

### 6.10 `GET /agent-runs/{id}`

```json
{
  "id": "01K...",
  "conversation_id": "01K...",
  "status": "waiting_user",
  "error": null,
  "started_at": "2026-08-20T09:30:00Z",
  "finished_at": "2026-08-20T09:31:00Z",
  "stream_url": "/api/agent-runs/01K.../events"
}
```

`data` 字段：

| 字段 | JSON 类型 | 定义 |
| --- | --- | --- |
| `id` | string | Run ULID |
| `conversation_id` | string | Conversation ULID |
| `status` | string | `queued/running/completed/waiting_user/failed/cancelled` |
| `error` | object / null | failed 时为 `{key:string,message:string/null}`，其他状态 null；积分相关键见 16.8 |
| `started_at` | UTC 时间 string / null | 尚未开始为 null |
| `finished_at` | UTC 时间 string / null | 尚未结束为 null |
| `stream_url` | string | SSE 相对地址，携带鉴权后可订阅；不创建新 Run |

查询成功始终 HTTP 200 / code 0，包括业务执行失败的 Run；执行错误在 `data.error`，不在顶层 `error`。当前不返回 `charge_id`，费用入口见 16.7。

对于新建的消息 Run，`data.error.message` 与终态 SSE 使用同一份已落库的本地化错误原因，语言取创建该 Run 的请求，规则见 2.2；查询时不重新选择语言或改写历史错误。

### 6.11 `POST /agent-runs/{id}/cancel`

Header：`Idempotency-Key` 必填。

仅 `queued/running` 且底层操作支持取消时成功。已进入不可中断提交阶段可以返回 `409 RUN_NOT_CANCELLABLE`，但仍保证最终状态通过 SSE/HTTP 可见。

### 7.1 接口清单

| Method | Path | 用途 |
| --- | --- | --- |
| GET | `/conversations/{conversation_id}/strategy` | Current Strategy 详情 |
| GET | `/strategies/{strategy_id}/history` | 当前/历史切换列表 |
| GET | `/strategy-nodes/{node_id}` | 历史 Strategy 详情 |
| POST | `/strategies/{strategy_id}/restore` | 恢复历史节点到 Current Strategy |

Strategy 不提供直接编辑接口。所有设计和代码修改必须通过 Agent Conversation 完成。

#### 名称与变更摘要

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `name` | string | 策略核心交易逻辑名称，优先沿用用户叫法。小调整保持稳定，旧名称不再准确时才改名；不默认拼接回测标的、周期、参数。历史节点保留冻结名称。 |
| `change_summary` | string / null | 版本选择器使用的短标签。新 Agent 写入中文通常 8～20 字、最多 32 字符；英文通常 3～8 词、最多 80 字符。描述累计关键变化，例如“收紧止损，加入量能过滤”。无历史基准时后端统一保存“初始方案”或“Initial setup”，不罗列完整策略规则。 |
| `change_base_node_id` | string / null | 此摘要比较的同策略历史节点 ID；修改时取最近已形成节点，无历史时为 null。用于明确比较对象，不是显示版本号。 |

`change_base_node_id` 固定记录这条摘要实际比较的基准。若回测进行中又有修改，后来完成的节点不会悄悄改写当前摘要的基准；下一次修改通过 `strategy_get.comparison_base` 读取最新已形成节点并重新整理。

以上字段同时返回于 CurrentStrategyDetail、history.current、history.items 和 StrategyNodeDetail。`change_summary` 不等于整体策略介绍 `design_summary`，也不是回测收益结论。完整参数和规则放在 Design；标签不重复策略名或未变内容。过长/多行的修改摘要会在调用 Code Agent 前返回校验错误，模型需重写，不截断后保存。历史兼容存储仍保留 200 字符容量。摘要用用户语言描述具体调整，不虚构优化效果；连续多次未回测修改覆盖更新同一条累计摘要，不新增节点。Agent 更新成功后，聊天中的 `strategy_card.title` 使用策略名，`strategy_card.summary` 使用本次累计变更摘要，便于回看对话时识别调整。

名称、摘要和比较基准随 Replay 创建冻结，完成时写入历史节点；之后的策略修改不会改变已冻结信息。即便完成时 Current Strategy 已变化，节点仍使用发起时的摘要和基准。恢复历史后，当前摘要为“恢复「来源摘要或名称」方案”，比较基准为恢复时最近形成的节点；原节点保持不变。相同策略重复回测复用节点，不产生新的策略变更。

旧记录新增字段为 null，不推测或回填不存在的变更说明。前端历史列表以 `change_summary` 为主、`name` 和时间/回测次数为辅；缺少摘要时回退到 `name`，以时间和回测次数辅助识别。选中状态仍以 `id` 标识，不能用名称或摘要去重。

## 8. Replay 创建与执行

### 8.1 核心边界

聊天主流程由 Agent 调用内部 `replay_run` Tool。用户已经明确要求回测且关键条件清晰时，Tool 直接创建 Replay、冻结 Strategy 与执行条件并启动回测，消息中直接出现 `replay_card`，不生成 `replay_confirmation`。

信息存在关键歧义时，Agent 使用自然语言或全局 `clarification_card` 询问；数据量超过服务端阈值时必须先取得用户同意或缩小范围。Clarification 只收集新的用户消息，不创建 Replay 草稿。

Agent Tool 只提交结构化条件。Replay 的数据库创建、幂等、Strategy 快照冻结、行情准备和 Sandbox 执行仍由确定性 Controller/Core 完成。Replay 状态固定为：`queued/running/completed/failed/cancelled`。

`replay_confirmation` 和基于它的 `POST /replays` 暂时保留为传统表单/兼容入口，但不属于当前 Agent 聊天流程。

### 8.2 接口清单

| Method | Path | 用途 |
| --- | --- | --- |
| POST | `/replays` | 备用传统表单入口：创建 Replay 并启动执行 |
| GET | `/replays/{replay_id}` | 获取 Replay 状态、条件和已有结果 |
| POST | `/replays/{replay_id}/cancel` | 取消 queued/running Replay |
| POST | `/replays/{replay_id}/retry` | 重新执行 failed/cancelled Replay |

### 8.3 Replay 执行条件

Agent Tool 或备用 `POST /replays` 最终都必须形成以下完整条件：

```json
{
  "symbol": "BTC/USDT",
  "market_type": "spot",
  "contract_type": null,
  "start_at": "2025-08-20T00:00:00Z",
  "end_at": "2026-08-19T23:59:59Z",
  "initial_capital": "10000.00000000",
  "leverage": null
}
```

现货固定 `contract_type=null`、`leverage=null`；合约 MVP 使用 `contract_type=perpetual`，`leverage` 必须大于等于 `1`。Strategy 方向、执行周期、手续费、滑点、仓位规则和数据源由 Strategy Code 与服务端规则解析，不允许前端提交。

`initial_capital` 是分配给当前单策略的独立资金预算。新建 Replay 固定全仓连续复投：`position_sizing.type=equity_percent`、`value=1.00000000`，平仓后按扣除成本的实际剩余资金投入下一笔；暂不提供固定金额或自定义入场比例。入场数量包含本次成交手续费并按交易精度向下取整，不预扣未来平仓费，不额外保留固定比例现金。合约保证金与开仓手续费合计不超过预算，杠杆继续读取 `leverage`。

历史 Replay 保留原冻结条件及结果（包括旧的 10%），`retry` 也不切换；使用新规则须新建 Replay，不能直接对旧指标乘以 10。

MVP 固定使用单向净持仓：现货只做多；合约 Strategy 可以声明 `long/short/both`，但同一时刻只能有一个净持仓方向，不支持 Hedge Mode。

### 8.4 `POST /replays`（备用传统表单入口）

当前 Agent 不调用此 HTTP 接口；它使用内部 `replay_run` 并复用相同 Replay 创建与执行逻辑。本接口暂时保留给未来高级参数表单和旧确认卡兼容。

Header：`Idempotency-Key` 必填。

```json
{
  "message_id": "01K_MESSAGE",
  "card_id": "01K_CARD",
  "conditions": {
    "symbol": "BTC/USDT",
    "market_type": "spot",
    "contract_type": null,
    "start_at": "2025-08-20T00:00:00Z",
    "end_at": "2026-08-19T23:59:59Z",
    "initial_capital": "20000.00000000",
    "leverage": null
  }
}
```

- `message_id`：承载确认卡片的 Assistant Message ID。
- `card_id`：该消息中 `replay_confirmation.id`。
- `conditions`：前端将确认表单当前值完整提交，允许用户在确认前修改。

后端在一个事务中完成：

1. 锁定当前用户的 Message，定位 `card_id`，校验其仍为 `replay_confirmation/waiting_confirmation`。
2. 从卡片内部读取可信的 `strategy_id/strategy_revision`，锁定 Current Strategy 并检查 revision 未变化。
3. 校验用户最终条件，重新解析 Strategy Runtime Spec，冻结 Strategy Design、Code、条件和执行假设。
4. 创建状态为 `queued` 的 Replay 和执行 Agent Run。
5. 保持 `card.id` 不变，把确认卡原位替换为带 `resource_id` 的 `replay_card/queued`。
6. 提交事务后启动后台执行并返回 HTTP `202`。

若校验失败，事务不创建 Replay。并发或重复点击由 Message 行锁、卡片状态和 `Idempotency-Key` 共同保证不会产生两个 Replay。

响应：

```json
{
  "replay": {
    "id": "01K_REPLAY",
```

### 8.5 `POST /replays/{id}/cancel`

Header：`Idempotency-Key` 必填。只允许取消 `queued/running`：

```json
{

  "status": "running",
  "cancel_requested": true
}
```

`queued` 可以立即变为 `cancelled`；`running` 记录取消请求，由执行器在安全检查点停止。已经完成的 Replay 不删除，接口返回 `completed` 和 `cancel_requested=false`。

### 8.6 `POST /replays/{id}/retry`

Header：`Idempotency-Key` 必填，请求体为空。只允许 `failed/cancelled`，复用同一个 Replay ID、已冻结 Strategy Code 和条件，增加内部 `attempt` 后重新进入 `queued`。重试不要求再次确认，也不创建第二个 Replay。

响应结构与 `POST /replays` 相同，并返回新的 `agent_run.id/stream_url`。

## 9. Replay 数据与播放

### 9.1 接口清单

| Method | Path | 用途 |
| --- | --- | --- |
| GET | `/conversations/{conversation_id}/replays` | 已完成 Replay History/Workspace 切换列表 |
| GET | `/replays/{replay_id}` | Replay Workspace 首屏详情 |
| PATCH | `/replays/{replay_id}` | 仅修改 Replay 名称 |
| GET | `/replays/{replay_id}/candles` | 按主周期或辅助周期分页读取 K 线；主周期附带预计算状态 |
| GET | `/replays/{replay_id}/trades` | 交易与成交记录 |
| GET | `/replays/{replay_id}/insights` | Replay 过程洞察与全局复盘洞察 |
| GET | `/replays/{replay_id}/report` | 完整研究报告 |

Replay 在 Agent 的 `replay_run` Tool 真正发起回测时创建，在执行完成后拥有不可变结果数据。完整生成顺序为：

```text
历史行情与 Strategy 快照
  → 回测执行
  → 交易、成交和逐 K 状态序列
  → AI Insights 与 Report
  → 播放数据文件写入对象存储
  → MySQL 写入 Replay 结果及索引
  → replay_card.status=completed
```

`GET /replays/{id}` 在 `queued/running/failed/cancelled` 时也可读取状态、冻结条件和错误；`result/playback` 为空。K 线、交易、洞察和报告接口只在 `completed` 后可用。用户播放、暂停或拖动进度不会重新运行策略、调用 Agent 或修改 Replay；完成后的结果只读，只有 `name` 允许更新。

数据是“生成一次、只读获取”，但不保证“一个请求下载全部”：首屏摘要、交易、洞察和报告分别按需读取；K 线与逐 K 状态体量较大，按游标或时间窗口分段加载。

Replay 的交互由前端基于同一时间轴完成：

- 播放、暂停、倍速、拖动、逐根推进和图表动画均为前端状态。
- 前端根据 Trade Fill 的 `candle_id/action/price/reason` 在对应 K 线上生成 Timeline Marker，并按当前 K 线显示仓位、权益和交易状态，不向后端上报播放位置。
- `runtime` Insight 直接绑定一根 `candle_id`；前端播放到并处理完该 K 线后揭示，可以暂停、突出显示证据区间或等待用户继续。
- `global` Insight 在进入整体预览、播放完成或用户跳过播放后展示，不要求绑定时间点。
- 点击 Trade、Fill 或有时间证据的 Insight 时，前端在本地定位对应时间点/区间。
- 用户继续追问时，调用 Conversation Message 接口并携带 `replay_id` 及可选的 `trade_id/fill_id/insight_id/timestamp`，创建新的 Agent Run；它是新的聊天交互，不属于 Replay 播放协议，也不修改原 Replay。

播放规则：

- 当前页面通过 SSE 收到 `replay_card` 从 `queued/running` 更新为 `completed` 时，前端自动打开该 Replay 并开始播放；该完成事件在当前交互中只处理一次。

- 后端不记录“是否首次打开”，也不需要前端额外写入本地首次打开标记。

- 接口中的 `result` 永远是完整回测指标。前端概览或播放到终点时展示该结果；播放中可从起点至当前播放位置的主周期 `state.equity` 计算实时指标，不能提前展示未来数据。具体口径见下文及 [前端调整说明](Replay%20全仓连续复投前端调整说明.md)。

资金与回撤口径：

- `execution_assumptions.position_sizing` 展示此 Replay 冻结的规则；`equity_percent=1` 才显示“全仓 · 连续复投”，旧比例按实际值显示，不从发布时间推断。
- `state.equity` 是策略权益，包含持仓浮盈亏和已发生的费用。`net_profit=equity-initial_capital`，`net_return_rate=net_profit/initial_capital`；前端不再从权益额外扣手续费或将交易收益率相加。
- 以 `initial_capital` 初始化历史峰值 `peak`，每个主周期收盘更新 `peak=max(peak,equity)`；当前回撤为 `(peak-equity)/peak`，截至当前的最大回撤是所有已见当前回撤的最大值。`state.drawdown_rate` 表示当前回撤，`result.max_drawdown_rate` 表示全程最大回撤，两者不同。
- 最大回撤区间取产生最大跌幅的历史权益峰值时点至后续谷值时点，幅度分母是该峰值。K 线图阴影只表达时间区间，其高度不代表价格跌幅；所有回撤与区间从同一主周期权益序列计算，包含初始资金起点。回放倒退时只使用当前位置之前的前缀结果。
- 所有 `*_rate` 使用小数比例字符串，例如 `0.038748` 展示为 `3.8748%`。单笔 Trade 的 `return_rate=net_pnl/entry_notional`，不能替代策略收益率或最大回撤；合约名义价值包含杠杆，旧 Replay 也可能未全仓。

### 9.6 `GET /replays/{id}/candles`

Query：

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `timeframe` | string | Replay 的 `execution_timeframe` | 只允许该 Replay 冻结的主周期或 `auxiliary_timeframes` 中的周期，区分大小写，如 `1h`、`4h`、`1M` |
| `cursor` | string | - | 当前周期与时间窗口的分页游标；每个周期独立保存，切换周期或时间窗口时重置 |
| `limit` | int | `2000` | 单个周期每页数量，1～5000 |
| `from` | datetime | Replay 的 `start_at` | 按 K 线开盘时间筛选，包含该时刻 |
| `to` | datetime | Replay 的 `end_at` | 按 K 线开盘时间筛选，不包含该时刻 |

每次请求返回一个周期的数据集，保持原有 `items/next_cursor/has_more` 分页结构。多周期图表根据详情中的 `strategy.execution_timeframe/auxiliary_timeframes`，或本接口的 `available_timeframes`，分别请求所需周期并独立分页。例如主周期 `1h`、辅助周期 `4h`：

```http
GET /api/replays/{id}/candles?limit=2000
GET /api/replays/{id}/candles?timeframe=4h&limit=2000
```

- 不传 `timeframe` 时与原接口一致，返回主周期和逐 K 状态；传入主周期得到相同结果。
- 请求周期必须属于该 Replay，不能用当前 Strategy 的新周期替换历史 Replay 的冻结周期，也不会临时重采样或下载其他周期。即使共享行情中有其他周期，也不能通过本接口读取。
- 所有时间转为 UTC；未带时区的时间按 UTC 解释。实际查询范围取请求窗口与 Replay 的 `[start_at, end_at)` 的交集，不返回区间外的 Warmup K 线；交集为空时返回空 `items`、`next_cursor=null`、`has_more=false`。
- 辅助周期只返回在 Replay `end_at` 之前已经收盘的 K 线，避免返回虽然已存入共享行情、但回测结束时仍未收盘的数据。`from/to` 仍按开盘时间筛选；播放过程中的可见性按下文的 `close_time` 规则处理。
- 周期不属于 Replay、无效游标，或同时提供的 `from >= to`，返回 HTTP 400、`code=40000`、`error.key=BAD_REQUEST`。周期错误的 `error.fields` 包含请求的 `timeframe` 和 `available_timeframes`。空字符串/过长周期、非法时间格式和越界 `limit` 返回 HTTP 422。Replay 不属于当前用户、尚未完成或结果不存在时返回 HTTP 404。

数据集与播放约定：

- `timeframe` 标识当前返回的数据集；`execution_timeframe` 标识驱动 Replay 播放的主周期；`available_timeframes` 按主周期在前、辅助周期按冻结顺序排列，且不重复。这些字段只读取 Replay 冻结记录，不修改策略或触发回测。
- `items[].id` 是共享 `market_candles.id`，同一周期同一根 K 线的 ID 稳定。不同周期是不同的 K 线记录，不能按 ID 或数组下标相互对齐。
- `sequence` 是当前周期、当前查询窗口内从 1 开始的顺序，跨分页连续；改变 `from/to` 后重新编号，不是跨周期的全局序号。`time` 表示开盘时间，`close_time` 表示实际收盘时间，两者均为 UTC。
- `state` 只有主周期返回对象，表示该主 K 线处理完后的仓位、权益和规则状态；`position` 为 `long/short/flat`。辅助周期返回 `null`，不复制主周期状态，也不使用全零状态冒充空仓。详情中的 `counts.candles` 仍只统计主周期 K 线，不是所有周期数量之和。
- Trade、Fill 和 Runtime Insight 的 `candle_id` 继续绑定主周期 K 线。前端以主周期驱动账户状态、交易标记和洞察；切换或并列展示辅助周期图表不会产生新的播放时间轴。
- 播放到某根主 K 线处理完成时，以其 `close_time` 为当前时刻；辅助图表只能揭示 `close_time <= 当前主 K 线 close_time` 的完整 K 线。不得因为辅助 K 线的 `time` 更早，就提前展示其最终 OHLCV。例如播放到 `1h` 的 00:00 K 线结束时，不能展示 00:00～04:00 的完整 `4h` K 线；需等到 03:00 的主 K 线结束。全局预览可展示已加载的完整历史。

Replay 只会在对象存储文件和数据库索引都准备完成后发布，因此正常情况下不存在“Replay 已可见但播放数据仍在准备”的状态。前端不直接依赖对象存储内部 Key。

### 9.7 `GET /replays/{id}/trades`

Query：`page/size/direction/exit_reason`。

一条 Trade 表示一次完整的净持仓周期。分组由回测执行器完成，前端不参与判断：

1. 净仓位从 `0` 变为非 `0` 时创建 Trade。
2. 持仓期间同方向成交属于 `increase`，仍在当前 Trade 中。
3. 反方向成交未使仓位归零时属于 `reduce`，仍在当前 Trade 中。
4. 净仓位回到 `0` 时以 `close` 结束当前 Trade。
5. 一次成交使仓位穿过 `0` 时，执行器在同一根 K 线上拆为旧 Trade 的 `close` Fill 和新 Trade 的 `open` Fill。
6. 回测结束仍有持仓时，执行器生成 `reason=end_of_test` 的 `close` Fill，完成最后一条 Trade。

- 分批加仓或退出时，每个 Fill 可以绑定不同的 `candle_id`；Trade 的入场、出场 K 线只是该完整持仓生命周期的首尾摘要。
- `items` 按 Trade `sequence` 排序；Fill 的 `sequence` 是 Replay 内全局成交顺序。前端需要完整成交时间轴时，将所有 Trade 的 Fill 拍平后仅按 Fill `sequence` 排序即可，不重新计算 Trade 归属。即使反手产生的平仓和开仓 Fill 位于同一根 K 线、具有相同 `occurred_at`，顺序也仍然确定。

### 9.8 `GET /replays/{id}/insights`

Insight 承担“陪用户分析交易过程”和“事后复盘”两种职责：

- `scope=runtime`：过程洞察。直接绑定 `candle_id`，前端处理完该 K 线后揭示；内容只能使用该 K 线收盘及之前已经发生的数据，禁止引用未来交易结果。

这里不再区分 `trigger_at` 和 `anchor`。过程洞察的 `candle_id` 同时表示“洞察属于哪根 K 线”和“播放到哪根 K 线时揭示”。分析器基于该 K 线处理完成后的数据快照生成洞察，前端也在这根 K 线上绘制 Marker。

## 10. Runner Package

Runner Package 使用一个“请求即等待、完成即下载”的接口，前端不创建 Package、不轮询状态，也不管理 Package ID。

### 10.1 `POST /runner-packages/download`

请求：

```json
{
  "strategy_node_id": "01K_NODE",
  "source_replay_id": "01K_REPLAY",
  "platform": "macos",
  "architecture": "arm64"
}
```

服务端校验 Strategy Node 归属后，使用以下内容计算稳定 Build Key：

```text
strategy_node_id + platform + architecture + runner_version + package_schema_version
```

处理逻辑：

```text
已有 ready 且未过期文件
  → 直接流式返回

已有 queued/building 任务
  → 当前 HTTP 请求加入同一任务的等待者
  → 构建完成后流式返回同一文件

不存在、已失败或已过期
  → 原子领取 Build Key
  → 只提交一个后台构建任务
  → 当前 HTTP 请求等待完成
  → 流式返回文件
```

响应 HTTP `200`，直接返回 ZIP：

```http
HTTP/1.1 200 OK
Content-Type: application/zip
Content-Disposition: attachment; filename="speakquant-runner-macos-arm64.zip"
Content-Length: 48392012
```

规则：

- 前端点击后显示本地“正在构建”状态，不发起轮询；HTTP 请求返回文件或错误后结束状态。
- API 使用 `async` 等待后台完成通知，不在 API 进程执行打包，也不阻塞 Python Worker 线程。
- 客户端刷新或中断请求不取消后台构建；下一次相同 Build Key 请求继续等待已有任务。
- 多个并发请求只允许一个构建者，其余请求共享完成通知和最终文件。
- Runner 构建必须有服务端硬超时，API Gateway/Load Balancer 的响应超时必须大于该构建超时。
- 只能使用已经形成的 Strategy Node。传 `source_replay_id` 时，它必须关联同一 Strategy Node，但不参与 Build Key 计算。
- 下载包默认模拟模式，不包含用户交易所 API Key。
- 构建失败时，在尚未开始文件响应的前提下返回标准 JSON Error Envelope 和稳定错误码 `RUNNER_PACKAGE_BUILD_FAILED`。

## 13. 状态与前端动作

### 13.1 Strategy

| 状态 | 前端文案 | 主要动作 |
| --- | --- | --- |
| `draft` | 尚未完成回测 | 继续修改、准备回测 |
| `tested` | 已验证 | 查看 Replay、继续修改、下载 Runner |
| `modified` | 存在未验证修改 | 查看差异、准备回测 |
| `restored` | 从历史恢复，尚未重新回测 | 继续修改、准备回测 |
| `running` | 正在回测 | 查看进度、按能力取消 |

### 13.2 Replay 执行

| 状态 | 前端动作 |
| --- | --- |
| `queued` | 展示等待，不虚构百分比 |
| `running` | 展示真实阶段，可请求取消 |
| `completed` | 打开 Replay Workspace |
| `failed` | 展示原因，可重试 |
| `cancelled` | 可重试 |

`waiting_confirmation` 只属于预留的 `replay_confirmation` 卡片，不属于 Replay 当前执行状态。

### 13.3 Replay 边界

- `no_trades` 是成功结果，不显示错误态。
- `quality_status=warning` 展示风险提示但允许研究。
- `quality_status=unreliable` 明确阻止确定性结论。
- 强平成交使用 `action=liquidation`，不得作为普通止损展示。
- 所有 Replay 显示历史数据范围和延迟，不出现实时行情含义。

## 14. 安全与联调约束

1. 前端不得保存或展示 Strategy Code Files。
2. 前端不得把 JWT 或 Google Credential 写入日志或埋点。
3. 所有资源接口先按当前用户过滤；对他人资源统一返回 404，避免枚举。
4. SSE 只能订阅当前用户的 Run，不提供 URL Token 方案。
5. Markdown 渲染必须做 XSS Sanitization，不执行内嵌 HTML/脚本。
6. Replay 和 Strategy 中的数值字符串由统一 Decimal Formatter 显示。
7. 删除、恢复、Replay 创建和 Runner 构建不能因网络重试重复执行。
8. 前端不得根据中文 `message` 判断逻辑，只使用 HTTP Status、`code`、`error.key` 和资源状态。
9. API 字段只做向后兼容新增；删除或改变语义必须升级 `/api/v2`。

## 15. MVP 暂不提供的接口

- 邮箱密码、忘记密码和重置密码。
- Global Strategy Assets。
- 独立 Replay Compare。
- Strategy 直接编辑、参数面板和代码下载。
- 在线实盘、交易所 API Key 保存、订单和持仓。
- Replay 修改、覆盖、恢复或重跑同一记录。
- Runner 实例状态和本地运行控制。

这些能力不应以临时字段或隐藏接口提前混入 MVP 契约。

## 16. 支付、订阅与积分

本节是当前后端实现的联调契约。下列 Path 均为**包含 `/api` 的完整路径**；不要在 Base URL 后重复拼接 `/api`。除特别声明外，响应示例均为统一 Envelope 内的 `data`，HTTP 成功状态为 `200`。

### 16.1 联调约定

| 项目 | 契约 |
| --- | --- |
| 鉴权 | `GET /api/billing/plans`、`GET /api/billing/payment-return` 公开；Webhook 使用供应商签名；本节其余接口必须携带 Bearer Token |
| 请求体 | 有 JSON 请求体的接口必须发送 `Content-Type: application/json`；字段名区分大小写，未知字段返回 `422 VALIDATION_ERROR`。取消/恢复续费、Portal 接口不需要请求体 |
| 数值 | 金额、积分、Token 数量、系数、基点和 revision 均为数值 **string**；`rank`、分页字段、Envelope `code` 是 **integer**。金额字符串不保证固定两位小数，`"10"` 与 `"10.00"` 等值；模型成本也可能返回 `"0E-12"`。积分/Token 是整数字符串，金额/成本/系数使用 Decimal 精确处理 |
| 币种 | 付款与报价统一 `"USD"`。前端不提交币种、价格、积分数或 Stripe Price ID，也不自行计算最终加购积分 |
| ID | 本地订单、订阅、报价、积分批次、流水、费用及调用记录 ID 是 ULID string；`payment_action` 内的供应商 ID 是不透明 string，可能带 `cs_`、`sub_` 等前缀，禁止按 ULID 校验 |
| 时间 | 业务日期是 UTC ISO 8601 string，通常以 `Z` 结尾；唯一当前兼容例外是 `payment_action.expires_at`，供应商封装可能返回无时区后缀的 UTC ISO 时间，应补 `Z` 后解析，不能按浏览器本地时区解释 |
| 可空与可选 | 表中 `T / null` 表示字段始终存在、值可为 null；注明“可选”的字段才允许省略。数组无数据返回 `[]`；对象无键时返回 `{}` |
| 所有权 | 只能读取本人订单、积分流水、费用记录；不存在和他人资源统一 `404 RESOURCE_NOT_FOUND` |
| 支付能力 | 当前使用 Stripe 托管 Checkout/Invoice/Portal URL。前端只处理标准 `payment_action`，不需要 Stripe SDK 或 Secret Key |

#### 幂等键与重试

本节所有**用户发起的 POST** 都必须携带 `Idempotency-Key`。建议为每次独立操作生成 UUID；去掉首尾空白后必须为非空 ASCII，最长 255 字符。Webhook 不使用此 Header。

- 支付模块的 Key 持久保存在数据库，**没有 24 小时自动失效窗口**；同一用户不能跨接口或跨参数复用一个 Key。
- 网络中断、超时、503 或重复点击产生的同一次操作，必须用**原接口、原请求体、原 Key**重试；不要用新 Key 规避未知付款结果。
- 用户明确重新发起一次购买、重新获取报价、重新打开已过期 Portal 链接时使用新 Key。先创建报价和再支付报价是两个操作，使用不同 Key。
- 同 Key 的订单创建请求返回同一订单；报价、取消/恢复、Portal 请求可能返回第一次成功的快照。展示最新状态以 `GET /api/billing/orders/{id}`、`GET /api/billing/account` 为准。
- 同 Key 的报价即使已过期也仍返回旧报价；出现 `QUOTE_STALE` 后用新 Key 重新报价，再用另一个新 Key 创建付款。不能给旧 `quote_id` 换 Key 反复支付。
- 重复订阅、降档和在途变更由服务端拒绝；前端禁用按钮只改善交互，不能替代服务端校验。

当前套餐与规则：Basic 每月 $10 / 8,000 积分，Pro 每月 $30 / 30,000 积分，Max 每月 $100 / 130,000 积分；全部按月自动续费。注册只赠送一次 3,000 积分，不按月刷新。月度积分到期不结转，注册赠送与加购积分不过期。有效订阅只能向上升级；旧订阅确实结束并由后台确认后，可重新选择套餐。展示数值以套餐接口和实际报价为准。

`PaymentAction` 所有字段都会返回：

| 字段 | JSON 类型 / 可空 | 定义 |
| --- | --- | --- |
| `payment_id` | string / 否 | 供应商 Checkout/Invoice/Portal 等动作引用，不能替代本地 order.id |
| `status` | string / 否 | 动作创建时付款状态；当前适配器常见 requires_action/processing/paid/unknown/expired/failed；以外层订单状态为准 |
| `url` | string / 是 | redirect 时的托管支付或管理页面 URL；可能为 null |
| `customer_id` | string / 是 | 供应商客户 ID |
| `subscription_id` | string / 是 | 供应商订阅 ID，不是本地 Subscription.id |
| `invoice_id` | string / 是 | 供应商账单 ID |
| `expires_at` | UTC 时间字符串 / 是 | 供应商提供的链接到期时间；无时间则 null，当前序列化可能无 Z 后缀 |

前端仅在 `action_type="redirect"` 且 `url` 非空时跳转；`none`、动作为空或 URL 为空时保留订单并查询后端状态。升级可能使用已保存银行卡直接扣款、直接返回已履约订单，不能强制假设每次都会打开 Stripe。

| payment_status | 含义 / 前端行为 |
| --- | --- |
| `created` | 本地订单已创建，尚未确认供应商创建结果，展示处理中 |
| `creating` | 正在向供应商创建付款，展示处理中 |
| `unknown` | 请求结果不确定，继续查询原订单；不要用新 key 连续重复付款 |
| `pending` | 已创建自动续费订单，待核实付款 |
| `requires_action` | 待用户付款/认证；可使用有效 payment_action.url |
| `processing` | 供应商处理中，等待后台核实 |
| `paid` | 已核实付款；仍需结合 fulfillment_status |
| `failed` | 支付失败；不视为充值成功 |
| `expired` | 付款过期或未付流程被替换关闭 |
| `canceled` | 付款已取消 |
| `partially_refunded` | 已确认部分退款 |
| `refunded` | 已确认全额退款 |
| `disputed` | 付款争议，可能有权益回收/风险缺口 |

| fulfillment_status | 含义 / 前端行为 |
| --- | --- |
| `pending` | 后台仍在核实/履约；即使 payment_status=paid 也显示处理中 |
| `fulfilled` | 已完成积分及订阅权益更新；payment_status=paid 时展示支付成功 |
| `superseded` | 已付款但账单对应的旧权益已被后续周期/升级/终止取代，不再发放旧额度；不显示为本次新充值到账 |
| `closed` | 未付款流程已终止，无权益发放 |

退款后的订单通常保留 `fulfillment_status=fulfilled`；退款、争议以 `payment_status` 和 `refunded_amount_usd` 优先展示，并刷新余额和风险状态。

| POST `/api/billing/subscription/upgrade` | `{"quote_id":"01M4T000000000000000000004"}`；同上述 quote_id 约束 | kind=upgrade 的 BillingOrder | 立即收目标套餐全价，不抵扣旧订阅费用；确认付款成功才使目标权益生效。未付升级不先作废旧额度 |
| POST `/api/billing/subscription/cancel` | 无 Body、无参数 | `{"subscription": Subscription}` | 只将 cancel_at_period_end=true，当前已付周期继续有效；没有可管理订阅404；变更处理中409 |
| POST `/api/billing/subscription/resume` | 无 Body、无参数 | `{"subscription": Subscription}` | 撤销周期末取消，使 cancel_at_period_end=false；只管理尚未结束且仍关联的订阅，已经结束需重新订阅；无可管理订阅404；变更处理中409 |
| POST `/api/billing/portal-sessions` | 无 Body、无参数 | `{"payment_action": PaymentAction}` | 已关联订阅且有供应商客户；无账单管理账户404；配置异常503。用于银行卡/账单/期末取消，禁止 Portal 直接切换套餐 |

取消/恢复响应的 `subscription` 字段始终存在且非 null，值为 16.2 的完整 Subscription；Portal 响应的 `payment_action` 字段始终存在且非 null，值为完整 PaymentAction。

无 Body 的三个接口不解析请求 Body，前端不传 Body 即可。创建付款可能自动即时扣款并返回 paid/fulfilled；应先检查订单成功状态，再决定是否跳转 URL。网络超时或 HTTP503 时沿用原 key 重试原请求，或查询已获得的 order.id，不把“暂未收到成功响应”当成“未发生付款”。

**加购金额校验：**格式错误、非正数、NaN/Infinity 或超过两位小数返回 HTTP `422` / `code=42200` / `VALIDATION_ERROR`；低于 $5 返回 HTTP `400` / `code=40945` / `BILLING_PAYMENT_MISMATCH`。没有业务最大金额，但金额换算后的美分值和当前钱包账面余额加本次到账积分均不得超过 uint64 表示范围（`18446744073709551615`），单次到账积分不得超过账本 signed64 正数范围（`9223372036854775807`）。超出这些技术表示范围返回 HTTP `400` / `code=40945` / `BILLING_PAYMENT_MISMATCH`，提示“加购金额超出系统可处理范围”。这些边界不作为 `topup_max_usd`，前端无需据此设置产品最大金额；第三方支付通道仍可能拒绝某些金额，服务端不保证任意自定义金额均可完成收款。

加购积分为 `floor(amount_cents × monthly_credits × 10000 / (monthly_price_cents × (10000 + markup_bps)))`；前端以报价返回的 `credits` 为准。报价没有锁定/预占钱包积分。

### 16.4 查询订单与支付回跳

#### GET `/api/billing/orders`

需 Bearer。Query：`page` integer 默认1、最小1；`size` integer 默认20、范围1～100。没有 kind/status/include_hidden 筛选参数。默认隐藏被用户新付款替换的未付款订单，按 created_at DESC、id DESC 排序。

```json
{
  "items": [],
  "page": 1,
  "size": 20,
  "total": 0,
  "total_pages": 0
}
```

`items` 为 BillingOrder[]；其余四项 integer，不可空；`total` 为该用户可见订单总数，`total_pages` 为向上取整页数，无订单时0。

#### GET `/api/billing/orders/{order_id}`

需 Bearer。Path `order_id` string 必填，本地订单 ID，无 Body/Query。返回 BillingOrder；资源不存在或归属非本人404。被替换而从列表隐藏的订单仍可凭本人已知 ID 查询。此接口读取本地权威状态，不在每次 GET 时请求 Stripe。

#### GET `/api/billing/payment-return`

公开的后端跳转落点，不要求 Bearer，不返回私有账务。Query `order_id` string 必填（不校验 ULID 或存在性），`cancelled` boolean 可选默认 false，建议传 `true/false`；无 Body。返回：

```json
{
  "order_id":"01M4T000000000000000000001",
  "cancelled":false,
  "message":"请登录后查询订单状态，支付结果以后台核实为准。"
}
```

三字段均不可空，`order_id` 原样返回，接口不验证订单是否存在。`cancelled=true` 是兼容的导航提示，不会取消付款或把订单标成 canceled；当前产品的取消跳转直接返回 Pricing，不经过本接口，也不要求携带取消或订单参数。

Checkout 支付成功使用前端 `/billing/payment-return?order_id={order_id}` 作为桥接页：立即返回前端在支付前保存的发起页，由发起页查询订单并刷新权益。Checkout 取消使用固定 `/pricing` 地址，直接返回 Pricing。前端不向创建付款接口传 `return_url`、来源路径或其他跳转字段；来源仅在前端本地保存。两条 Stripe 跳转 URL 均由服务端部署配置决定，生产配置示例：

```dotenv
BILLING_SUCCESS_URL=https://speakquant.com/billing/payment-return?order_id={order_id}
BILLING_CANCEL_URL=https://speakquant.com/pricing
```

后端代码的默认成功地址仍是本接口，作为未配置前端时的 JSON 兜底；默认取消地址为 `http://localhost:6002/pricing`。Portal 返回地址另由 `BILLING_PORTAL_RETURN_URL` 配置。修改配置并重启 API 后，只影响新创建的 Checkout Session；已经创建的 Session 保留原来的成功/取消链接，同 Key 恢复旧订单也不会刷新这些链接。

### 16.5 `GET /api/credits/balance`

需 Bearer，无 Query/Body，无需幂等 Key。

返回 `data`：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `available_credits` | string | 扣除调用预占后，目前可用于新调用的积分 |
| `by_kind` | object<string,string> | 各积分来源的可用积分；动态键，不保证四个键均存在；可能含值 `"0"` 的历史来源 |
| `grants` | array<object> | `remaining_credits > 0` 的积分批次，非完整批次历史 |
| `grants[].id` | string | 积分批次 ID，与流水 `grant_id` 对应 |
| `grants[].kind` | string | `signup` 注册赠送 / `monthly` 月订阅 / `topup` 加购 / `compensation` 运营补偿 |
| `grants[].status` | string | `active` / `expired` / `superseded` / `revoked` |
| `grants[].available_credits` | string | 该批次未被预占的余额 |
| `grants[].expires_at` | string / null | 月度批次通常为订阅周期结束；注册、加购、补偿通常 null |

批次状态：`active` 有效；`expired` 到期；`superseded` 已由升级覆盖；`revoked` 全额退款/争议撤销。失效批次尚有调用预占时仍可能出现在 `grants`，其可用额为 0；预占释放后移除。批次按到期时间优先、永久批次靠后，然后创建时间/ID 排序，与扣减优先级一致。

```json
{
  "available_credits": "10400",
  "by_kind": {
    "monthly": "7400",
    "signup": "3000"
  },
  "grants": [
    {
      "id": "01M4T000000000000000000101",
      "kind": "monthly",
      "status": "active",
      "available_credits": "7400",
      "expires_at": "2026-11-13T10:00:00Z"
    },
    {
      "id": "01M4T000000000000000000102",
      "kind": "signup",
      "status": "active",
      "available_credits": "3000",
      "expires_at": null
    }
  ]
}
```

此 GET 会补建积分账户、只发放一次注册赠送，并清理已到期额度，因此可能新增账务流水。前端展示 `available_credits`，按需使用 `by_kind` 和 `grants` 展示来源与到期时间。余额大于 0 也不能保证足够启动下一次调用，因为调用前会检查该请求的费用上界。

### 16.6 `GET /api/credits/ledger`

需 Bearer，无 Body，无需幂等 Key。

查询参数：`page:integer`，默认 1、最小 1；`size:integer`，默认 20、范围 1–100。当前无 action、Run、charge、日期等筛选参数，也不提供 `include_internal` 开关。

本接口仅返回 `credits_delta != 0` 的实际积分增减。服务端在 SQL 查询中先按用户及该条件过滤，再按 `created_at DESC,id DESC` 排序、分页；`total` 与 `total_pages` 使用相同筛选条件，不是全部内部账本记录数。`reserve`、普通 `release`、零扣减 `consume`、仅改变风险缺口而余额不变等零积分记录仍保存在内部账本，不在此接口返回。`release_expired` 等造成实际余额减少的记录继续返回。

`data={items:array,page:integer,size:integer,total:integer,total_pages:integer}`；`total` 为该用户符合上述条件的流水总数，空记录 `total_pages=0`。字段保持兼容，包括预占相关字段，不代表接口返回预占过程记录。

| `items[]` 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | string | 流水 ID，前端列表唯一键 |
| `grant_id` | string | 涉及的积分批次 ID |
| `charge_id` | string / null | 任务计费 ID；实际扣减/失效预占回收通常非空，发放/过期/升级覆盖/退款通常 null |
| `attempt_key` | string / null | 一次真实 LLM 请求（含重试）的账务关联键；不要解析其格式 |
| `action` | string | 前端显示类型；积分入账按来源细分，见下表，不新增独立来源字段 |
| `credits_delta` | string | 本次账面余额增量，可正/负，保证不为 `"0"` |
| `reserved_delta` | string | 本次预占总额增量，可负/零 |
| `balance_after` | string | 该条操作后的账户账面余额 |
| `reserved_after` | string | 该条操作后的账户预占余额 |
| `metadata` | object | 附加信息，通常 `{}`；目前撤销/恢复填充下列已定义键，见下 |
| `created_at` | string | 流水时间 |

当前公开返回的 `action` 与前端中英文名称映射：

| 值 | 中文名称 | 英文名称 | 含义与增量 |
| --- | --- | --- | --- |
| `signup_bonus` | 新用户注册奖励 | New user registration bonus | 注册赠送入账，`credits_delta > 0` |
| `topup` | 积分加购 | Credit top-up | 单独加购积分入账，`credits_delta > 0` |
| `subscription_basic` | 订阅 Basic 套餐 | Basic subscription | Basic 月度积分入账，含首订/续费发放，`credits_delta > 0` |
| `subscription_pro` | 订阅 Pro 套餐 | Pro subscription | Pro 月度积分入账，含首订/续费/升级发放，`credits_delta > 0` |
| `subscription_max` | 订阅 Max 套餐 | Max subscription | Max 月度积分入账，含首订/续费/升级发放，`credits_delta > 0` |
| `compensation` | 积分补偿 | Credit compensation | 运营补偿积分入账，`credits_delta > 0` |
| `grant` | 积分发放 | Credits granted | 无法识别来源或缺少历史套餐信息的入账兜底，`credits_delta > 0` |
| `consume` | 积分消耗 | Credits used | 保持原名称及语义；实际费用扣减，`credits_delta < 0`、`reserved_delta < 0` |
| `release_expired` | 过期预占回收 | Expired reservation removed | 预占来源已到期、被覆盖或撤销，未使用部分无法回到可用额，两种 delta 均为负 |
| `expired` | 积分到期 | Credits expired | 月度到期回收未预占余额，`credits_delta < 0` |
| `superseded` | 套餐升级回收 | Credits replaced on upgrade | 升级覆盖回收旧月度未预占余额，`credits_delta < 0` |
| `revoke` | 权益撤销 | Credits revoked | 退款/争议等回收未使用权益，`credits_delta < 0`；仅风险缺口变化的零记录不返回 |
| `restore` | 权益恢复 | Credits restored | 争议胜诉等恢复原批次仍有效权益，`credits_delta > 0`；不会复活已到期/被覆盖额度，仅减少风险缺口的零记录不返回 |

仅内部 `CreditLedger.action=grant` 在公开响应中按原积分批次来源转换；内部账本仍保存 `grant`，不修改历史记录、不新增字段或 Migration。订阅套餐优先取该批次关联订单的历史 `plan_code`，缺少订单套餐信息时回退原 `CreditGrant.metadata.plan_code`，仍缺失或不能识别 `basic/pro/max` 时返回 `grant`；不读取当前订阅套餐，因此升级不会改变旧流水名称。已用完的批次仍参与来源查询，不依赖 `balance.grants` 是否包含该批次。`consume` 及其他原动作值保持不变，前端按 `action` 映射名称，无需解析 metadata 或查询当前订阅。

`metadata` 当前键（仅 `revoke/restore`；其他 action 为 `{}`）：

| 键 | 类型 | 含义 |
| --- | --- | --- |
| `cumulative_revoked` | string | 该批次本次操作后累计被撤销的积分权益；不是本条扣减额 |
| `risk_debt_delta` | string | 本次风险缺口增量，可正/负/零 |
| `original_batch_status` | string | 仅 `restore`：恢复时原批次底层状态，值同批次状态枚举 |

```json
{
  "items": [
    {
      "id": "01M4T000000000000000000104",
      "grant_id": "01M4T000000000000000000101",
      "charge_id": "01M4T000000000000000000105",
      "attempt_key": "attempt-1",
      "action": "consume",
      "credits_delta": "-500",
      "reserved_delta": "-500",
      "balance_after": "10500",
      "reserved_after": "100",
      "metadata": {},
      "created_at": "2026-10-13T10:01:00Z"
    }
  ],
  "page": 1,
  "size": 20,
  "total": 1,
  "total_pages": 1

```

返回记录仍是批次级流水，不按调用或 Run 聚合；同一真实调用跨多个批次扣减时仍有多条 `consume`，流水条数不是调用次数。只将 `consume` 作为模型消费，`release_expired` 等属于额度回收。过滤和入账名称映射只改变查询展示，不修改预占、实际扣费、积分取整或内部账本。`action` 已能区分注册奖励、各档订阅、积分加购及补偿；来源不完整的历史入账显示通用 `grant`。接口不另返回 `grant_kind/plan_code`、订单 ID、Run ID 或调用目的，不提供订单跳转或首订/续费/升级的独立类型细分。

### 16.7 `GET /api/credits/charges/{charge_id}`

需 Bearer。Path `charge_id` 必填 string（本地费用 ULID），无 Query/Body，无需幂等 Key。`charge_id` 为计费记录 ID，不是 Run ID。只允许查询当前用户记录，不存在或属于他人返回 HTTP 404 / `code=40400` / `error.key=RESOURCE_NOT_FOUND` / `message="费用记录不存在"`。

| `data` 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | string | charge_id |
| `run_id` | string / null | 对应 Agent Run ID；独立账务调用可 null |
| `status` | string | `open` 调用中 / `pending` 存在预占或未知费用待核实 / `settled` 已完成结算 |
| `coefficient` | string | 本 Run 冻结的扣分系数，如 `"2.500000"` |
| `credits_per_usd` | string | 每 1 美元标价对应积分，如 `"1000"` |
| `pricing_version` | string | 任务计费规则版本；当前 `"v1"`，按不透明版本标识处理 |
| `total_cost_usd` | string | 已成功核实并结算的 LLM 采购成本合计；pending 时不包含未知成本 |
| `charged_credits` | string | 已实际扣减积分；冻结额不计入 |
| `created_at` | string | 计费记录建立时间 |
| `finalized_at` | string / null | 执行结束时首次发起费用收尾的时间；非空不等于全部费用 settled |
| `attempts` | array<object> | 一次真实外部请求一项（重试单独计）；创建时间/ID 正序；可为空 |

`attempts[]`：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | string | attempt ID |
| `attempt_key` | string | 与流水关联的幂等键 |
| `purpose` | string / null | 当前计费集成使用 `main` / `code` / `title` / `memory`；底层允许其他值，兼容未知值 |
| `status` | string | `reserved` / `settled` / `released` / `unknown` / `waived` |
| `budget_credits` | string | 该请求预占上界，非最终消费 |
| `settled_credits` | string | 该请求已扣减积分 |
| `cost_usd` | string / null | 核实采购成本；未结算/已释放/豁免时可能为 null，不能将 null 当 0 |
| `provider_request_id` | string / null | 供应商请求 ID，可能缺失 |
| `deadline_at` | string / null | 调用超时/恢复判断截止时间；到期不代表免费或已自动释放 |
| `settled_at` | string / null | 结算/释放/豁免时间 |
| `resolution_reason` | string / null | 核查/释放说明，非固定枚举；例如 `provider_not_billed`、人工核查原因、`verified_cost_exceeds_reserved_budget; review required` |

状态说明：`reserved` 预占中；`settled` 已扣实际费用；`released` 确认未收费后退回预占；`unknown` 费用待核实且继续冻结；`waived` 人工核查/豁免后释放。费用状态独立于 Run 执行状态，Run failed/cancelled 也可能有已消费或 pending 费用。

| --- | --- | --- |
| `provider` | string / null | LLM 供应商标识，当前支持 `easyrouter` / `openai_compatible` / `fake`，按不透明字符串处理 |

| `output_tokens` | string | 输出 Token 数 |

| `cache_write_tokens` | string | 缓存写入 Token 数 |

| `cost_source` | string / null | 当前写入 `provider` 供应商响应费用 / `provider_billing_log` EasyRouter账单核实 / `price_snapshot` 完整用量乘费率快照 / `fake` 测试零成本 / `provider_rejected` 确认未收费；未知成本可 null |

### 16.8 积分不足与模型费用异常通知

发送消息 HTTP 接口先创建异步 Run，通常成功返回后才做 LLM 预占；不要只依赖发送消息返回 HTTP 402 判断余额不足。每次发起真实 LLM 调用前检查可用积分能否覆盖请求费用上界，不足则不发起此次外部调用，Run 标记 failed。

计费错误使用发起新会话/消息请求的界面语言（`Accept-Language → user.locale → zh-CN`），不从对话文本推断。没有已生成正文时还会保存一条同语言的普通 Assistant 失败兜底消息；已有正文保留，错误原因通过 Run 错误字段反馈。系统提示本身不产生 LLM 调用或费用，历史正文及错误不追溯翻译。

监听 GET `/api/agent-runs/{run_id}/events` 的 `run.finished` SSE 事件；SSE 不使用 API Envelope，`data` 的 JSON 为（以下示例的发起请求语言为 `zh-CN`）：

```text
event: run.finished
data: {"run_id":"01M4T000000000000000000107","conversation_id":"01M4T000000000000000000108","occurred_at":"2026-10-13T10:01:01Z","payload":{"status":"failed","error":{"key":"CREDITS_INSUFFICIENT","message":"积分余额不足，请升级套餐或加购积分"}}}
```

前端按 `payload.error.key` 判断，不匹配中文文案。`CREDITS_INSUFFICIENT` 时保留已有回复并停止加载：有效订阅用户可升级/加购，无有效订阅用户进入套餐购买；到账后由用户重新发起任务，不自动重发原消息。`run.finished.payload.status` 的终态值为 `completed / waiting_user / failed / cancelled`，`error` 成功/取消/等待用户时为 null，失败为 `{key:string|null,message:string|null}`。相关错误：`CREDITS_INSUFFICIENT` 积分不足；`CREDITS_RISK_BLOCKED` 风险缺口/账户受限；`BILLING_RECONCILIATION_PENDING` 费用待核实；`LLM_PRICE_NOT_CONFIGURED` 模型费率未核实。最后两者不应提示用户充值就能解决。

重新连接 SSE 会先收到 `run.snapshot`，`payload={run:{id,status,error?},active_tools:array,messages:array}`；运行中的在线快照可能不带 `run.error`，MySQL 恢复快照会带该字段（非失败为 null）。其中 run.status 可为 `queued/running/completed/waiting_user/failed/cancelled`；已终止 Run 会继续返回 `run.finished` 后结束连接，终态由 MySQL 恢复。GET `/api/agent-runs/{run_id}` 同样以成功 Envelope 返回 `data={id,conversation_id,status,error,started_at,finished_at,stream_url}`，`started_at/finished_at:string|null`；error 为 null 或 `{key:string,message:string|null}`。即便 Run 业务执行失败，此 GET 仍是 HTTP 200 / code 0，错误在 data.error。

收到 Run 结束/余额不足后刷新 balance；账务 pending 时后续可刷新 charge/balance，避免把预占当永久扣费。仅 title/Memory 辅助调用余额不足时会跳过（标题本地回退、Memory 保留），不会把已完成的主答复改成失败；主流程和 Code 调用余额不足会停止 Run。

当前不存在积分余额变动专用推送、支付结果 SSE、后端返回的 next_call_required_credits 或积分不足所差额度字段；前端需要在任务结束、支付履约完成、页面重新激活等时机主动 GET balance。已有输出保留，已经成功结算的调用不会因后续积分不足或 Run failed 自动退款。

### 16.9 前端支付与恢复流程

#### 套餐页初始化与按钮

进入套餐页并行读取 `GET /api/billing/plans`、`GET /api/billing/account`、`GET /api/credits/balance`。未登录时只能读取公开套餐，购买前先登录。

| 账户情况 | 前端行为 |
| --- | --- |
| `subscription=null` 且无在途变更 | 三档均可通过首次订阅接口购买 |
| 有有效订阅 | 当前档显示“当前套餐”；更低档禁用；更高档先调用升级预览，再确认全价覆盖规则 |
| `topup_eligible=true` | 开放金额输入与加购报价。若为 false，不发起加购 |
| `cancel_at_period_end=true` 且仍在有效期 | 显示“已取消自动续费，有效至 current_period_end”，允许恢复续费；不当作立即失效 |
| 有在途订阅变更 | 暂停新的订阅变更/加购动作，恢复已知订单或刷新账户等待结果 |
| `status=past_due/unpaid/paused` 或周期已结束 | 显示实际状态，进入账单管理处理；不要仅凭 `auto_renew=true` 判断可用。服务端确认旧订阅终止、账户返回 `subscription=null` 后才重新购买 |

`account.pending_order_id` 当前是**在途操作标识**：订阅/升级时是订单 ID，取消/恢复续费处理中可能是操作记录 ID。优先使用本次创建接口返回的 `Order.id` 轮询；仅从账户恢复时可尝试查单，若该 ID 返回 404 则刷新账户，不能据此宣称付款丢失。加购在途订单不写入该字段，须用保留的订单 ID 或订单列表恢复。

#### 发起付款、返回与到账

1. 在请求发出前保留本次操作的接口、请求体和 Key。拿到订单后在前端本地保留 `Order.id` 和发起页地址，不依赖支付页面仍然打开；这些来源信息不传给后端创建付款接口。
2. 先判断当前订单 `payment_status/fulfillment_status`。已经 `paid + fulfilled` 时直接刷新账户和余额；不要因旧 `payment_action` 仍有 URL 再次打开付款。
3. 需用户操作且 `payment_action.action_type="redirect"`、`url` 非 null 时打开该 URL。升级可能使用已有银行卡立即扣款，返回 `action_type="none"`，无需跳转。`unknown/processing` 且无 URL 时显示处理中并查单。
4. Checkout 成功支付经过前端 `/billing/payment-return?order_id=...` 桥接页后立即返回已保存的发起页，不在桥接页等待履约；Checkout 取消直接回固定 `/pricing`，无取消中间页。原发起页可以每 1～2 秒调用 `GET /api/billing/orders/{id}`，重新获得焦点或返回时立即查询；长时间未确定时降低频率，保留“处理中”与查询入口。这个频率是前端建议，不是后端延迟或到账 SLA；后台收到回调即处理。当前没有支付结果专用 SSE/WebSocket。
5. 以 `paid + fulfilled` 作为本次权益已生效的判据，然后刷新 `GET /api/billing/account`、`GET /api/credits/balance` 和订单列表；`paid + pending` 仍显示“付款已确认，权益处理中”。`paid + superseded` 表示付款被核实但历史权益未重发，停止等待并刷新账户展示当前权益。
6. `failed/expired/canceled` 或 `fulfillment_status=closed` 时结束自动等待，展示未完成，可重新购买；`refunded/partially_refunded/disputed` 时展示对应售后状态并刷新余额，不把历史 `fulfilled` 当成新的到账。
7. 网络断开或 HTTP 503 时保留原 Key；已知订单 ID 则先查单，未知则用原 POST + 原参数 + 原 Key 恢复。HTTP 200 仅说明接口请求成功，不等于已经收款。

GET 查单只读取本地权威账务，不会每次触发供应商查询。Stripe 回调核实并即时履约，失败由 Stripe 重试与账务 Worker 补偿、对账。前端不能调用 Webhook，不能根据跳转参数、供应商 URL 或浏览器支付截图自行确认成功。

#### 用户退出支付后再次购买

用户关闭/退出支付页面不修改订单。首次订阅或加购明确再次购买时使用新操作 Key；加购需要重新报价并使用新的付款 Key。后台先向供应商关闭原未付流程：

- 确认原流程未收款且已关闭：原订单变为 `expired + closed`，从订单列表隐藏，再创建新订单；已知旧订单 ID 仍可查。
- 原流程已收款：后台先恢复履约，返回 `SUBSCRIPTION_ALREADY_EXISTS`，前端刷新账户与原订单。
- 原流程仍处理中或状态不确定：返回 `BILLING_RECONCILIATION_PENDING`，保留原付款并继续恢复，不能把它当作已作废。

未付款升级有单独限制：在途升级会阻止新的升级预览，返回 `SUBSCRIPTION_UPGRADE_IN_PROGRESS`；原升级报价也已被消费。此时通过原订单继续付款，或用原升级 POST + 原 `quote_id` + 原 Key 恢复，不能先重新报价、再用新 Key 替换升级。待原变更履约或后台确认关闭/过期、pending 清除后，再获取新报价。当前没有用户主动关闭未付款升级的 HTTP 接口。

不能在付款结果未知时反复生成新 Key；该机制用于用户明确重新购买，不用于网络重试。

### 16.10 错误与前端处理

HTTP 错误使用第 2.4 节 Envelope，`data` 通常为 null，业务逻辑识别 `error.key`，不匹配中文文案。以下 `code` 是 JSON integer；同一个业务码可能对应不同 HTTP 状态。

| HTTP | code | error.key | 场景与处理 |
| --- | --- | --- | --- |
| 400 | 40001 | `IDEMPOTENCY_KEY_REQUIRED` | Key 缺失或为空；补齐本次操作 Key |
| 422 | 42200 | `VALIDATION_ERROR` | 非法套餐/报价 ID/金额、未知请求字段、Header 超长、分页越界；根据 `error.fields.errors` 修正输入 |
| 409 | 40946 | `IDEMPOTENCY_CONFLICT` | 非 ASCII Key，或同用户同 Key 换接口/参数；网络重试恢复原参数，真正新操作才换 Key |
| 404 | 40400 | `RESOURCE_NOT_FOUND` | 订单/费用不存在或不属于本人；或没有可取消/恢复/管理的订阅账户 |
| 403 | 40340 | `TOPUP_NOT_ELIGIBLE` | 没有有效付费订阅、状态非 active 或已到期；加购及升级都可能返回此 Key，刷新账户 |
| 409 | 40940 | `SUBSCRIPTION_ALREADY_EXISTS` | 已订阅、重复选择当前档、已有订阅流程，或替换时发现原单已支付；刷新账户与订单 |
| 409 | 40941 | `SUBSCRIPTION_DOWNGRADE_NOT_ALLOWED` | 有效订阅不能降档；重新选择更高套餐 |
| 409 | 40942 | `SUBSCRIPTION_UPGRADE_IN_PROGRESS` | 有待核实的订阅变更，包括取消/恢复；先恢复在途操作 |
| 409 | 40943 | `QUOTE_STALE` | 报价不存在/他人报价/类型不符/过期/已使用，或订阅 ID、revision 已变化；重新报价与确认，不能复用旧报价 |
| 409 或 503 | 40960 | `BILLING_RECONCILIATION_PENDING` | 付款结果、关闭原付款、续费开关或模型费用待核实；保留原 Key 与订单，不盲目重付。模型场景通过 Run 的 SSE/HTTP 错误传达 |
| 400、409 或 503 | 40945 | `BILLING_PAYMENT_MISMATCH` | 低于最低加购金额，或金额/到账积分/钱包合计超出各自数据库技术表示范围时为 400；核验冲突是 409；供应商创建付款确定性失败映射为 503。技术边界不是业务充值上限，详见 16.3。停止当前动作并刷新已有订单，勿因 HTTP 503 就自动换 Key |
| 503 | 50340 | `BILLING_NOT_CONFIGURED` | 收款绑定、供应商配置或 Portal 不可用；提示稍后重试/联系支持，不让用户在前端输入密钥 |
| 402 | 40260 | `CREDITS_INSUFFICIENT` | LLM 调用所需预占超过可用积分；Agent 路径通常通过 SSE/Run 错误反馈，详见积分不足契约 |
| 402 | 40261 | `CREDITS_RISK_BLOCKED` | 有退款风险缺口或账户被限制；提示联系支持，普通加购不会自动清除风险状态 |
| 409 | 40961 | `BILLING_ATTEMPT_ALREADY_PROCESSED` | 内部模型费用调用已结束，不能再次结算/发起；刷新账务，不自动重跑 |
| 409 | 40962 | `BILLING_ATTEMPT_CONFLICT` | 内部调用标识或结算参数冲突；停止重试并保留原任务 |
| 409 | 40963 | `BILLING_SOURCE_CONFLICT` | 积分来源幂等参数冲突；停止重试并联系支持 |

`BILLING_ATTEMPT_STILL_RUNNING`（409 / 40964）仅用于内部人工费用豁免流程，没有用户 HTTP 操作入口。通用 401、500 错误沿用第 2.4 节。充值、退款和供应商异常的详细内部原因不作为前端判断依据。

### 16.11 供应商回调（服务端接口）

`POST /api/billing/webhooks/stripe` 仅供 Stripe 调用。请求为原始 Stripe JSON body（不得重新序列化后验签），Header `Stripe-Signature` 必填；不使用 Bearer Token 或用户幂等 Key。原始 body 最大 2,097,152 bytes，超过返回 HTTP 413 / code 40945。未知供应商返回 404；验签或解析失败返回 400 / code 40945。

| 响应 data 字段 | 类型 | 说明 |
| --- | --- | --- |
| `received` | boolean | 已接收并持久化，成功响应固定 true |
| `processed` | boolean | true 表示该事件已完成处理；false 可表示已有执行者、租约被接管或事件未匹配本地用户，不能当作付款到账证明 |
| `duplicate` | boolean（可选） | 仅重复事件出现，值为 true；新事件不返回此字段 |

首次正常处理示例：`{"received":true,"processed":true}`；已处理重复事件为 `{"received":true,"processed":true,"duplicate":true}`；正在被其他执行者处理的重复事件为 `{"received":true,"processed":false,"duplicate":true}`。

验签后持久保存事件并立即核实供应商、金额、币种、归属及周期，在当前请求内完成账务事务；正常流程不等待 Worker 轮询。处理失败返回 HTTP 503 / code 40960 / `BILLING_RECONCILIATION_PENDING`，已保存事件保留待重试，财务事务不部分生效。此接口不把供应商内部回调结构暴露为前端协议，前端始终通过本地订单和余额确认结果。
