# Trade Lab MVP 接口定义文档

> 文档版本：V1.1  
> 更新日期：2026-09-08\
> 协议：HTTPS + JSON；Agent 实时消息使用 SSE  
> API 前缀：`/api`

## 1. 文档范围

本文是 Trade Lab MVP 前后端联调契约，覆盖：

- Google 登录、邮箱验证码登录、JWT 刷新和退出。
- 用户资料和产品语言。
- Conversation History、消息历史和资产列表。
- Agent 实时 SSE、断线重连和结构化卡片事件。
- Current Strategy、Strategy History 和恢复。
- 回测条件、确认、进度、取消、失败和重试。
- Replay 指标、K 线、交易时间线、洞察和报告。
- Runner 下载包构建和下载。

Agent Loop、策略代码生成、回测引擎和 Replay 生成算法属于后续独立技术方案。本文只规定它们对前端暴露的输入、状态和输出。

## 2. 通用协议

### 2.1 环境

| 环境 | Base URL |
| --- | --- |
| 本地 | `http://127.0.0.1:6001/api` |
| 测试 | 后续由部署环境提供 |
| 生产 | 后续由部署环境提供，必须 HTTPS |

健康检查不带版本前缀：`GET /health`。

### 2.2 请求 Header

| Header | 必填 | 说明 |
| --- | --- | --- |
| `Authorization: Bearer <access_token>` | 受保护接口必填 | JWT Access Token |
| `Content-Type: application/json` | JSON 请求必填 | UTF-8 JSON |
| `Accept: application/json` | HTTP 接口建议 | 响应格式 |
| `Accept: text/event-stream` | SSE 必填 | SSE 响应格式 |
| `X-Request-ID` | 否 | 前端链路 ID；不传则服务端生成 |
| `Idempotency-Key` | 创建资源/触发任务时必填 | 建议 UUID，同一用户下 24 小时内唯一 |
| `Accept-Language` | 否 | 仅用于系统界面文案，不控制 Agent 回复语言 |

除登录、验证码、Refresh、公开配置和 Health 外，其余接口统一使用：

```http
Authorization: Bearer eyJ...
```

### 2.3 成功响应

所有非 SSE 接口使用统一 Envelope：

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "request_id": "req_01K..."
}
```

- `code=0` 表示成功。
- HTTP Status 表达协议结果；`code` 表达稳定业务结果。
- 删除成功返回 HTTP `200` 和 `data.deleted=true`，不使用无响应体的 `204`。
- 除明确展示完整 Envelope 的示例外，后续接口示例均表示 Envelope 内的 `data` 字段。

### 2.4 错误响应

```json
{
  "code": 40902,
  "message": "Strategy 已发生变化，请重新确认",
  "data": null,
  "error": {
    "key": "BACKTEST_CONFIRMATION_STALE",
    "fields": {
      "expected_revision": 4,
      "actual_revision": 5
    }
  },
  "request_id": "req_01K..."
}
```

通用错误：

| HTTP | code | key | 场景 |
| --- | --- | --- | --- |
| 400 | `40000` | `BAD_REQUEST` | 请求格式或业务参数错误 |
| 400 | `40001` | `IDEMPOTENCY_KEY_REQUIRED` | 缺少幂等 Key |
| 401 | `40100` | `AUTH_REQUIRED` | 未提供 Token |
| 401 | `40101` | `AUTH_TOKEN_INVALID` | Access Token 非法 |
| 401 | `40102` | `AUTH_TOKEN_EXPIRED` | Access Token 过期 |
| 401 | `40103` | `AUTH_SESSION_REVOKED` | Session 已撤销 |
| 401 | `40104` | `REFRESH_TOKEN_INVALID` | Refresh Cookie 缺失或无效 |
| 403 | `40300` | `FORBIDDEN` | 无权访问资源 |
| 404 | `40400` | `RESOURCE_NOT_FOUND` | 资源不存在或不属于当前用户 |
| 409 | `40900` | `RESOURCE_STATE_CONFLICT` | 当前状态不允许操作 |
| 409 | `40901` | `REVISION_CONFLICT` | 乐观锁 revision 不一致 |
| 409 | `40902` | `BACKTEST_CONFIRMATION_STALE` | 回测确认卡已失效 |
| 422 | `42200` | `VALIDATION_ERROR` | 字段校验失败 |
| 429 | `42900` | `RATE_LIMITED` | 频率限制 |
| 500 | `50000` | `INTERNAL_ERROR` | 未知服务端异常 |
| 503 | `50300` | `SERVICE_UNAVAILABLE` | 外部服务或执行器暂不可用 |

字段错误放在 `error.fields`，不得把第三方 SDK、SQL 或堆栈信息返回前端。

### 2.5 时间、ID 与数值

- ID 均为 26 位 ULID 字符串，前端不得转为 Number。
- 时间均为 ISO 8601 UTC，如 `2026-08-20T09:30:00.123456Z`。
- 金额、价格、数量和比率在 JSON 中统一返回字符串，避免 JavaScript 浮点误差。
- 比率为小数，例如 `"0.12340000"` 表示 `12.34%`。
- 普通业务列表使用 `page/size`；消息历史和 K 线使用各自的顺序位置参数。

### 2.6 分页

Conversation、Strategy History、Replay、Trade 等普通列表统一使用：

```http
GET /api/conversations?page=1&size=20
```

响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "items": [],
    "page": 1,
    "size": 20,
    "total": 52,
    "total_pages": 3
  },
  "request_id": "req_01K..."
}
```

- `page` 从 1 开始，默认 1。
- `size` 默认 20，最大 100。
- 数据库使用 `OFFSET (page - 1) * size LIMIT size`。
- Conversation History 变化时，不保证跨多次请求形成严格静态快照；MVP 接受列表更新造成的轻微位置变化。
- 消息历史继续使用 `before_sequence/limit`，便于向上加载。
- Replay K 线继续使用 `cursor/limit`，便于顺序读取大体量数据文件。

### 2.7 幂等与并发

- 创建 Conversation、发送消息、创建/重试 Replay 和恢复 Strategy 必须带 `Idempotency-Key`。Runner Package 按服务端 Build Key 自然幂等，不依赖前端生成幂等 Key。
- 相同用户、接口和 Key 的重试返回第一次请求的结果，不重复执行。
- Strategy 修改使用 `expected_revision` 防止旧页面覆盖；Agent 创建 Replay 时在同一事务中锁定并冻结 Current Strategy。预留兼容接口仍会比较确认卡片中的 `strategy_revision`，不要求前端单独回传版本号。
- 前端收到 `40901/40902` 后应刷新对应详情，不自动重复覆盖。

### 2.8 语言边界

- Agent 不接收或保存单独的对话语言字段，默认根据用户当前消息和上下文选择合适的回复语言。
- 系统界面、固定错误文案等非 LLM 内容的国际化独立处理，本阶段不展开具体方案。

## 3. JWT 认证

### 3.1 Token 规则

- Access Token：JWT，有效期 1 小时，通过 `Authorization` Header 发送。
- Refresh Token：随机不可读的长期 Token，不设置业务过期时间，通过 HttpOnly Cookie 保存。
- Web 前端不读取 Refresh Token，不放入 localStorage。
- Refresh Token 使用 `<session_id>.<random_secret>` 结构；Session ID 只用于定位，随机部分必须具备至少 256 bit 熵。
- Refresh 时不轮换 Refresh Token，只签发新的 Access Token。
- 正常产品流程只有用户主动退出会撤销 Session；浏览器清除 Cookie、账号删除或管理员禁用属于例外。
- JWT 签名算法生产环境使用 `RS256` 或 `EdDSA`，禁止把对称密钥交给前端。

Access Token Claims：

```json
{
  "iss": "trade-lab-api",
  "aud": "trade-lab-web",
  "sub": "01K...user_id",
  "sid": "01K...session_id",
  "type": "access",
  "iat": 1787216400,
  "exp": 1787220000,
  "jti": "01K...token_id"
}
```

Refresh Cookie：

```text
Set-Cookie: trade_refresh=<token>; HttpOnly; Secure; SameSite=Lax; Path=/api/auth; Max-Age=315360000
```

`Max-Age=315360000` 约为 10 年，用于实现产品意义上的“永久登录”；浏览器规范不存在真正无限期 Cookie，并且浏览器或用户仍可能主动清理。开发环境可关闭 `Secure`，测试和生产必须开启。

### 3.2 AuthResponse

Google 登录、邮箱验证和 Refresh 成功统一返回：

```json
{
  "access_token": "eyJ...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "user": {
    "id": "01K...",
    "email": "user@example.com",
    "display_name": "User",
    "avatar_url": null,
    "locale": "zh-CN",
    "timezone": "UTC",
    "created_at": "2026-08-20T09:00:00Z"
  }
}
```

## 4. 公开与认证接口

### 4.1 接口清单

| Method | Path | 鉴权 | 用途 |
| --- | --- | --- | --- |
| GET | `/health` | 否 | 进程健康检查 |
| GET | `/meta/quick-examples` | 否 | 首页 Quick Examples |
| GET | `/auth/google/config` | 否 | 获取 Google Client ID 和浏览器登录 nonce |
| POST | `/auth/google` | nonce Cookie + Origin | Google GIS Credential 登录，无需 Access Token |
| POST | `/auth/email/code` | 否 | 发送邮箱验证码 |
| POST | `/auth/email/verify` | 否 | 验证邮箱并登录 |
| POST | `/auth/refresh` | Cookie | 刷新 Access Token |
| POST | `/auth/logout` | 是 | 撤销当前 Session |
| GET | `/users/me` | 是 | 当前用户 |
| PATCH | `/users/me` | 是 | 更新基础设置 |

### 4.2 `GET /meta/quick-examples`

Query：`locale=zh-CN|en-US`，默认读取 `Accept-Language`。

```json
{
  "items": [
    {
      "id": "trend_following",
      "title": "趋势跟随",
      "content": "当 BTC 的 20 日均线上穿 60 日均线时做多……"
    }
  ]
}
```

最多返回 4 条。该配置可以来自代码或配置中心，MVP 不要求数据库表。

### 4.3 Google 登录

#### 4.3.1 `GET /auth/google/config`

无需登录。返回 `ApiResponse<{client_id, nonce}>`，并设置 10 分钟有效的
`trade_google_nonce` HttpOnly Cookie（Path=/api/auth/google，SameSite=Lax，非 local 环境 Secure）。
响应 `Cache-Control: no-store`。前端 fetch 必须携带 `credentials: include`，将 nonce 传入
`google.accounts.id.initialize`。重复初始化会替换当前浏览器的 challenge。
未配置 `GOOGLE_CLIENT_ID` 返回 `50300 SERVICE_UNAVAILABLE`。

无请求 Body。实际请求地址为 `GET /api/auth/google/config`，成功响应示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "client_id": "<web-client-id>.apps.googleusercontent.com",
    "nonce": "<server-generated-random-string>"
  },
  "request_id": "<request-id>"
}
```

- `client_id` 是公开的 Web 客户端标识，可提供给前端；Client Secret 不参与本流程。
- `nonce` 用于将 Google 签发的 ID Token 与当前浏览器的登录请求关联，不能省略或自行生成替代。
- Cookie 由浏览器管理，前端无需也不能读取其 HttpOnly 内容。
- nonce Cookie 的服务端签名有效期为 10 分钟。Google credential 还受自身 `exp` 限制，两者分别校验。
- 不要在每次组件 render、按钮点击或普通 API 请求前重复调用此接口；新 Cookie 会覆盖旧 challenge。


#### 4.3.2 `POST /auth/google`

前端通过 Google Identity Services 获得 Credential 后提交，服务端必须验证签名、`aud`、`iss`、`exp`、`email_verified` 和 Cookie 对应的 `nonce`。
Google 时间声明允许最多 30 秒时钟偏差；签名、受众和 nonce 仍严格校验。
只接受 JSON 回调提交，Origin 必须位于 `CORS_ORIGINS`，请求必须携带 credentials。
本接口不是 GIS HTML 自动 POST/redirect 接收端，不采用 `g_csrf_token` 表单协议。

请求：

```json
{
  "credential": "google_id_token"
}
```

请求字段：

| 字段 | 类型 | 必填 | 约束 / 说明 |
| --- | --- | --- | --- |
| `credential` | string | 是 | GIS callback 返回的 Google ID Token，长度 1～16384；不是 Google Access Token 或 OAuth code。 |
| `verification_id` | string / null | 否 | 第三方邮箱补验证时与 code 一起提交，长度 26；来自 `/api/auth/email/code`。 |
| `code` | string / null | 否 | 第三方邮箱补验证时提交，必须为 6 位数字字符串。 |

不接收额外字段，包括客户端自报的 email、sub、name、picture 或条款版本。普通登录只传 credential。

响应：`ApiResponse<AuthResponse>`（见 3.2），并设置 `trade_refresh` HttpOnly Cookie；
成功响应 `Cache-Control: no-store`，同时清除 `trade_google_nonce` Cookie。
返回的 Access Token 是 Trade Lab 自己签发的业务 Token，后续 API 使用它作为 Bearer Token。


业务规则：

- 已绑定的 Google `sub` 优先定位用户，Provider 邮箱变更不改变绑定，也不覆盖用户主邮箱。
- 首次绑定：Gmail 或 `email_verified=true` 且具有 `hd` 的 Workspace 邮箱可直接匹配并复用原用户。
- 其他第三方邮箱首次绑定（含新用户）返回 `40910 GOOGLE_EMAIL_VERIFICATION_REQUIRED`，data 为 `{email}`。
  前端调用 `/auth/email/code`，再向本接口提交原 credential 加 `verification_id`、`code`。
  服务端验证验证码所属邮箱一致、未过期且未消费，原子创建/绑定身份、消费验证码并签发 Session。
  不要先调用 `/auth/email/verify` 消费此绑定验证码。若 challenge 或 credential 过期，重新发起 GIS 登录。
- 同邮箱验证码登录复用用户并补齐 email identity；停用账号不能通过任一方式登录。
- 验签失败：`40105 GOOGLE_CREDENTIAL_INVALID`；challenge 失效：`40106 GOOGLE_LOGIN_CHALLENGE_INVALID`；
  Origin 非法：`40300 FORBIDDEN`；并发唯一约束冲突：`40911 AUTH_CONFLICT`（客户端可重试）；
  Google 公钥网络故障：`50300 SERVICE_UNAVAILABLE`。成功后清除 challenge Cookie。
- 凭据只用于本次验签，不保存或记录 Google Token；用户、身份、条款和 Session 在一个事务内提交。
- Timezone 初始为 UTC，登录后可通过用户设置接口修改。
- 登录即代表用户接受页面展示的当前服务条款和隐私政策。具体生效版本由服务端配置并写入 Consent，不接受客户端自报版本。


#### 4.3.3 第三方邮箱首次绑定

如果 Google 账户使用非 Gmail、非 Google Workspace 托管的邮箱，即便 Google 返回
`email_verified=true`，首次绑定也需要确认当前邮箱归属。服务端返回 HTTP 409：

```json
{
  "code": 40910,
  "message": "请先验证邮箱以关联 Google 账号",
  "data": {"email": "user@example.com"},
  "request_id": "<request-id>",
  "error": {
    "key": "GOOGLE_EMAIL_VERIFICATION_REQUIRED",
    "fields": {}
  }
}
```

前端按以下顺序继续，Google credential 仅临时保存在内存：

1. 使用响应 `data.email` 调用 `POST /api/auth/email/code`，获得 verification_id；根据 expires_in / resend_after 展示有效期和重发倒计时。
2. 用户输入验证码后，调用 `POST /api/auth/google`，请求如下。不要先调用普通 `/api/auth/email/verify`，否则会提前消费验证码。
3. 成功后清除内存中的 Google credential、验证码和 verification_id，使用返回的 AuthResponse 完成登录。

```json
{
  "credential": "<the-google-id-token-kept-in-memory>",
  "verification_id": "<26-character-verification-id>",
  "code": "123456"
}
```

后端根据验证过的 Google credential 确定邮箱，并校验验证码记录对应同一邮箱；
用户创建或复用、身份关联、验证码消费、Consent 和 Session 一并提交。
绑定成功后再次使用同一 Google sub 登录，无需重复邮箱补验证。

#### 4.3.4 错误与前端处理

| HTTP | code / error.key | 前端处理 |
| --- | --- | --- |
| 401 | `40105 GOOGLE_CREDENTIAL_INVALID` | 凭据无效、过期或 nonce 不匹配等；提示重新开始 Google 登录，不无限重试原 credential。 |
| 401 | `40106 GOOGLE_LOGIN_CHALLENGE_INVALID` | nonce Cookie 缺失、无效或过期；检查 credentials、主机名及 Cookie 配置，再重新初始化。 |
| 401 | `40103 AUTH_SESSION_REVOKED` | 用户已停用等，停止登录并展示账号状态提示。 |
| 403 | `40300 FORBIDDEN` | 检查请求 Origin 与后端 CORS_ORIGINS；浏览器自动设置 Origin，前端 JS 不手动伪造。 |
| 409 | `40910 GOOGLE_EMAIL_VERIFICATION_REQUIRED` | 进入 4.3.3 的邮箱补验证流程。 |
| 409 | `40911 AUTH_CONFLICT` | 并发唯一约束冲突；允许用户重试，避免并行重复提交。 |
| 400 | `40010 EMAIL_CODE_INVALID` | 验证码错误、已失效、已消费或邮箱不匹配；提示更正或重发。 |
| 400 | `40011 EMAIL_CODE_EXPIRED` | 重新发送邮箱验证码。 |
| 429 | `42901 EMAIL_CODE_ATTEMPTS_EXCEEDED` | 停止尝试当前验证码，重新申请；发送限流另按 4.4 处理。 |
| 422 | `42200 VALIDATION_ERROR` | 按字段约束修正请求；不要记录或显示 credential 内容。 |
| 503 | `50300 SERVICE_UNAVAILABLE` | 可能未配置 Client ID，或 Google 公钥验证服务不可用；保留邮箱登录入口并提示稍后重试。 |

Google 弹窗被取消、SDK 未加载或浏览器阻止登录提示时，可能没有任何后端请求。
前端需区分这些状态与后端 HTTP 错误，不把用户取消显示为账号异常。

#### 4.3.5 本地前端接入步骤

本地配置约定：

| 配置 | 当前值 / 要求 |
| --- | --- |
| 前端地址 | `http://localhost:6002` |
| 后端 API Base URL | `http://localhost:6001/api` |
| Google Cloud 项目 | `Trade Lab` / `trade-lab-507705` |
| 开发 OAuth 客户端 | `Trade Lab Web Local`，Web application 类型 |
| Google Authorized JavaScript origins | `http://localhost`、`http://localhost:6002` |
| 后端环境变量 | GOOGLE_CLIENT_ID 为上述客户端；CORS_ORIGINS 包含前端来源；本地 APP_ENV=local |

浏览器统一用 localhost 访问前端和后端。虽然后端 CORS 也允许 `http://127.0.0.1:6002`，
Google 客户端当前未配置这个来源；localhost 与 127.0.0.1 也不能混用为 Cookie 主机名。
前端 6002 与后端 6001 是跨 Origin、同 Site，因此仍需要 CORS 和 credentials: include。

接入顺序：

1. 在登录页提供真实服务条款和隐私政策链接，按产品约定展示同意提示，并保存用户登录前输入。
2. 从 Google 加载 GIS SDK，等待脚本 load 后再访问 google.accounts.id，不使用旧版 platform.js / gapi.auth2。
3. 获取一次 `/api/auth/google/config`，将 client_id、nonce 传给 initialize，渲染官方按钮。
4. 将 callback 的 credential 提交后端；成功后保存内存 Access Token 与用户状态，返回登录前的页面。
5. 若需要邮箱补验证，保留当前 challenge 和内存 credential，按 4.3.3 继续。

以下示例展示接入核心。`onAuthenticated`、`onEmailVerificationRequired`、`onError` 是前端传入的 UI / 状态处理函数；
`onEmailVerificationRequired` 收到的 credential 只能保存在内存中。示例不包含产品条款 UI 和通用 HTTP Client 的刷新逻辑。

```html
<script src="https://accounts.google.com/gsi/client" async defer></script>
<div id="google-login-button"></div>
```

```javascript
const API_BASE = 'http://localhost:6001/api';

async function authRequest(path, body, method = 'POST') {
  const response = await fetch(`${API_BASE}${path}`, {
    method,
    credentials: 'include',
    cache: 'no-store',
    headers: body === undefined ? {} : { 'Content-Type': 'application/json' },
    body: body === undefined ? undefined : JSON.stringify(body),
  });
  const result = await response.json();
  if (!response.ok || result.code !== 0) {
    throw Object.assign(new Error(result.message || '登录失败'), {
      status: response.status,
      key: result.error?.key,
      data: result.data,
    });
  }
  return result.data;
}

// 在 SDK load 完成、页面已展示条款后调用；同一次登录流程只初始化一次。
async function mountGoogleLogin({
  element, onAuthenticated, onEmailVerificationRequired, onError,
}) {
  try {
    const config = await authRequest('/auth/google/config', undefined, 'GET');
    google.accounts.id.initialize({
      client_id: config.client_id,
      nonce: config.nonce,
      auto_select: false,
      use_fedcm_for_prompt: true,
      use_fedcm_for_button: true,
      callback: async ({ credential }) => {
        try {
          const auth = await authRequest('/auth/google', { credential });
          onAuthenticated(auth); // 内存保存 auth.access_token，更新 auth.user。
        } catch (error) {
          if (error.key === 'GOOGLE_EMAIL_VERIFICATION_REQUIRED') {
            onEmailVerificationRequired({ email: error.data.email, credential });
          } else {
            onError(error);
          }
        }
      },
    });
    google.accounts.id.renderButton(element, { theme: 'outline', size: 'large' });
  } catch (error) {
    onError(error); // SDK 加载失败、配置失败和网络错误需展示可恢复提示。
  }
}

// 补验证页面：分别由“发送验证码”和“提交验证码”动作调用。
```

- React/Vue 等组件不要因重渲染重复 initialize；开发模式 effect 重入时应复用初始化 Promise，避免两个配置请求覆盖 Cookie。
- 同一页面的按钮和 One Tap 共用一次 initialize。若 challenge 过期或用户退出后重新登录，清理旧流程再获取新配置；需要时重新挂载登录页。
- Google 登录成功会清除 challenge Cookie，不能继续复用旧 credential 创建新会话。普通业务请求不需要重新执行 GIS 登录。
- 前端刷新会话使用 `POST /api/auth/refresh`，明确指定 POST 并携带 Cookie；正式产品统一由 HTTP Client 处理刷新与请求重试。
- 业务接口使用 `Authorization: Bearer <Trade Lab access_token>`。Refresh 失败按 4.6 返回登录页，保留用户输入。
- 退出使用 `POST /api/auth/logout`，携带 Access Token 和 Cookie；成功后清理内存状态并调用 `google.accounts.id.disableAutoSelect()`，不退出用户的整个 Google 账号。

### 4.6 `POST /auth/refresh`

无 JSON Body，浏览器自动携带 Refresh Cookie。服务端校验长期 Session，更新 `last_used_at`，返回新的 Access Token 和 User；Refresh Token 本身保持不变。

前端跨 Origin 开发时必须使用 `credentials: "include"`；服务端 CORS 只能允许明确的前端 Origin，不能在携带 Cookie 时使用 `*`。

若 Cookie 缺失、Token 不匹配或 Session 已撤销，返回 `40104 REFRESH_TOKEN_INVALID` 或 `40103 AUTH_SESSION_REVOKED`。前端清除内存 Access Token 并回到登录页，同时保留未提交输入到浏览器本地草稿。

前端统一刷新规则：

1. 普通业务接口收到 `40102 AUTH_TOKEN_EXPIRED` 时调用一次 Refresh。
2. Refresh 成功后替换内存中的 Access Token，并重试原请求一次。
3. 多个请求同时发现过期时复用同一个 Refresh Promise，避免并发刷新风暴。
4. 重试后仍为 401 时停止重试，进入登录页，避免死循环。

Refresh 逻辑只存在于统一 HTTP Client，不进入 Conversation、Agent、Replay 等业务代码。

### 5.6 `PATCH /conversations/{id}`

请求字段均可选，但至少提交一个字段；未修改的字段直接省略：

```json
{
  "title": "我的 BTC 趋势策略",
  "is_favorite": true,
  "status": "archived"
}
```

- `title` 是研究名称（Conversation 标题），传入字符串长度为 1～200 个字符；保存时去掉首尾空白。前端应先去掉首尾空白，再校验非空及长度。超过 200 字符返回 HTTP `422`、`code=42200`、`error.key=VALIDATION_ERROR`。
- 用户修改 title 后 `title_source=user`，后续 AI 不再自动覆盖。
- 收藏不改变“全部”列表；收藏后记录进入“收藏”列表并移出“非收藏”列表，取消收藏则相反。

成功返回 HTTP `200`，`data` 直接为更新后的 `ConversationSummary`。完整 Envelope 示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": "01K...",
    "title": "我的 BTC 趋势策略",
    "status": "archived",
    "is_favorite": true,
    "last_message_at": "2026-08-20T09:30:00Z",
    "created_at": "2026-08-20T09:00:00Z",
    "updated_at": "2026-08-20T09:35:00Z"
  },
  "request_id": "req_01K..."
}
```

返回层级约定：PATCH 从响应体的 `data` 读取最新记录；GET 详情从 `data.conversation` 读取。两者的记录字段均为 `ConversationSummary`。重命名、收藏或取消收藏成功后，前端按 `id` 使用 PATCH 返回的记录更新本地列表和当前研究标题。

### 5.8 Message

```json
{
  "id": "01K...",
  "conversation_id": "01K...",
  "agent_run_id": "01K...",
  "sequence": 12,
  "role": "assistant",
  "status": "completed",
  "content": "我先确认一个会显著影响策略的问题……",
  "cards": [],
  "created_at": "2026-08-20T09:31:00Z",
  "updated_at": "2026-08-20T09:31:04Z"

```

Message 不定义 `type=text/markdown`，内容格式由 `role` 决定：

- `role=user`：`content` 是无格式纯文本，前端必须转义后展示，不解析 Markdown。
- `role=assistant`：`content` 是 Markdown，前端按统一 Markdown 规范渲染并执行 XSS Sanitization；普通纯文本天然也是合法 Markdown。
- `cards` 始终为数组；普通消息返回空数组。同一条 Assistant 消息可以附带多张卡片，卡片不改变 `content` 的渲染格式。

### 5.9 `GET /conversations/{id}/messages`

Query：

- `before_sequence`：加载更早消息；首次不传。
- `limit`：默认 50，最大 100。

响应：

```json
{
  "items": [],
  "next_before_sequence": 100,
  "has_more": true,
  "active_run": {
    "id": "01K_RUN",
    "status": "running",
    "stream_url": "/api/agent-runs/01K_RUN/events"
  }
}
```

`items` 始终按 sequence 正序，只包含已经持久化的消息。当前实现不会把生成中的 Assistant 半成品写入 MySQL；实时文本、工具状态和卡片以 SSE Snapshot 为准。

`active_run` 可以为 `null`。Agent 消息正在编排 Replay 时优先返回前端已经连接的 `message` Run；没有活动的消息 Run 时，返回最新的 `queued/running` 确定性操作 Run。

服务端在同一数据库会话中先读取 `active_run`，再读取消息历史。Agent Finalizer 在同一事务中写入最终 Assistant Message 并结束 Run，因此这个响应只会表达两种有效状态：存在 `active_run`，前端继续连接 SSE；或者 `active_run=null`，最终消息已经可以从历史中读取。

### 5.10 `POST /conversations/{id}/messages`

Header：`Idempotency-Key` 必填。

请求：

```json
{
  "content": "为什么这里没有开仓？"
}
```

字段：

- 普通文本消息只需提交 `content`，其余字段均为特定交互场景下的可选字段。
- 回答 Clarification 时，传 `reply_to_message_id` 和非空 `structured_answers` 数组，一次提交卡片内所有必答题。每项为 `{question_id,value}` 或 `{question_id,custom_text}`，二者恰好填写一个非空字符串（最长 2000 字符）；`question_id` 必须使用卡片返回的题目 ID，不得重复。
- 批量回答时可以省略 `content`，服务端按原题顺序生成包含题目和答案的用户纯文本消息；如传入 `content`，则作为补充文字追加在回答之后。普通消息仍必须传非空 `content`（最多 20000 字符）。
- 原 `structured_answer` 单对象仅保留兼容，不可与 `structured_answers` 同传，也需要提供 `reply_to_message_id`；新接入统一使用数组，单题时数组长度为 1。
- 从 Replay 发起追问时可传 `context={replay_id,trade_id,fill_id,insight_id,timestamp}`，只提交当前交互实际关联的字段。
- 服务端必须验证 Replay 以及可选的 Trade/Fill/Insight 属于当前 Conversation。
- 请求体不包含 `client_message_id`；请求重试统一使用 Header 中的 `Idempotency-Key`，由前端公共 HTTP 层自动生成，业务页面无需处理。

整组回答请求示例：

```json
{
  "reply_to_message_id": "01K_ASSISTANT_MESSAGE",
  "structured_answers": [
    {"question_id": "01K_QUESTION_MARKET", "value": "合约"},
    {"question_id": "01K_QUESTION_TIMEFRAME", "custom_text": "15m"}
  ]
}
```

服务端验证题目属于被回复的 Assistant 消息、选项有效、自定义回答被允许，且同一卡片的必答题已全部回答。漏答、未知题目或非法选项返回 HTTP `400`、`BAD_REQUEST`；重复题目 ID、空答案、同时填写选项和自定义文本等请求格式错误返回 HTTP `422`、`VALIDATION_ERROR`。已完成的卡片再次使用新幂等 Key 提交返回 HTTP `409`、`RESOURCE_STATE_CONFLICT`；相同 Key 重试返回首次成功结果。

整组答案、原卡片的已答状态、一条 User 消息和一个新 Agent Run 在同一事务中保存；任一题校验失败，整组不保存。答案可以覆盖被回复消息内的多张澄清卡片，但每张涉及的卡片均须提交全部必答题。

响应 HTTP `202`：

```json
{
  "user_message": {
    "id": "01K...",
    "conversation_id": "01K...",
    "sequence": 37,
    "role": "user",
    "status": "completed",
    "content": "为什么这里没有开仓？",
    "cards": [],
    "created_at": "2026-08-20T09:35:00Z"
  },
  "updated_messages": [],
  "agent_run": {
    "id": "01K_RUN",
    "status": "queued",
    "stream_url": "/api/agent-runs/01K_RUN/events"
  }
}
```

`updated_messages` 返回本次提交所更新的历史 Assistant 消息，结构与 `/messages` 的 `items` 相同。普通发送时为 `[]`；批量回答成功时包含被回复的消息，其卡片已更新为 `status=completed`、`data.answered=true`，并在 `data.answers` 中保存答案。前端按消息 `id` 替换本地记录，再连接新 Run 的 SSE。刷新后通过 HTTP 历史恢复同样的题目、答案和已答状态。

## 6. Agent Run 与 SSE

SSE 的作用域是单个 Agent Run，不是整个 Conversation：

```text
一条用户消息或一次确认操作
  → 创建一个 Agent Run
  → 返回该 Run 唯一的 stream_url
  → SSE 只推送该 Run 的消息文本、临时工具状态、卡片及卡片状态
  → Run 完成、失败、取消或等待用户后关闭连接
```

- 历史 Conversation 消息只通过 HTTP 获取。
- SSE 不发送此前 Agent Run 的历史消息。
- 用户回答 Clarify、请求回测或再次追问时，会创建新的 Agent Run 和新的 `stream_url`。
- Messages 响应中的 `active_run` 只表示前端当前应连接的一个 `queued/running` Run。Agent 调用 `replay_run` 时内部会有一个 Replay 执行 Run，但它的状态卡同步到外层消息 Run，前端仍只连接消息 Run。

内部职责边界：

```text
AgentLoop → RunOutputStore → Redis
Redis → SSE API → 前端连接
AgentRunExecutor → AgentRunFinalizer → DAO → MySQL
```

- Agent Loop 只输出 Delta/Event，不处理或感知 SSE 连接。
- Redis 隔离生成端和传输端；零个、一个或多个 SSE 连接都不影响 Agent 执行。
- SSE API 只读取 Redis 并写入当前 HTTP Response，不负责保存最终业务数据。
- Agent Run 的最终落库由 Executor 调用 Finalizer 完成。

### 6.2 为什么使用 fetch SSE

浏览器原生 `EventSource` 不能设置 `Authorization` Header。本项目使用 `fetch()` 获取 `text/event-stream` 并通过 `ReadableStream` 解析 SSE，不把 JWT 放进 URL。

前端伪代码：

```ts
const response = await fetch(streamUrl, {
  headers: {
    Authorization: `Bearer ${accessToken}`,
    Accept: "text/event-stream",
  },
  signal: abortController.signal,
});

if (!response.ok || !response.body) {
  // 按统一错误响应处理
}

// 使用项目 SSE parser 逐块解析 response.body，不按网络 chunk 直接 split 行。
```

### 6.3 SSE 响应 Header

```http
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```

服务端每 15 秒发送注释心跳：

```text
: ping 2026-08-20T09:30:15Z

```

### 6.4 SSE 与 Access Token 生命周期

- Access Token 只在建立 SSE HTTP 连接时校验一次。
- SSE 建立成功后，即使 Access Token 在运行途中到达 `exp`，服务端也不因此主动关闭该连接。
- 不在心跳或每个事件上重复校验 JWT 过期时间。
- 如果网络断开后重新连接时 Access Token 已过期，SSE 请求返回 `40102 AUTH_TOKEN_EXPIRED`。
- 前端调用 `POST /auth/refresh`，获得新 Access Token 后重新连接原来的 `active_run.stream_url`。
- Refresh 和重连不会创建新的 Agent Run，也不会重新提交用户消息、Clarify 回答或回测请求。
- 重连成功后先收到该 Run 的 `run.snapshot`，再继续接收实时增量。

### 6.5 SSE Frame

所有 `data` 都包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `run_id` | string | Agent Run ID |
| `conversation_id` | string | Conversation ID |

### 6.6 SSE 事件

| event | payload | 前端行为 |
| --- | --- | --- |
| `run.snapshot` | `{run, messages, active_tools}` | 用本次 Run 的文本、卡片和正在执行的工具覆盖本地临时状态 |
| `message.delta` | `{message_id, start_offset, end_offset, delta}` | 消息不存在则创建，然后按字符偏移追加 Markdown |
| `tool.status` | `{message_id, id, label, status}` | 按 `id` 创建或更新临时工具执行状态 |
| `card.upsert` | `{message_id, card}` | 在对应消息的 `cards` 中，按 `card.id` 创建或整体替换 |
| `run.finished` | `{status, error}` | 标记 Run 终态并关闭 SSE |

`run.finished.status` 只允许 `completed/failed/cancelled/waiting_user`；仅 `failed` 时 `error` 非空。前端收到 `run.finished` 时同时清除该 Run 仍存在的临时 Tool Status。

协议刻意不定义 `run.started`、`message.started`、`message.completed`、`tool.started`、`tool.completed`、`card.created` 和 `card.updated`：

- Run 是否已开始由 `run.snapshot.run.status` 表达，额外的 `run.started` 不会带来新的业务状态。
- 第一条 `message.delta` 到达时，前端若找不到 `message_id`，直接创建空的 Assistant 消息并追加文本；不需要先等 `message.started`。
- 第一条 `card.upsert` 也可以创建对应 `message_id` 的 Assistant 消息容器，因此卡片可以先于文本出现，也可以完全不带文本。
- 第一条 `tool.status` 同样可以创建对应 `message_id` 的前端临时 Assistant 容器；这不代表单独创建一条持久化 Message。工具开始与结束统一使用同一事件和 `id` 原位更新。
- `card.upsert` 同时覆盖创建和更新，前端不需要维护两套分支。
- 消息是否已经完成跟随整个 Run 的 `run.finished`；当前不存在“一次 Run 内某条消息先独立完成、其他消息继续生成”的业务需求，因此不重复发送 `message.completed`。
- `run.finished` 不能省略，因为单纯关闭连接无法区分正常完成、等待用户、业务失败和网络中断。

服务端在每条 Assistant 消息开始输出前生成固定的 `message_id`，属于该消息的文本、临时工具状态与卡片事件始终使用同一 ID。

收到 `run.finished` 后，前端将该 Run 下仍为 `streaming` 的消息统一收尾：Run 为 `completed/waiting_user` 时设为 `completed`，Run 为 `failed/cancelled` 时设为对应状态。以后只有真的出现“同一 Run 内多条消息需要独立结束”的业务场景，才新增消息级终态事件。

不得用 `message.delta` 传内部思维过程、隐藏推理、Prompt、代码执行日志或服务队列术语。

`run.snapshot` 示例：

```json
{
  "run": {
    "id": "01K_RUN",
    "status": "running"
  },
  "active_tools": [
    {
      "message_id": "01K_MESSAGE",
      "id": "call_01K",
      "label": "正在读取回测详情",
      "status": "running"
    }
  ],
  "messages": [
    {
      "id": "01K_MESSAGE",
      "role": "assistant",
      "status": "streaming",
      "content": "我正在整理策略规则",
      "cards": [
        {
          "id": "01K_CARD",
          "type": "strategy_card",
          "status": "generating",
          "resource_id": null,
          "title": "正在生成 Strategy",
          "summary": null,
          "data": null
        }
      ]
    }
  ]
}
```

Snapshot 中的 `messages` 只包含本次 Agent Run 创建或正在更新的文本，以及这些消息所附卡片的最新概要和状态；`active_tools` 只包含当下仍在执行的临时工具状态。Snapshot 不包含整个 Conversation History，也不包含 Strategy 或 Replay 详情。历史记录仍由 `GET /conversations/{id}/messages` 返回。

#### Tool Status 协议

`tool.status` 用于不产生持久业务资产的通用读取或检查工具，例如“读取网页策略详情”和“读取回测详情”。

开始执行：

```text
event: tool.status
data: {"run_id":"01K_RUN","conversation_id":"01K_CONVERSATION","occurred_at":"2026-08-20T09:31:00Z","payload":{"message_id":"01K_MESSAGE","id":"call_01K","label":"正在读取回测详情","status":"running"}}
```

执行完成：

```text
event: tool.status
data: {"run_id":"01K_RUN","conversation_id":"01K_CONVERSATION","occurred_at":"2026-08-20T09:31:02Z","payload":{"message_id":"01K_MESSAGE","id":"call_01K","label":"已读取回测详情","status":"completed"}}
```

`status` 只允许 `running/completed/failed`。前端使用同一 `id` 原位更新；收到 `completed/failed` 后可以短暂展示再折叠或淡出。

`label` 由服务端 Tool Definition 生成，不使用模型自由生成的文案。事件不发送原始 Tool Name、Arguments、Result、内部日志或异常堆栈。工具结果只进入 Agent Transcript，Agent 随后通过 `message.delta` 继续回答。

Tool Status 不单独创建 Conversation Message、不写入 MySQL，也不进入 HTTP 历史消息。Redis `RunLiveState` 只保存当前 `running` 项；新连接使用 `run.snapshot.active_tools` 恢复当前进度，已结束的历史 Tool Status 不恢复。

`RedisRunOutputStore` 处理 Tool Status 时必须先更新 `RunLiveState` 再发布事件：`running` 时加入 `active_tools`，`completed/failed` 时从 `active_tools` 移除。这与文本、Card 使用同一 Snapshot 边界规则，保证断线重连时不会留下已结束的“正在读取”状态。

#### Snapshot 与实时 Delta 的实现模型

Agent 生成过程不依赖前端连接，前端连接、断开或重连都不能暂停或改变 Agent。服务端为每个运行中的 Agent Run 维护一份短期 `RunLiveState`：按 `message_id` 保存当前完整文本、Offset 和有序 `cards` 数组，按 Tool Call ID 保存当前 `active_tools`，同时保存 Run 状态以及服务端内部使用的最后 Redis Stream ID。

Agent Loop 每次获得新的 LLM 文本块时只调用 `RunOutputStore` 输出 Delta。`RedisRunOutputStore` 负责：

1. 将文本追加到 `RunLiveState.messages[message_id].content` 并更新该消息的 Offset。
2. 发布带有 `start_offset/end_offset` 的 `message.delta`。

这两项 Redis 更新必须保持一致，但属于输出存储实现，不属于 Agent Loop 或 SSE 连接逻辑。Agent Loop 不持有前端连接列表，也不向任何 SSE Response 直接写数据。

`RunLiveState` 才是运行过程中 Snapshot 的实时来源。Snapshot 本身不是持续变化并反复推送的对象；每次建立 SSE 连接时，服务端从当时的 `RunLiveState` 复制一份不可变快照发送给该连接。

为了覆盖“读取 Snapshot 的同时生成器仍在输出”的竞态，SSE 服务必须按以下顺序建立连接：

1. 先订阅该 Run 的实时事件，并开始在服务端缓冲新事件。
2. 再读取当前 `RunLiveState`，向前端发送 `run.snapshot`。
3. 根据 Snapshot 对应的最后 Redis Stream ID，丢弃已经包含在 Snapshot 中的缓冲事件，只发送边界之后的新事件；文本 Offset 继续作为前端内容连续性校验。
4. 继续转发之后到达的新事件，直到 Run 进入终态并关闭 SSE。

因为生成器总是“先更新实时状态，再发布 Delta”，所以：订阅前产生的文本一定已包含在 Snapshot 中；订阅后产生的文本一定会进入连接缓冲。两者可能重叠，但不会形成缺口，重叠部分由 Offset 去重。这个过程不需要暂停 Agent。

生产环境中 `RunLiveState` 与实时事件通道必须是 API 实例和 Agent Worker 可共同访问的短期基础设施；共享内存仅用于单进程开发，分布式部署使用 Redis。MySQL 检查点用于历史读取和故障恢复，不作为正常连接时实时 Snapshot 的唯一来源。

前端连接时不传事件 `seq`。文本连续性由 `start_offset/end_offset` 校验；Tool Status 按 `id` 更新；卡片先按 `message_id` 定位所属消息，再按 `card.id` 原位替换。SSE 建立后依赖 HTTP/TCP 保序；连接中断时重新建立连接并获取新的 Snapshot，而不是要求旧连接续传。

前端收到快照后直接替换对应 Run 的临时 UI。随后处理 delta 时：

`start_offset/end_offset` 使用 Unicode Code Point 数量；Python 使用 `len(content)`，JavaScript 使用 `Array.from(content).length`，避免 Emoji 等字符造成偏移理解不一致。

- `end_offset <= 当前内容长度`：该 delta 已包含在快照中，忽略。
- `start_offset == 当前内容长度`：正常追加。
- `start_offset > 当前内容长度`：出现缺口，重新获取 Run/Message 快照，不猜测缺失内容。

#### Run 终态持久化顺序

Agent Loop 返回最终 `AgentRunResult` 后，由 `AgentRunExecutor` 负责收尾：

```text
AgentRunExecutor
  → AgentRunFinalizer
      → DAO 事务写入 MySQL
  → MySQL 提交成功
  → RunOutputStore 发布 run.finished
  → SSE API 转发终态事件并关闭连接
```

成功事务保存该 Run 产生或更新的全部 Assistant 最终消息及其 `cards` 数组，更新 Agent Run、Conversation，并按本次结果写入 Strategy、Replay 等相关业务数据。失败或等待用户时同样先通过 Finalizer 保存对应状态，再发布 `run.finished`。

必须先提交 MySQL，再发布 Redis `run.finished`。否则前端收到终态后立即请求 HTTP 详情，可能读取不到最终数据。SSE API 不参与该事务，也不能承担最终消息落库职责。

### 6.7 Clarification Card

```json
{
  "id": "01K_CARD",
  "type": "clarification_card",
  "status": "waiting_user",
  "resource_id": null,
  "title": "需要确认策略信息",
  "summary": "请选择交易市场和执行周期",
  "data": {
    "questions": [
      {
        "id": "01K_QUESTION_MARKET",
        "question": "这个策略用于现货还是合约？",
        "required": true,
        "options": ["现货", "合约"],
        "allow_custom": false
      },
      {
        "id": "01K_QUESTION_TIMEFRAME",
        "question": "使用哪个执行周期？",
        "required": true,
        "options": ["1h", "4h"],
        "allow_custom": true
      }
    ],
    "answered": false,
    "answers": []
  }
}
```

Clarification 与其他卡片一样通过 `card.upsert` 发送。Agent 将当前已知、可一起确认的问题合并为一次 `ask_user` 调用，一张卡片包含 1～5 道题，每题提供 2～5 个快捷选项。前端按 `questions` 顺序让用户连续作答，完成整组后通过 `POST /conversations/{id}/messages` 一次提交 `structured_answers`，不逐题发送消息，不单独产生回答接口。
`options` 是 Agent 动态生成的选项文本数组，前端直接展示并将选中的文本作为回答提交；当前不定义额外的 `label/value` 对象。

每题的 `id` 由服务端生成，在 SSE 和历史消息中保持稳定，前端原样用作 `question_id`。旧历史卡片缺少题目 ID 时，服务端读取时补齐稳定 ID，无需前端自行生成。当前生成的题目均为 `required=true`；`allow_custom=false` 时只能提交选项中的文本。仅当前题的答案引入无法预先确定的新问题时，Agent 才在下一轮继续询问。

提交成功后卡片保留原有题目，将 `status` 置为 `completed`、`data.answered` 置为 `true`，`data.answers` 按题目顺序保存 `{question_id,value}` 或 `{question_id,custom_text}`。前端据此恢复已答内容并停止重复提交。

Clarification 是全局通用交互，不是回测专用确认：问题能归纳为少量封闭选项、点击明显比输入更方便时使用。需要开放式补充、解释取舍，或者按钮没有降低回答成本时，Agent 直接在 Markdown 中自然语言提问；用户仍通过同一个消息接口回答。

### 6.8 Card 协议

SSE 中的卡片只携带前端展示和后续 HTTP 跳转所需的最小信息：

```json
{
  "id": "01K_CARD",
  "type": "replay_card",
  "status": "queued",
  "resource_id": "01K_REPLAY",
  "title": "BTC 均线趋势策略 · 第 1 次验证",
  "summary": "正在准备行情数据",
  "data": null
}
```

Card 公共字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | Card ULID；创建后保持不变，是更新卡片的唯一键 |
| `type` | string | 卡片渲染类型；新增类型不改变 SSE 事件协议 |
| `status` | string | 当前状态；合法值由具体 `type` 定义 |
| `resource_id` | string/null | 对应业务资源 ID；生成完成前或无独立资源时为空 |
| `title` | string | 卡片标题 |
| `summary` | string/null | 卡片简要说明 |
| `data` | object/null | 类型专属的轻量展示数据；不得放入完整业务详情 |

首次出现：

```text
event: card.upsert
data: {"run_id":"01K_RUN","conversation_id":"01K_CONVERSATION","occurred_at":"2026-08-20T09:32:00Z","payload":{"message_id":"01K_MESSAGE","card":{"id":"01K_CARD","type":"replay_card","status":"queued","resource_id":"01K_REPLAY","title":"BTC 均线趋势策略 · 第 1 次验证","summary":"正在准备行情数据","data":null}}}
```

完成后更新同一张卡：

```text
event: card.upsert
data: {"run_id":"01K_RUN","conversation_id":"01K_CONVERSATION","occurred_at":"2026-08-20T09:32:09Z","payload":{"message_id":"01K_MESSAGE","card":{"id":"01K_CARD","type":"replay_card","status":"queued","resource_id":"01K_REPLAY","title":"BTC 均线趋势策略 · 第 1 次验证","summary":"已确认，等待执行","data":null}}}
```

前端先按 `message_id` 定位消息，再在该消息的 `cards` 数组中按 `card.id` 执行 upsert：不存在则追加，存在则使用完整 `card` 对象原位替换。首次出现顺序就是卡片展示顺序，后续更新不得改变位置。Redis Stream 保证同一 Run 内事件顺序，因此不额外引入卡片 `version`。

一条 Assistant Message 可以包含零张、一张或多张卡片。同一条消息中的每张卡片必须使用不同 `card.id`；一张卡片从 `generating` 更新为 `completed` 时必须保持原 ID。新增卡片类型只需要新增对应 Card Schema 和前端 Renderer，不新增 SSE event。

当前卡片类型：

- `clarification_card`：`waiting_user/completed`。
- `strategy_card`：`generating/completed`。
- `replay_card`：`queued/running/completed/failed/cancelled`。
- `actions`：`available/disabled`，预留。

`replay_confirmation` Renderer 暂时保留兼容，但 Agent 当前不生成该卡片。

以上只是当前 Renderer 注册表，不是封闭枚举。前端遇到暂不认识的 `type` 时，至少可以使用公共字段渲染通用标题、摘要和状态，不得因此中断后续 SSE 处理。

回测执行期间不定义结构化阶段列表，通过同一张 `replay_card` 的 `status/summary` 表达必要状态。未来如果需要更细进度，仍只扩展该卡片，不新增独立进度实体。

预留确认卡片通过 `data.conditions` 携带允许用户编辑的少量条件；运行中的 Replay 卡片不携带 Strategy Code、K 线、交易记录、Timeline、洞察或报告。`resource_id` 可用后，前端通过 Strategy 或 Replay HTTP 接口获取详情。

### 6.9 首次连接与断线恢复

前端进入 Conversation 详情页时：

1. 并行请求 `GET /conversations/{id}`、`GET /conversations/{id}/messages` 和所需资产接口。
2. HTTP Messages 负责渲染已经持久化的完整历史。
3. Messages 响应的 `active_run=null` 时不建立 SSE，页面完全使用 HTTP 数据。
4. `active_run` 存在时连接其 `stream_url`。
5. SSE 首条 `run.snapshot` 中的当前 Run 消息按 `message_id` upsert 到消息列表，之后再追加 Delta。

若 Run 在“Messages 返回 active_run”之后、SSE 真正建立之前已经完成，SSE 接口仍返回一次包含最终消息和终态 Run 的 `run.snapshot`，随后发送对应终态事件并关闭。Snapshot 与 HTTP 历史出现同一消息时统一按 `message_id` upsert，不会重复展示，也不需要重新提交消息。

SSE 本身只负责实时传输，本项目不承诺逐包重放。恢复的是当前文本、正在执行的工具和卡片最新状态：

1. 网络断开后，前端只检查刚才断开的 `run_id`，调用 `GET /agent-runs/{run_id}`；需要时同时刷新 Conversation Messages。
2. Run 已完成、失败、取消或 `waiting_user` 时，直接使用 HTTP 的消息和资源状态恢复页面，不再连接该 Run 的 SSE。
3. 只有该 Run 仍为 `queued/running` 时，才重新请求它原来的 `stream_url`。
4. 服务端新连接建立后首先发送 `run.snapshot`，仅包含该 Run 的文本、活动工具和卡片最新状态。
5. 前端使用 Snapshot 覆盖旧的流式文本、活动工具和卡片，再继续接收 `message.delta/tool.status/card.upsert`。
6. Access Token 过期时先调用 Refresh，再携带新的 Authorization 重连。

这种恢复允许丢失已经没有意义的中间传输包，但不会丢失用户消息、最终 AI 回复和已经持久化的卡片/资源结果，也避免把高频文本事件写入 MySQL。

## 8. Replay 创建与执行

### 8.1 核心边界

聊天主流程由 Agent 调用内部 `replay_run` Tool。用户已经明确要求回测且关键条件清晰时，Tool 直接创建 Replay、冻结 Strategy 与执行条件并启动回测，消息中直接出现 `replay_card`，不生成 `replay_confirmation`。

信息存在关键歧义时，Agent 使用自然语言或全局 `clarification_card` 询问；数据量超过服务端阈值时必须先取得用户同意或缩小范围。Clarification 只收集新的用户消息，不创建 Replay 草稿。

Agent Tool 只提交结构化条件。Replay 的数据库创建、幂等、Strategy 快照冻结、行情准备和 Sandbox 执行仍由确定性 Controller/Core 完成。Replay 状态固定为：`queued/running/completed/failed/cancelled`。

`replay_confirmation` 和基于它的 `POST /replays` 暂时保留为传统表单/兼容入口，但不属于当前 Agent 聊天流程。

### 8.2 接口清单

| Method | Path | 用途 |
| --- | --- | --- |
| POST | `/replays` | 备用传统表单入口：创建 Replay 并启动执行 |
| GET | `/replays/{replay_id}` | 获取 Replay 状态、条件和已有结果 |
| POST | `/replays/{replay_id}/cancel` | 取消 queued/running Replay |
| POST | `/replays/{replay_id}/retry` | 重新执行 failed/cancelled Replay |

### 8.3 Replay 执行条件

Agent Tool 或备用 `POST /replays` 最终都必须形成以下完整条件：

```json
{
  "symbol": "BTC/USDT",
  "market_type": "spot",
  "contract_type": null,
  "start_at": "2025-08-20T00:00:00Z",
  "end_at": "2026-08-19T23:59:59Z",
  "initial_capital": "10000.00000000",
  "leverage": null
}
```

现货固定 `contract_type=null`、`leverage=null`；合约 MVP 使用 `contract_type=perpetual`，`leverage` 必须大于等于 `1`。Strategy 方向、执行周期、手续费、滑点、仓位规则和数据源由 Strategy Code 与服务端规则解析，不允许前端提交。

MVP 固定使用单向净持仓：现货只做多；合约 Strategy 可以声明 `long/short/both`，但同一时刻只能有一个净持仓方向，不支持 Hedge Mode。

### 8.4 `POST /replays`（备用传统表单入口）

当前 Agent 不调用此 HTTP 接口；它使用内部 `replay_run` 并复用相同 Replay 创建与执行逻辑。本接口暂时保留给未来高级参数表单和旧确认卡兼容。

Header：`Idempotency-Key` 必填。

```json
{
  "message_id": "01K_MESSAGE",
  "card_id": "01K_CARD",
  "conditions": {
    "symbol": "BTC/USDT",
    "market_type": "spot",
    "contract_type": null,
    "start_at": "2025-08-20T00:00:00Z",
    "end_at": "2026-08-19T23:59:59Z",
    "initial_capital": "20000.00000000",
    "leverage": null
  }
}
```

- `message_id`：承载确认卡片的 Assistant Message ID。
- `card_id`：该消息中 `replay_confirmation.id`。
- `conditions`：前端将确认表单当前值完整提交，允许用户在确认前修改。

后端在一个事务中完成：

1. 锁定当前用户的 Message，定位 `card_id`，校验其仍为 `replay_confirmation/waiting_confirmation`。
2. 从卡片内部读取可信的 `strategy_id/strategy_revision`，锁定 Current Strategy 并检查 revision 未变化。
3. 校验用户最终条件，重新解析 Strategy Runtime Spec，冻结 Strategy Design、Code、条件和执行假设。
4. 创建状态为 `queued` 的 Replay 和执行 Agent Run。
5. 保持 `card.id` 不变，把确认卡原位替换为带 `resource_id` 的 `replay_card/queued`。
6. 提交事务后启动后台执行并返回 HTTP `202`。

若校验失败，事务不创建 Replay。并发或重复点击由 Message 行锁、卡片状态和 `Idempotency-Key` 共同保证不会产生两个 Replay。

响应：

```json
{
  "replay": {
    "id": "01K_REPLAY",
    "status": "queued",
    "confirmed_at": "2026-08-20T09:32:00Z"
  },
  "agent_run": {
    "id": "01K_RUN",
    "status": "queued",
    "stream_url": "/api/agent-runs/01K_RUN/events"
  }
}
```

前端立即连接 `stream_url`。SSE 使用同一 `card.id` 推送 `replay_card` 的 `queued/running/completed/failed/cancelled` 最新状态；完整数据始终通过 Replay HTTP 接口读取。

### 8.5 `POST /replays/{id}/cancel`

Header：`Idempotency-Key` 必填。只允许取消 `queued/running`：

```json
{
  "id": "01K_REPLAY",
  "status": "running",
  "cancel_requested": true
}
```

`queued` 可以立即变为 `cancelled`；`running` 记录取消请求，由执行器在安全检查点停止。已经完成的 Replay 不删除，接口返回 `completed` 和 `cancel_requested=false`。

### 8.6 `POST /replays/{id}/retry`

Header：`Idempotency-Key` 必填，请求体为空。只允许 `failed/cancelled`，复用同一个 Replay ID、已冻结 Strategy Code 和条件，增加内部 `attempt` 后重新进入 `queued`。重试不要求再次确认，也不创建第二个 Replay。

响应结构与 `POST /replays` 相同，并返回新的 `agent_run.id/stream_url`。

## 9. Replay 数据与播放

### 9.1 接口清单

| Method | Path | 用途 |
| --- | --- | --- |
| GET | `/conversations/{conversation_id}/replays` | 已完成 Replay History/Workspace 切换列表 |
| GET | `/replays/{replay_id}` | Replay Workspace 首屏详情 |
| PATCH | `/replays/{replay_id}` | 仅修改 Replay 名称 |
| GET | `/replays/{replay_id}/candles` | 分页读取已冻结的 K 线和预计算状态 |
| GET | `/replays/{replay_id}/trades` | 交易与成交记录 |
| GET | `/replays/{replay_id}/insights` | Replay 过程洞察与全局复盘洞察 |
| GET | `/replays/{replay_id}/report` | 完整研究报告 |

Replay 在 Agent 的 `replay_run` Tool 真正发起回测时创建，在执行完成后拥有不可变结果数据。完整生成顺序为：

```text
历史行情与 Strategy 快照
  → 回测执行
  → 交易、成交和逐 K 状态序列
  → AI Insights 与 Report
  → 播放数据文件写入对象存储
  → MySQL 写入 Replay 结果及索引
  → replay_card.status=completed
```

`GET /replays/{id}` 在 `queued/running/failed/cancelled` 时也可读取状态、冻结条件和错误；`result/playback` 为空。K 线、交易、洞察和报告接口只在 `completed` 后可用。用户播放、暂停或拖动进度不会重新运行策略、调用 Agent 或修改 Replay；完成后的结果只读，只有 `name` 允许更新。

数据是“生成一次、只读获取”，但不保证“一个请求下载全部”：首屏摘要、交易、洞察和报告分别按需读取；K 线与逐 K 状态体量较大，按游标或时间窗口分段加载。

Replay 的交互由前端基于同一时间轴完成：

- 播放、暂停、倍速、拖动、逐根推进和图表动画均为前端状态。
- 前端根据 Trade Fill 的 `candle_id/action/price/reason` 在对应 K 线上生成 Timeline Marker，并按当前 K 线显示仓位、权益和交易状态，不向后端上报播放位置。
- `runtime` Insight 直接绑定一根 `candle_id`；前端播放到并处理完该 K 线后揭示，可以暂停、突出显示证据区间或等待用户继续。
- `global` Insight 在进入整体预览、播放完成或用户跳过播放后展示，不要求绑定时间点。
- 点击 Trade、Fill 或有时间证据的 Insight 时，前端在本地定位对应时间点/区间。
- 用户继续追问时，调用 Conversation Message 接口并携带 `replay_id` 及可选的 `trade_id/fill_id/insight_id/timestamp`，创建新的 Agent Run；它是新的聊天交互，不属于 Replay 播放协议，也不修改原 Replay。

`items[].id` 是 Replay 发布时为该根 K 线生成的稳定 `candle_id`，Trade、Fill 和 Insight 都通过它直接关联 K 线。`sequence` 是主时间轴内从 1 开始的播放顺序，`time` 表示 K 线开盘时间。前端不需要再用时间戳、分页位置或数组下标猜测关联关系。

当前 Replay 播放只使用 `execution_timeframe` 对应的主 K 线序列，因此关联字段不再重复携带 `timeframe`。辅助周期数据属于策略计算输入，不作为独立播放时间轴；以后如果产品需要同时展示多周期图表，再为 Candle 增加对应的数据集关系，而不是把周期信息散落在每个 Insight 和 Fill 中。

Replay 只会在对象存储文件和数据库索引都准备完成后发布，因此正常情况下不存在“Replay 已可见但播放数据仍在准备”的状态。前端不直接依赖对象存储内部 Key。

### 9.7 `GET /replays/{id}/trades`

Query：`page/size/direction/exit_reason`。

一条 Trade 表示一次完整的净持仓周期。分组由回测执行器完成，前端不参与判断：

1. 净仓位从 `0` 变为非 `0` 时创建 Trade。
2. 持仓期间同方向成交属于 `increase`，仍在当前 Trade 中。
3. 反方向成交未使仓位归零时属于 `reduce`，仍在当前 Trade 中。
4. 净仓位回到 `0` 时以 `close` 结束当前 Trade。
5. 一次成交使仓位穿过 `0` 时，执行器在同一根 K 线上拆为旧 Trade 的 `close` Fill 和新 Trade 的 `open` Fill。
6. 回测结束仍有持仓时，执行器生成 `reason=end_of_test` 的 `close` Fill，完成最后一条 Trade。

因此，持仓过程中可以继续买卖，但只有仓位归零后再次建立仓位才计算新的 Trade。`trade_count/win_count/loss_count` 均以该规则生成的 Trade 为统计单位。

```json
{
  "items": [
    {
      "id": "01K_TRADE",
      "sequence": 1,
      "direction": "long",
      "status": "closed",
      "entry_candle_id": "01K_ENTRY_CANDLE",
      "exit_candle_id": "01K_EXIT_CANDLE",
```

K 线关联规则：

- `Trade.entry_candle_id`：首次开仓成交所在的 K 线。
- `Trade.exit_candle_id`：最终平仓成交所在的 K 线。
- `Fill.candle_id`：本次实际成交所在的 K 线，是绘制成交 Marker 的直接依据。
- `entry_at/exit_at/occurred_at` 仍然保留，分别表达交易时间范围和成交的精确模拟时刻，不再用于推断 K 线。

- `items` 按 Trade `sequence` 排序；Fill 的 `sequence` 是 Replay 内全局成交顺序。前端需要完整成交时间轴时，将所有 Trade 的 Fill 拍平后仅按 Fill `sequence` 排序即可，不重新计算 Trade 归属。即使反手产生的平仓和开仓 Fill 位于同一根 K 线、具有相同 `occurred_at`，顺序也仍然确定。

### 9.8 `GET /replays/{id}/insights`

Insight 承担“陪用户分析交易过程”和“事后复盘”两种职责：

- `scope=runtime`：过程洞察。直接绑定 `candle_id`，前端处理完该 K 线后揭示；内容只能使用该 K 线收盘及之前已经发生的数据，禁止引用未来交易结果。

这里不再区分 `trigger_at` 和 `anchor`。过程洞察的 `candle_id` 同时表示“洞察属于哪根 K 线”和“播放到哪根 K 线时揭示”。分析器基于该 K 线处理完成后的数据快照生成洞察，前端也在这根 K 线上绘制 Marker。

## 10. Runner Package

Runner Package 使用一个“请求即等待、完成即下载”的接口，前端不创建 Package、不轮询状态，也不管理 Package ID。

### 10.1 `POST /runner-packages/download`

请求：

```json
{
  "strategy_node_id": "01K_NODE",
  "source_replay_id": "01K_REPLAY",
  "platform": "macos",
  "architecture": "arm64"
}
```

服务端校验 Strategy Node 归属后，使用以下内容计算稳定 Build Key：

```text
strategy_node_id + platform + architecture + runner_version + package_schema_version
```

处理逻辑：

```text
已有 ready 且未过期文件
  → 直接流式返回

已有 queued/building 任务
  → 当前 HTTP 请求加入同一任务的等待者
  → 构建完成后流式返回同一文件

不存在、已失败或已过期
  → 原子领取 Build Key
  → 只提交一个后台构建任务
  → 当前 HTTP 请求等待完成
  → 流式返回文件
```

响应 HTTP `200`，直接返回 ZIP：

```http
HTTP/1.1 200 OK
Content-Type: application/zip
Content-Disposition: attachment; filename="trade-lab-runner-macos-arm64.zip"
Content-Length: 48392012
```

规则：

- 前端点击后显示本地“正在构建”状态，不发起轮询；HTTP 请求返回文件或错误后结束状态。
- API 使用 `async` 等待后台完成通知，不在 API 进程执行打包，也不阻塞 Python Worker 线程。
- 客户端刷新或中断请求不取消后台构建；下一次相同 Build Key 请求继续等待已有任务。
- 多个并发请求只允许一个构建者，其余请求共享完成通知和最终文件。
- Runner 构建必须有服务端硬超时，API Gateway/Load Balancer 的响应超时必须大于该构建超时。
- 只能使用已经形成的 Strategy Node。传 `source_replay_id` 时，它必须关联同一 Strategy Node，但不参与 Build Key 计算。
- 下载包默认模拟模式，不包含用户交易所 API Key。
- 构建失败时，在尚未开始文件响应的前提下返回标准 JSON Error Envelope 和稳定错误码 `RUNNER_PACKAGE_BUILD_FAILED`。

MVP 真正的用户资产只有 Strategy 和 Replay。`card.type` 表示 UI 渲染类型，不表示 Assistant 消息类型，也不要求每种卡片都对应用户资产。当前 Agent 使用 `clarification_card/strategy_card/replay_card`；`actions` 和 `replay_confirmation` Renderer 暂时保留，当前聊天流程不使用。

## 13. 状态与前端动作

### 13.1 Strategy

| 状态 | 前端文案 | 主要动作 |
| --- | --- | --- |
| `draft` | 尚未完成回测 | 继续修改、准备回测 |
| `tested` | 已验证 | 查看 Replay、继续修改、下载 Runner |
| `modified` | 存在未验证修改 | 查看差异、准备回测 |
| `restored` | 从历史恢复，尚未重新回测 | 继续修改、准备回测 |
| `running` | 正在回测 | 查看进度、按能力取消 |

### 13.2 Replay 执行

| 状态 | 前端动作 |
| --- | --- |
| `queued` | 展示等待，不虚构百分比 |
| `running` | 展示真实阶段，可请求取消 |
| `completed` | 打开 Replay Workspace |
| `failed` | 展示原因，可重试 |
| `cancelled` | 可重试 |

`waiting_confirmation` 只属于预留的 `replay_confirmation` 卡片，不属于 Replay 当前执行状态。

### 13.3 Replay 边界

- `no_trades` 是成功结果，不显示错误态。
- `quality_status=warning` 展示风险提示但允许研究。
- `quality_status=unreliable` 明确阻止确定性结论。
- 强平成交使用 `action=liquidation`，不得作为普通止损展示。
- 所有 Replay 显示历史数据范围和延迟，不出现实时行情含义。

## 14. 安全与联调约束

1. 前端不得保存或展示 Strategy Code Files。
2. 前端不得把 JWT 或 Google Credential 写入日志或埋点。
3. 所有资源接口先按当前用户过滤；对他人资源统一返回 404，避免枚举。
4. SSE 只能订阅当前用户的 Run，不提供 URL Token 方案。
5. Markdown 渲染必须做 XSS Sanitization，不执行内嵌 HTML/脚本。
6. Replay 和 Strategy 中的数值字符串由统一 Decimal Formatter 显示。
7. 删除、恢复、Replay 创建和 Runner 构建不能因网络重试重复执行。
8. 前端不得根据中文 `message` 判断逻辑，只使用 HTTP Status、`code`、`error.key` 和资源状态。
9. API 字段只做向后兼容新增；删除或改变语义必须升级 `/api/v2`。

## 15. MVP 暂不提供的接口

- 邮箱密码、忘记密码和重置密码。
- Subscription、积分、充值和用户可见 Token Usage。
- Global Strategy Assets。
- 独立 Replay Compare。
- Strategy 直接编辑、参数面板和代码下载。
- 在线实盘、交易所 API Key 保存、订单和持仓。
- Replay 修改、覆盖、恢复或重跑同一记录。
- Runner 实例状态和本地运行控制。

这些能力不应以临时字段或隐藏接口提前混入 MVP 契约。
